Minimal coding agent: happy path and failure modes ​

ReviewedPublishedAI-assisted

Re-implements the Week 1 coding agent from Stanford CS146S and runs five offline scenarios with a scripted model to see where the minimal design works and where it fails.

Question
Does the minimal coding-agent design (text tool protocol, tool registry, nested loops) complete a multi-step edit, and how does it behave on malformed calls, unknown tools, paths outside the workspace, and destructive edits?
Hypothesis
The happy path works with two tool steps; the failure cases are not handled: they either crash, stop silently, or succeed when they should be refused.

Scripted model, not a real LLM

كل الردود اللي "الموديل" بيرجعها في التجربة دي مكتوبة مسبقًا في الكود (scripted fake model). ده مقصود: الهدف هنا نختبر الـ harness نفسه، يعني الـ loop والـ parser والـ tools، مش ذكاء الموديل. النتيجة اللي تحت اتولّدت فعلًا بتشغيل code/experiments.py يوم 2026-11-07 على Python 3.12.10.

Question and hypothesis ​

المحاضرة الأولى في Stanford CS146S بنت coding agent بسيط في حوالي 200 سطر Python، بتلات tools: read_file وlist_files وedit_file [eric2026post]. السؤال هنا: التصميم ده بيشتغل فعلًا في مهمة محتاجة أكتر من خطوة؟ وبيتصرف إزاي لما الحاجة تمشي غلط؟

Hypothesis: الـ happy path هيشتغل بخطوتين (قراءة وبعدين تعديل). لكن الحالات الصعبة مش متعالجة: هتلاقي حالة بتوقع البرنامج، وحالة بتقف من غير ما حد يحس، وحالة بتنجح مع إنها المفروض تترفض.

لو الـ agent رفض المسار اللي برا الـ workspace، أو بلّغ الموديل إن الـ tool call كان غلط بدل ما يسكت، يبقى الـ hypothesis غلط.

Learning objectives ​

  • تشغّل agent loop كاملة من غير API key، وتفهم كل رسالة بتتضاف للـ history.
  • تميّز بين الـ failure اللي بيوقع البرنامج (crash) والـ failure الساكت (silent failure)، وتعرف ليه التاني أخطر.
  • تستنتج من النتائج إيه الـ guardrails اللي أي coding agent حقيقي محتاجها.

Setup ​

الكود في code/:

  • mini_agent.py: الـ agent نفسه. نفس تصميم المحاضرة: الموديل يطلب الأداة بسطر tool: name({json})، والنتيجة بترجع رسالة user شكلها tool_result({...})، والـ dispatch بيستخدم TOOL_REGISTRY[name] مباشرة زي المحاضرة.

    فرق واحد مقصود: النسخة المنشورة بتضيف رد الـ assistant للـ history بس لما يكون رد نهائي، فالموديل بيشوف نتايج الأدوات من غير ما يشوف هو نفسه طلب إيه [eric2026post]. النسخة دي بتضيف كل رد، عشان الـ history تبقى مفهومة. الموديل الـ scripted مابيقراش الـ history، فالفرق ده مابيغيّرش الـ tools اللي اتنفذت ولا حالة الملفات في أي سيناريو؛ اللي بيتغير بس قايمة الـ roles في السيناريو 1 (بالقاعدة المنشورة كانت هتبقى 5 رسائل بدل 7).

  • experiments.py: خمس سيناريوهات، كل واحد في folder مؤقت جديد، بموديل scripted.

bash
cd content/labs/minimal-coding-agent/code
python experiments.py     # prints the transcript and writes ../results/run-output.txt

مفيش أي dependency برا الـ standard library، ومفيش network.

Method ​

كل سيناريو بيدي الـ agent طلب واحد، والموديل الـ scripted بيرجع ردود ثابتة. بنسجل: الـ tools اللي اتنفذت، آخر رد، وحالة الملفات بعد التشغيل.

#ScenarioWhat the scripted model sends
1Happy pathread_file، بعدها edit_file، بعدها رد نهائي
2Malformed calltool: read_file({'filename': 'hello.py'}) (single quotes، يعني JSON غلط)
3Unknown tooltool: run_tests({}) (أداة مش موجودة في الـ registry)
4Path escaperead_file على ../outside.txt (ملف برا الـ workspace)
5Destructive editedit_file بـ old_str فاضي على ملف موجود فيه 3 سطور

Analysis ​

الـ hypothesis اتأكد. الـ happy path اشتغل، والأربع حالات التانية كل واحدة فشلت بطريقة مختلفة.

أخطر حالة هي رقم 2، مش رقم 3. الـ crash في رقم 3 مزعج، بس على الأقل واضح: البرنامج وقف وقالك KeyError. في رقم 2 محدش عرف إن فيه مشكلة أصلًا. الموديل كان عايز يقرأ الملف، والـ parser ماقدرش يفهم الـ JSON، فرجع list فاضية. والـ loop متصممة إن "مفيش tool calls" معناها "الموديل خلص". فالـ agent وقف وطبع للمستخدم سطر الـ tool call نفسه كأنه إجابة. ده بيحصل بسبب سطر except: continue اللي الـ notes حذرت منه.

رقم 4 و5 مش bugs في الـ parsing. دي قرارات تصميم ناقصة. resolve_abs_path بتحوّل أي مسار لمسار كامل، بس مش بتتأكد إنه جوه المشروع. وedit_file بـ old_str فاضي معناها "اكتب فوق الملف كله". الموديل كان قصده يضيف عنوان، والنتيجة إن الملف اتمسح. الأداة عملت بالظبط اللي اتطلب منها، والمشكلة إن الـ interface بتاعها بيخلي الغلطة دي سهلة.

اللي الداتا بتقوله: التصميم الأساسي صح كـ core. التفسير (مش نتيجة مقاسة): أي coding agent حقيقي محتاج طبقة guardrails فوق الـ loop دي: error feedback للموديل، حد أقصى للخطوات، workspace restriction، وتأكيد قبل العمليات اللي بتمسح.

Limitations and threats to validity ​

  • الموديل scripted. موديل حقيقي ممكن يصلّح نفسه لو شاف رسالة error واضحة، بس هنا مفيش رسالة error أصلًا بتوصله، فده مش بيغيّر نتيجة رقم 2 و3.
  • الكود re-implementation مبنية على الكود المنشور في المقال والـ study notes، مش نسخة حرفية. الـ notes نفسها ملخص ثانوي اتكتب بمساعدة AI، والـ recording نفسه ماتراجعش.
  • كل سيناريو اتشغل مرة واحدة. مفيش عشوائية في التجربة دي، فالتكرار مش هيغيّر النتيجة.

Next steps ​

  • نضيف error feedback: بدل continue، نرجّع للموديل رسالة فيها سبب الفشل ونشوف (بموديل حقيقي) هل بيصلّح الـ call.
  • نجرب نفس السيناريوهات على native tool calling ونقارن.

Exercise: Harden the agent

عدّل mini_agent.py عشان السيناريوهات 2 و3 و4 و5 كلها تتعامل صح: الموديل يعرف بالغلط، والبرنامج مايقعش، والمسار اللي برا الـ workspace يترفض، والكتابة فوق ملف موجود تحتاج تأكيد.

Solution

اقتراح من أربع تغييرات صغيرة:

  1. في extract_tool_invocations رجّع الأخطاء كمان، مثلًا ("__invalid__", {"error": str(exc), "line": line})، والـ loop تبعتها للموديل كـ tool_result.
  2. استخدم TOOL_REGISTRY.get(name)، ولو مش موجودة ابعت {"error": "unknown tool", "available": list(TOOL_REGISTRY)}.
  3. في resolve_abs_path شيّك إن المسار جوه الـ workspace: if not path.is_relative_to(WORKSPACE): raise PermissionError(...).
  4. في edit_file_tool، لو old_str == "" والملف موجود، ارفض إلا لو فيه parameter صريح زي overwrite=True.

اتأكد بإنك تعدّل experiments.py بحيث كل سيناريو يطبع النتيجة المتوقعة الجديدة.

Review questions ​

  1. ليه السيناريو 2 أخطر من السيناريو 3، مع إن 3 هو اللي وقّع البرنامج؟
  2. في السيناريو 5، مين غلطان: الموديل ولا تصميم الأداة؟ دافع عن إجابتك.
  3. إيه علاقة "مفيش tool calls معناها خلصنا" بالـ silent failure في السيناريو 2؟
