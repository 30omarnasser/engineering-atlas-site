Good Vibrations? A Qualitative Study of Vibe Coding ​

ReviewedPublishedAI-assisted

دراسة نوعية (46 thread على Reddit، و88 post على LinkedIn، و11 interview) بتبني theory للـ vibe coding: محادثة مع الـ AI، وco-creation، وflow وjoy، والـ trust كعامل وسيط بيزوّد الـ flow والمخاطر مع بعض؛ ومعاها خريطة لـ 13 pain point و28 best practice مربوطين بشروط الـ flow.

In one paragraph ​

الـ paper بتسأل: المطورين نفسهم فاهمين الـ vibe coding إزاي، وبيعملوه ليه وإزاي، وبيقع فين؟ الباحثين (University of Michigan وMicrosoft Research وUniversity of Victoria وUMass Amherst) حللوا 134 post وأكتر من 5,000 comment على Reddit وLinkedIn، ومعاهم 11 interview [pimenova2025, Abstract]. الناتج theory فيها أربع مكونات: الـ paradigm (محادثة باللغة الطبيعية مع الـ AI)، والـ activity (co-creation)، والـ experience (flow وjoy)، والـ trust كعامل وسيط: الثقة الأعلى بتسمح بـ co-creation أعمق وflow أكتر، بس بتزوّد المخاطر على الـ software والمطور والمجتمع [pimenova2025, §4.1, Fig. 1]. ومعاها خريطة بتربط 13 pain point بـ 28 best practice وبشروط الـ flow [pimenova2025, Fig. 2]. دي دراسة نوعية: بتوصف تجارب وبتبني نظرية، ومش بتقيس إن أي practice بتشتغل.

Learning objectives ​

  • تشرح الأربع مكونات في الـ theory، وليه الـ trust "وسيط" مش مكوّن زي الباقي.
  • تحدد مكان الـ vibe coding على التلات محاور: interaction، وgrounding، وverification.
  • تعدّ الـ pain points الـ 13 وتربط كل واحد بالـ practices اللي في Fig. 2.
  • تفرّق بين اللي الـ paper لاحظته من المشاركين واللي هي بتقترحه أو بتفترضه.
  • تقرا نتايج دراسة نوعية من غير ما تحوّلها لأرقام انتشار.

Problem ​

المصطلح صاغه Andrej Karpathy في فبراير 2025: "fully give in to the vibes, embrace exponentials, and forget that the code even exist[s]" [pimenova2025, §4.1]. بس مفيش تعريف متفق عليه، والدراسات اللي سبقت ركزت على الكود الناتج أو على نظريات من غير بيانات كفاية [pimenova2025, Abstract]. الباحثين بيقولوا إن معنى المصطلح بيتحدد بالناس اللي بتستخدمه، مش باللي صاغه [pimenova2025, §4.1].

Where vibe coding sits ​

الـ paper بتقسّم البرمجة باللغة الطبيعية على تلات محاور [pimenova2025, §2.1]:

  • Interaction mode: طلب واحد (one-shot) ولا محادثة بتتحسن بالتدريج.
  • Grounding: كلام بس، ولا كلام معاه artifacts (أمثلة input/output، وtests، وtypes، وschemas).
  • Verification: فحص بالعين، ولا oracles منظمة (tests، ومخرجات متوقعة، وformal specs).

Analysis ​

اتبعوا flexible qualitative coding (Deterding and Waters) على تلات مراحل في NVivo 15 [pimenova2025, §3.3]:

  1. Index codes: سبع codes عامة: الخمسة بتوع الـ research questions (Definition، Practice، Perceptions، Pain Points، Best Practice)، وFuture Desires، وInteresting Quote.
  2. Analytic codes: codes صغيرة بكلام المشاركين نفسه (in vivo coding)، والـ saturation لما document جديد مايطلّعش code جديد.
  3. Axial coding: ربط الـ codes في categories وعلاقات على Miro.

ماحسبوش inter-rater reliability؛ استخدموا negotiated agreement (كل واحد يعمل coding لوحده وبعدين يتناقشوا). وقالوا إن IRR ممكن يوحي بموضوعية مش موجودة في بحث بيبني نظرية [pimenova2025, §3.3]. وماعدّوش تكرار كل theme عن قصد، عشان مايبانش إن فيه statistical significance [pimenova2025, §3.3].

Results ​

The four components ​

1. Conversational interaction (the paradigm). البرمجة بتحصل بالكلام، وبقراية وكتابة كود قليلة أو صفر: "you're just guiding the tool" (I8) [pimenova2025, §4.2]. والفرق عن الـ agentic coding عند واحد من المشاركين هو كمية التدخل: "The less I need to interact with the genie, the more agentic it becomes" (I7). ده وصف مشارك، مش تعريف رسمي. المزايا المذكورة: مجهود ذهني أقل، وتعلم أقل لحاجات مش عايز تتعلمها، وإتاحة البرمجة لغير المبرمجين، وflow [pimenova2025, §4.2].

2. Co-creation (the activity). الـ AI بياخد قرارات أعلى من التنفيذ، في الـ features والـ design: "the LLM is leading the process, as opposed to you leading the process" (I3). وفيه spectrum من co-creation كامل لـ delegation (أنت بتحدد والـ AI بينفذ)، والـ paper بتقترح إن الـ trust هو اللي بيحدد مكانك عليه [pimenova2025, §4.3].

3. Flow and joy (the experience). شروط Csikszentmihalyi للـ flow تلاتة: أهداف واضحة، وتوازن بين الصعوبة والمهارة، وfeedback فوري [pimenova2025, §4.4]. مشارك عنده 46 سنة خبرة قال إن الـ vibe coding "brings back the joy of programming" (I7). وفيه اللي وصفه بإنه "intoxicating" لأنك بتسيب قرارات كتير للـ agent (I6) [pimenova2025, §4.3].

4. Trust (the mediating factor). الثقة بتحدد قد إيه سلطة هتديها للـ AI، وبتدعم الـ flow عن طريق إحساس التحكم وسهولة الشغل؛ بس الثقة العالية بتجيب مخاطر [pimenova2025, §4.5]. مثال صريح: "you can basically set [roo] to auto-approve everything it does if you trust it" (R15)؛ ومثال ضمني: "Vibe coding is just approving pull requests you don't understand" (R41).

حاجات تستاهل تتلاحظ من الـ quotes:

  • الـ personas ممكن تأذي: مشارك كتب في الـ rules إن الـ agent "best senior programmer"، فبطّل يعمل endpoints وsession tests و"acted like an arrogant know-it-all dev" (R43) [pimenova2025, §4.2].
  • الـ agent بيعدّل الـ tests: "the tests all passed, except for one which isn't our fault" (I5) [pimenova2025, §4.3].
  • الـ version control: "I had 30 files in my change log with hours of work uncommitted" (R35) [pimenova2025, §4.3].
  • الـ external memory: مشارك بنى tool بيعمل code map للمشروع كله "so AI tools can actually follow what's going on" (R14) [pimenova2025, §4.4].
  • ثنائية في الـ practices: ناس بتفضّل تعليمات محددة في كل prompt (تحكم)، وناس بتحط guidance عامة مرة واحدة في الـ context (سهولة). الباحثين بيفترضوا إن الاختيار ده مرتبط بالـ trust، ومش بيثبتوه [pimenova2025, §4.4].

The code review problem ​

الـ manual review بيزوّد الثقة: "read the code line by line, and test what the code does" (I11). بس هو نفسه pain point: "My 400-line code is now 3000 lines and neither of us can read it anymore" (R63). فيه اللي بيرجّع المراجعة للـ AI، وده بيحافظ على الـ flow بس بيعكس ثقة عالية في الموديل، و"it is unclear how effective these strategies are compared to traditional code review" [pimenova2025, §4.5]. والـ implication العملية في الـ discussion: الفرق "cannot outsource verification to the same models that generate code" [pimenova2025, §5.2].

Platform differences ​

LinkedIn أكتر إيجابية (إنتاجية ونجاح)، وReddit أكتر سلبية (pain points ومخاطر)، والـ interviews أكتر توازن [pimenova2025, §5.1]. التفسير المقترح: LinkedIn بالاسم الحقيقي والـ impression management، وReddit pseudonymous ومعاه negativity bias. بس الاتجاهات دي مش مطلقة، وكل مكونات الـ theory ظهرت في التلات مصادر [pimenova2025, §5.1]. الدرس: ماتقيّمش أداة AI من مصدر واحد.

Implications ​

[pimenova2025, §5.2]:

  • Education: تعليم التعاون مع الـ GenAI جنب الأساسيات (algorithms، وtesting، والنظرية)، والحذر من skill atrophy.
  • Practice: الـ review load كبير، والفرق محتاجة processes ليه.
  • Tooling: دمج الـ version control والـ provenance، وذاكرة محادثة أطول، وruns قابلة للإعادة، مع الحفاظ على سرعة الاستجابة وإحساس التحكم.
  • Research: اختبار الـ pain points والـ practices تجريبيًا، ودراسات طويلة للمهارات والثقة، وتقييم في بيئات صناعية، وتقييم أمني للكود الناتج.

Technical example ​

Fig. 2 كبيانات: Python script كتبته بنفسي بينقل الصورة صف بصف، وبيتأكد إن الأعداد مطابقة لنص الـ paper (13 pain point، و8 interaction practices، و20 co-creation practices)، وبيعدّ كل flow code اتربط بكام practice. اتشغل على Python 3.12.

from collections import Counter

FLOW = {  # Fig. 2 legend: A-C are conditions for flow, D-G are characteristics of flow
    "A": "clear set of goals", "B": "balance of challenge and skill", "C": "clear, immediate feedback",
    "D": "sense of control", "E": "rewarding process", "F": "in the moment", "G": "effortlessness",
}

# pain point -> [(best practice, flow codes)], transcribed row by row from Fig. 2
INTERACTION = {
    "AI company oversight": [],
    "Inaccurate self-assessment": [("Mindset management", "EF")],
    "Accurately specifying intent": [("Use AI to refine intent", "AG"), ("Use personas", "EF"),
                                     ("Prompt engineering", "BD")],

                                           ("Proactive conversation management", "B"),

}
CO_CREATION = {

    "Version control": [("External version control", "C"), ("AI logs changes", "C")],
    "Poor structure, planning": [("Plan first", "A"), ("Actively manage structure and abstractions", "D")],

def practices(group: dict) -> list[tuple[str, str]]:

counts = Counter(code for _, codes in interaction + co_creation for code in codes)
for code, n in sorted(counts.items(), key=lambda kv: (-kv[1], kv[0])):
    print(f"  [{code}] {FLOW[code]:<30} {n}")

Limitations ​

Stated by the authors [pimenova2025, §7]:

  • البيانات snapshot من مايو لـ يوليو 2025، والممارسات بتتغير بسرعة.
  • الـ sampling (top posts والأحدث، وحد أقصى للنتايج) ممكن يزوّد وزن الـ posts الأكتر تفاعل والـ early adopters.
  • 11 interview بس، وفيه recall bias لأن المشاركين بيحكوا تجارب قديمة.
  • اختاروا الناس اللي بتستخدم مصطلح "vibe coding"، فاللي بيعمل نفس الحاجة باسم تاني ممكن يكون مش ممثّل.
  • المشاركين متطوعين من غير مقابل، ومن snowball sampling وقنوات community.

My assessment:

  • Fig. 2 فرضية مش نتيجة: ربط كل practice بشرط flow تفسير الباحثين، والـ paper نفسها بتحط "empirical tests of reported pain points and real world impact of best practices" كـ future work [pimenova2025, §5.2].
  • الأدوات اتغيرت: الـ quotes بتتكلم عن Roo وClaude 3.7 وCursor credits [pimenova2025, §4.2][pimenova2025, §4.4]. الـ agents الحالية بتشغّل tests وبتعمل commits وعندها memory files، فبعض الـ pain points ممكن يكون اتغير شكلها.
  • الـ paper مش متسقة في رقم واحد: حجم r/vibecoding في المقدمة 159K وفي §3.2 156,000 (كلام عن أوقات مختلفة غالبًا) [pimenova2025, §1] [pimenova2025, §3.2].
  • مش peer reviewed: الـ PDF "Manuscript submitted to ACM"، وسطر "Received 20 February 2007; revised 12 March 2009; accepted 5 June 2009" في آخره placeholder جاي من template الـ ACM، مش تواريخ قبول حقيقية. وصفحة arXiv لسه كاتبة "19 pages, 2 figures" بتاعة v1، والـ v2 25 صفحة.
  • شفافية تستاهل التقدير: في footnote بيقولوا إن citation الـ eight flow traits منقولة من Royal ومش قاريين المصدر الأصلي غير إنهم اتأكدوا إنه موجود [pimenova2025, §6.5].

Exercises ​

Exercise: Map the symptom

لكل موقف، حدد الـ pain point في Fig. 2 والـ practices المقابلة: (1) الـ agent قال "all tests pass" وانت اكتشفت إنه عدّل test. (2) بعد ساعتين في نفس الـ chat بقى يقترح حل اترفض قبل كده. (3) غيّر 30 ملف ومفيش commit.

Solution

(1) Incorrect solutions / low reliability: use or generate tests، وvalidate correctness، وmanual code review. (2) Inconsistent conversational memory: proactive conversation management (ابدأ chat جديد)، وexternal memory aids، وcontinuous consensus. (3) Version control: external version control وAI logs changes [pimenova2025, Fig. 2].
