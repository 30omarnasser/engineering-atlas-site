Agent Retrieval Bench: Evaluating Repository Context Retrieval for Coding Agents ​

ReviewedPublishedAI-assisted

Benchmark بيقيس هل الـ retriever يقدر يلاقي ملفات الـ repository اللي الـ coding agent محتاج يقراها قبل ما يعدّل، أو يعرف إن مفيش ملف محلي مفيد: 427 sample من 25 repository، ومفيش retriever واحد بيكسب في كل حاجة.

In one paragraph ​

معظم الـ benchmarks بتحكم على الـ coding agent من الآخر: الـ patch عدّى الـ tests ولا لأ. الـ paper دي بتقيس خطوة قبل كده: هل النظام لقى الملفات اللي الـ agent محتاج يقراها قبل ما يعدّل؟ الفكرة إن الـ relevance هنا معناها "الملف اللي هيساعدك في الخطوة الجاية"، مش "الملف اللي كلامه شبه السؤال". الـ benchmark فيه 427 sample من 25 repository، وكل sample مبني من إشارة حقيقية من شغل التطوير (PR، review comment، failure trace، edit معروف)، والبحث بيتم في نسخة الـ repository قبل الإصلاح [qin2026, Abstract]. النتيجة الأساسية: مفيش عيلة retrieval واحدة بتكسب في كل المهام والمقاييس، والـ embeddings والـ structure-aware retrieval بيكمّلوا بعض [qin2026, §8]. الكود والداتا منشورين [arb-repo; arb-data].

Learning objectives ​

  • تشرح الفرق بين semantic code search وما الـ paper بتسميه agentic relevance.
  • تعدّد الـ subsets الخمسة وتقول الـ gold في كل واحدة إيه.
  • تشرح إزاي الـ benchmark بيمنع تسريب الإجابة للـ retriever (frozen base commit و query sanitization).
  • تعرّف Recall@k وMRR وBCY@B وPES، وتعرف كل واحد بيقيس إيه ومابيقيسش إيه.
  • تقرا نتايج الـ leaderboard من غير ما تبالغ فيها: per-task، وrepository imbalance، والـ provisional rows.

Problem ​

الـ agent عشان يصلّح حاجة لازم الأول يجيب الـ context الصح: يقرا الملفات اللي تهم. والـ agents بتعمل ده بخليط من indexes وrepo maps وأدوات زي grep وقراية ملفات وبحث متكرر [qin2026, §1]. لو التقييم بيبص على الـ patch بس، الفشل في المرحلة دي بيستخبى جوه رقم واحد.

الـ paper بتقول إن الـ relevance في شغل الـ agents مختلفة عن الـ code search التقليدي. في الـ code search، الملف relevant لو معناه قريب من السؤال. هنا، الملف relevant لو قرايته هتساعد الـ agent ياخد الخطوة الصح الجاية، حتى لو مش شبه السؤال خالص [qin2026, §3]. أمثلة من الـ paper: PR بيوصف تعديل في الـ implementation والـ context المفيد هو regression test؛ review comment على ملف والقيد الناقص في module تاني؛ failure trace بيذكر test والسبب الحقيقي في ملف implementation [qin2026, §1].

والـ claim بتاعهم محدود عن قصد: component-level مش end-to-end. هم بيقولوا صراحة إنهم مش بيدّعوا إن الـ retrieval هو السبب الأساسي لفشل الـ patches، ولا إن File F1 بديل عن repair بيعدّي الـ tests [qin2026, §1].

Construction and leakage control ​

البيانات من سجلات تطوير عامة على GitHub في 25 repository متختارين عن قصد (مش random sample)، بست لغات أساسية: 13 Python، و3 Go، و3 Rust، و3 TypeScript، و2 Java، و1 JavaScript [qin2026, §5.1]. والـ corpus manifest الكامل فيه 308 base-commit snapshot، و391,932 ملف، و7,922,369 chunk؛ والـ samples المنشورة بتستخدم 271 snapshot منهم [qin2026, §5.1].

الخطوات اللي بتمنع الغش [qin2026, §5.1, §6]:

  1. الـ repository بيتجمّد عند الـ base commit، يعني قبل الإصلاح. وبيتأكدوا إن كل gold file موجود فعلًا في النسخة دي.
  2. الـ gold بيتحدد من evidence الإصلاح الحقيقي (الـ resolving change)، بس الـ retriever مابيشوفوش.
  3. الـ query بيتعمله sanitization: بيتشال الـ raw diff، والـ fix hash، والـ gold paths بالظبط، وأي artifacts متولدة من موديل (suggestions أو review analysis). في trace2code الـ stack frames الظاهرة بتفضل، لأنها جزء طبيعي من الإشارة، مش تسريب.
  4. checks بعد التجميع: schema، ووجود الملفات في الـ corpus، والتكرار، والتسريب.

النتيجة المعلنة: صفر rows بـ schema أو corpus غلط، وصفر fatal shortcut leakage في الأربع فئات اللي اختبروها [qin2026, §6, Table 3]. وهم نفسهم بيقولوا إن ده بيثبت traceability مش إن كل ملف مفيد اتسجل: ممكن يبقى فيه ملفات مفيدة تانية مش متعلّمة gold [qin2026, §6].

Baselines ​

تلات عائلات static retrieval [qin2026, §7]:

  • Lexical: BM25 العادي، وكمان heuristic اسمه "lexical": TF-IDF-style مع bonuses للـ path والـ basename والـ symbols. الـ paper بتنبّه إنه مش BM25.
  • RepoMap: baseline من غير vectors، مستوحى من الـ repo maps بتاعة الـ coding agents، بيرتّب الملفات بإشارات من الـ path والـ symbols والـ references والـ repository graph. في الجداول اسمه aider-style-repomap. للمقارنة: الـ repo map في Aider بيرتّب الملفات بـ graph، الملفات nodes والـ dependencies edges، وبيبعت للموديل خريطة مختصرة في حدود token budget [aider-repomap].
  • Embeddings (open-source): Qwen3-Embedding-4B، وQwen3-Embedding-8B، وjina-code-embeddings-0.5b، وpplx-embed-v1-4b، وnomic-embed-code. كل chunk بيتعمله embedding، والـ vectors بتتعمل L2 normalization، والترتيب بالـ dot product (يعني cosine)، وscore الملف = أعلى score لأي chunk فيه [qin2026, §7; qin2026, App. C]. ومن غير query أو passage prefixes، فدي zero-shot baselines مش أحسن configuration ممكنة لكل موديل [qin2026, App. C].

كل الـ positive rows بتبحث في كل ملفات الـ repository (candidate_filter=all_files) [qin2026, §7].

The pplx row is provisional

الـ pplx-embed-v1-4b طلّع tokenizer warning بيوصي بـ fix_mistral_regex=true، والـ evaluator ماعدّاش الـ option ده. فالـ paper بتعتبر نتايجه provisional لحد ما يتعاد تشغيله [qin2026, App. C].

Metrics ​

Recall@k: نسبة الـ gold files اللي ظهرت في أول k ملفات unique [qin2026, §3]. الصيغة دي كتابتي للتعريف ده، متوسطة على الـ samples:

Recall@k=1N∑i=1N|Gi∩Topk(i)||Gi|

حيث Gi الـ gold files للـ sample رقم i، وTopk(i) أول k ملفات في الترتيب.

MRR: بيعتمد على أول gold file في الترتيب [qin2026, §3]. بالتعريف المعتاد، لكل sample بناخد 1/ranki لأول gold file، وبعدين المتوسط. يعني لو أول gold في المركز 4، الـ sample ده بيساهم بـ 0.25.

BCY@B (Budgeted Context Yield): السؤال هنا: لو عندي budget قدره B token، قد إيه من الـ gold هيدخل فعلًا الـ context؟ الـ packing [qin2026, §3]:

  • الملفات بتترتب بالـ rank، ومن غير تكرار.
  • كل ملف بيتكتب كده: ### {path} وتحته المحتوى، والـ header والـ newlines بيتحسبوا من الـ budget.
  • الـ packing greedy، وآخر ملف بس هو اللي ممكن يتقص عند حد الـ budget.
  • الـ tokens بتتعد بـ tokenizer ثابت مبني على regex اسمه regex_code_tokenizer_v1.
BCYτ@B=1N∑i=1N1|Gi|∑g∈Gi1[mig(B)≥min(τ,Lig)]

حيث mig(B) عدد tokens المحتوى من الـ gold file g اللي دخلت تحت الـ budget، وLig طول الملف، وτ أقل محتوى لازم يدخل [qin2026, §3]. الـ canonical هو τ=1: يعني BCY بيقيس exposure (الملف ظهر في الـ context)، مش إن الملف كله اتقرا أو اتفهم. وجربوا τ لحد 128 والترتيب بين الـ methods ماتغيرش؛ أكبر نزول كان 0.0081 [qin2026, §8.5]. وخلي بالك: الـ details المتخزنة فيها أول 20 ملف بس، فـ BCY عند 16k و32k ممكن يبقى lower bound [qin2026, §3].

PES@k (Potential Exploration Savings): لكل sample، Ti هو الـ event اللي الـ agent لمس فيه أول gold file، وRi@k معناها الـ retriever حط gold في أول k [qin2026, §3]:

PES@k=1N∑imax(Ti−1,0)I[Ri@k]

يعني: لو الـ retriever كان لاقي الملف من الأول، كام خطوة استكشاف كان ممكن تتوفر؟ والـ paper صريحة إنه upper-bound proxy، مش تقدير causal لعدد الـ tool calls اللي هتتوفر فعلًا [qin2026, §3].

File F1: الـ F1 العادي بين الـ precision والـ recall على مستوى الملفات. في تجارب الـ agents، الـ final File F1 بيقيّم التلات ملفات اللي الـ agent سلّمهم في الآخر بس [qin2026, App. E].

RRF (reciprocal rank fusion): لدمج ترتيبين من غير ما نقارن scores مختلفة الطبيعة [qin2026, §8.3]:

sRRF(f)=∑m∈M160+rm(f)

حيث rm(f) ترتيب الملف f عند الـ method m (من 1)، والـ method بتساهم بصفر لو الملف مش في الـ top-20 المتخزن بتاعها.

Repository imbalance ​

Gin لوحده فيه 88 من الـ 345 positive sample، وأكبر 4 repositories فيهم 203 (58.8%) [qin2026, §8.1]. لما وزنوا كل repository بالتساوي بدل كل sample، Qwen3-4B بقى الأول في Recall@20 كمان (0.6344 قصاد 0.6193 لـ Qwen3-8B)، وRepoMap نزل لـ 0.4619 [qin2026, Table 5]. يعني جزء من تفوق Qwen3-8B وRepoMap جاي من الـ repositories اللي فيها samples أكتر.

A simple hybrid helps ​

دمج Qwen3-8B وRepoMap بالـ RRF، على الـ 287 sample بتوع code2test وcomment2context وtrace2code[qin2026, §8.4, Table 9]:

  • MRR من 0.2296 (أحسن نتيجة فردية) لـ 0.2713.
  • Recall@20 من 0.7070 لـ 0.7331.
  • في trace2code، Recall@20 بقى 0.8795، أعلى من الاتنين لوحدهم (0.8366 لـ RepoMap و0.7970 لـ Qwen3-8B).
  • BCY@8k للـ hybrid على نفس التلات مهام 0.4884 [qin2026, Table 10].

بس الـ hybrid مش retriever عام بيكسب في كل حاجة: في code2test الـ MRR بتاعه لسه أقل شوية من Qwen3-4B [qin2026, §8.4]. والدمج post-hoc على الـ top-20 المتخزن، مش موديل جديد اتدرّب.

Finding the file is not finding the lines ​

في الـ 345 positive sample، الـ median للـ gold file فيه 515 سطر، و51.8% منهم أطول من 500 سطر. وفي الـ 287 sample اللي ليهم line-span annotations، الـ evidence المتعلّمة median بتاعها 27 سطر بس، يعني 4.7% من الملف (median) [qin2026, §8.6, Table 11]. ولما قاسوا على مستوى السطور، الترتيب اتغير: Qwen3-8B الأول في File Recall@20 (0.7070) بس رابع في Line F1، وQwen3-4B الأول في Line F1 بـ 0.0276، وكل الـ Line F1 قليلة جدًا [qin2026, §8.6, Table 12]. (التحليل ده بيستخدم packing قديم بالحروف، مش الـ BCY الـ canonical.)

The budget changes the winner ​

في edit2ripple، Qwen3-4B أحسن من Qwen3-8B عند budget قدره 4k (BCY 0.3707 قصاد 0.3333)، وQwen3-8B أحسن عند 8k (0.5129 قصاد 0.5043) [qin2026, Table 25]. يعني "أحسن موديل" بيعتمد على الـ context budget بتاعك.

Technical example ​

Sketch كتبته بنفسي لـ Recall@k والـ reciprocal rank والـ RRF ونسخة مبسطة من الـ BCY packing. البيانات toy ومش من الـ paper، وعدد الـ tokens لكل ملف معطى بدل الـ tokenizer الحقيقي. اتشغل على Python 3.12.

def recall_at_k(ranking: list[str], gold: set[str], k: int) -> float:
    """Fraction of gold files that appear in the top k unique files."""
    top = list(dict.fromkeys(ranking))[:k]
    return len(gold & set(top)) / len(gold)


def reciprocal_rank(ranking: list[str], gold: set[str]) -> float:
    """1 / rank of the first gold file; 0 if no gold file is ranked."""
    for rank, path in enumerate(dict.fromkeys(ranking), start=1):
        if path in gold:
            return 1 / rank
    return 0.0

    """Reciprocal rank fusion: score(f) = sum over methods of 1 / (k + rank)."""
    scores: dict[str, float] = {}
    for ranking in rankings:
        for rank, path in enumerate(ranking, start=1):
            scores[path] = scores.get(path, 0.0) + 1 / (k + rank)
    return sorted(scores, key=lambda p: (-scores[p], p))


def bcy(ranking: list[str], gold: set[str], tokens: dict[str, int],
        budget: int, header: int = 3, tau: int = 1) -> float:
    """Greedy packing by rank; a gold file counts once tau of its content tokens fit."""
    left, yielded = budget, 0
    for path in dict.fromkeys(ranking):
        if left <= header:
            break
        packed = min(tokens[path], left - header)  # last file may be cut at the boundary
        left -= header + packed
        if path in gold and packed >= min(tau, tokens[path]):
            yielded += 1
    return yielded / len(gold)


gold = {"auth/session.py", "auth/tokens.py"}
embedding = ["auth/session.py", "docs/auth.md", "auth/login.py", "auth/tokens.py"]

Limitations ​

Stated by the authors:

  • الـ benchmark تشخيصي مش web-scale: 427 sample، و25 repository، ومش sample عشوائي من GitHub [qin2026, §11; qin2026, §5.1].
  • توزيع الـ samples مش متوازن: Gin لوحده 25.5% من الـ positives [qin2026, §11].
  • التقييم file-level أساسًا، والـ file exposure غير تحديد المكان المفيد جوه الملف؛ والـ span annotations مش موجودة لـ edit2ripple [qin2026, §11].
  • مافيش قياس لـ patch generation أو نجاح end-to-end، ولا إثبات إن miss في الـ retrieval بيسبب فشل في الإصلاح [qin2026, §11; qin2026, §8.7].
  • الـ gold labels تقريبية، وممكن يبقى فيه ملفات مفيدة بديلة مش متعلّمة [qin2026, §11].
  • الـ seed pilot صغير وsingle-run، فمافيش confidence intervals ولا significance [qin2026, §11].
  • تصنيف الـ relevance relations (semantic-direct، structural-indirect، workflow-conventional، causal-indirect) قواعد deterministic مش classes متحقق منها مستقل، ومتلخبط مع نوع المهمة: الـ causal-indirect هو trace2code بالظبط [qin2026, §11; qin2026, §8.3].
  • بعض النتايج provisional (pplx) أو lower bounds (BCY عند 16k و32k) [qin2026, §8.9].

My assessment:

  • My reading: الـ benchmark بيقيس الـ retriever لوحده بشكل نضيف، بس الـ agents الحقيقية بتعمل retrieval تفاعلي. أرقام الـ static leaderboard مش هتترجم مباشرة لأداء agent معين؛ والـ paper نفسها بتقول إن الـ static top-k scores مش أداء agent كامل [qin2026, §1].
  • الـ embeddings اتجربت من غير الـ prompts الموصى بيها، فالفروق بين الـ embedding models ممكن تتغير لو كل موديل اتظبط صح. ده بيأثر على المقارنة بين الموديلات أكتر من الفكرة الأساسية (complementarity).
  • علامات الـ relevance relations اتولدت بقواعد كتبها Codex حسب الـ paper [qin2026, §3]، وفيه audit بمساعدة موديل للـ labels [qin2026, §5.1]. الـ paper بتقول إن الـ audit ده مستقل عن الـ retrievers اللي اتقيمت، بس مش واضح قد إيه منه اتراجع يدوي.
  • الـ paper ورقة arXiv v1 ومافيش peer review لحد تاريخ الوصول.

Exercises ​

Exercise: Compute the metrics by hand

عندك sample فيه gold = {a.py, b.py, c.py}، والـ retriever رجّع بالترتيب: x.py، b.py، y.py، a.py، z.py. احسب Recall@2، وRecall@5، والـ reciprocal rank.

Solution

Recall@2 = 1/3 (بس b.py في أول اتنين). Recall@5 = 2/3 (b.py وa.py). أول gold في المركز 2، فالـ reciprocal rank = 0.5.

Exercise: Fuse two rankings

retriever A: p, q, r. retriever B: r, s, p. احسب الـ RRF score لكل ملف بـ k = 60 ورتبهم.

Solution

p: 1/61 + 1/63 ≈ 0.03227. r: 1/63 + 1/61 ≈ 0.03227 (نفس القيمة بالظبط). q: 1/62 ≈ 0.01613. s: 1/62 ≈ 0.01613. الترتيب: p وr متعادلين في الأول، بعدين q وs متعادلين. محتاج قاعدة tie-break (مثلًا بالـ path) عشان الترتيب يبقى deterministic.

Exercise: Why the abstention result flipped

اشرح في 3 جمل ليه الـ abstention حسّنت النتيجة في الـ mixed protocol ووقعتها في الـ natural-only.

Solution

الـ counterfactual samples فيها repository غلط خالص، فأعلى score بيبقى واطي بوضوح والـ threshold بيمسكها بسهولة. الـ natural cases شكلها محلي، فالـ score مش بيفرّقها عن الـ positives. ولما الـ threshold اتظبط على الـ natural بس، رفض positives كتير، فالـ selective success نزل [qin2026, §8.8].

Review questions ​

  1. إيه الفرق بين relevance في الـ code search التقليدي والـ agentic relevance في الـ paper دي؟
  2. ليه الـ retriever بيبحث في الـ base commit مش في نسخة بعد الإصلاح؟
  3. BCY@8k بيقيس إيه بالظبط؟ وليه τ=1 معناها exposure مش comprehension؟
  4. ليه نتيجة "الـ agents مالمستش gold في 27% لـ 35%" مش معناها إنهم فشلوا في إصلاح 27% من الـ bugs؟
  5. ليه الـ leaderboard اتغير لما وزنوا الـ repositories بالتساوي؟
  6. إيه اللي بيقوله الـ oracle seed (F1 = 0.6337) عن المشكلة بعد ما الـ retrieval يتحل؟
