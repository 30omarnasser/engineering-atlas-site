I Still Prefer MCP Over Skills (David Mohl) ​

ReviewedPublishedAI-assisted

David Mohl's opinion piece: skills are good as knowledge (how to use a tool you already have, your jargon, a file format), but connecting an agent to a service should go through an MCP server the service owns, not a CLI plus a SKILL.md; the best setup is a skill that documents an MCP server.

In one paragraph ​

المقالة رد على موجة "MCP is dead, skills are the new standard". موقف الكاتب: الـ skills ممتازة كـ معرفة (إزاي تستخدم أداة موجودة، المصطلحات الداخلية، التعامل مع نوع ملفات)، بس لما الـ skill تبدأ بـ "install this CLI first" عشان توصل لخدمة، تبقى ضفت طبقة مالهاش لازمة. التوصيل بالخدمات مكانه MCP server الخدمة نفسها بتملكه. وأحسن حاجة الاتنين مع بعض: skill بتشرح الـ MCP server.

Learning objectives ​

  • تفرّق بين skill "pure" (معرفة) وskill بتعتمد على CLI عشان تعمل حاجة.
  • تعدّ حجج الكاتب لـ MCP وتعرف حدود كل حجة.
  • تصمم "manual for a connector": skill فوق MCP server.

Problem ​

الكاتب "very heavy AI user" وبيقول إن الـ narrative بقى إن كل integration محتاجة CLI مخصوصة وmarkdown manual. وده بيفشل في بيئات كتير: ChatGPT وPerplexity وClaude على الـ web مابيشغّلوش CLIs، فأي skill معتمدة على CLI "dead on arrival" هناك [mohl2026, The Friction with Skills].

الـ MCP "API abstraction": الموديل يعرف إيه مش إزاي؛ ينادي devonthink.do_x() والـ server يتصرف [mohl2026, What I Love About MCP]. ومميزاته عنده:

ونفس القايمة تقريبًا موجودة في slides المحاضرة كـ "Additional MCP Perks": seamless auth، وسهولة الـ versioning، والـ portability، والـ sandboxing للـ remote MCP [cs146s-1013, Additional MCP Perks].

The friction with CLI-backed skills ​

[mohl2026, The Friction with Skills]:

  • Deployment: الـ CLIs لازم تتنشر وتتثبّت (binaries، npm، uv).
  • Secrets: الـ tokens بتتحط فين؟ .env plain text، أو بيئة ephemeral بتنسى الـ secrets بكرة.
  • Fragmentation: كل أداة بتثبّت الـ skills بطريقة؛ skill من منصة ممكن تفشل في التانية بـ YAML errors.
  • Context bloat: ممكن تحمّل SKILL.md كامل عشان تنادي حاجة زي car.turn_on().

Connectors vs manuals ​

قاعدته [mohl2026, Connectors vs. Manuals]:

  • MCP = الـ interface للاتصال بحاجة برّه، والخدمة نفسها تملكه. أمثلته: Google Calendar (عندها remote MCP بـ OAuth)، وNotion (mcp.notion.so/mcp)، وأدوات زي Hopper وXcode بـ MCP جوه الـ session الحية فبيعرفوا context مستحيل CLI يعرفه.
  • Skills تبقى "pure": تعليم أدوات موجودة (curl، git، gh، gcloud)، وworkflows والمصطلحات الداخلية، والتعامل مع formats (زي الـ PDF skill)، وأنماط الـ secrets ("use fnox in this repo"). بس حتى هنا: لإدارة issues، GitHub MCP أحسن من skill على gh.

ويقترح أسامي: الـ skills تتسمى LLM_MANUAL.md والـ MCPs تتسمى Connectors.

Skills + MCP: a manual for a connector ​

أقوى جزء [mohl2026, Skills + MCP]: لما يشتغل مع MCP server ويكتشف gotchas (format تاريخ YYYY-MM-DD مش YYYYMMDD، search بيقص النتايج إلا لو زوّدت parameter، أداة اسمها مضلل)، بيطلب من Claude يلم كل اللي اتعلموه في skill. الـ MCP بيعمل الاتصال، والـ skill "cheat sheet" عشان مايعيدش نفس الأخطاء كل session.

Results ​

مقال رأي: مفيش قياسات. الأمثلة تجارب الكاتب الشخصية.

Technical example ​

skill من النوع اللي بيوصفه (مثال من عندي؛ اسم الـ server والأدوات افتراضيين):

markdown
---
name: notes-mcp-guide
description: How to use the notes MCP server correctly. Use before calling any notes.* tool.
---

# Notes MCP: known gotchas
- Dates must be `YYYY-MM-DD`; `YYYYMMDD` returns an empty list, not an error.
- `notes.search` returns 20 results by default; pass `limit` for more.
- To link notes, call `notes.get` first: `notes.link` needs the note id, not the title.
- Never call `notes.delete` without showing the user the note title first.

الـ skill دي مابتعملش أي اتصال؛ كل الأفعال لسه أدوات MCP. هي بس بتوفّر الأخطاء اللي اتصلحت قبل كده.

Limitations ​

  • Stated by the author: موقفه مبني على استخدامه الشخصي، وبيقول بوضوح إن الاتنين ليهم مكان [mohl2026, Connectors vs. Manuals]. وفي الآخر بيعلن عن منتجين بتوعه (MCP Nest وWarplet)، فخد ده في الاعتبار.
  • My assessment: الحجج قوية لـ remote services، أضعف لأدوات محلية موجودة أصلًا: لو عندك CLI موثوقة ومثبّتة، MCP server جديد ممكن يزوّد تعقيد من غير مكسب. والـ remote MCP بيحط ثقة في الـ server owner، وده موضوع security لوحده (شوف Cloudflare's enterprise MCP architecture).

Exercises ​

Exercise: Connector or manual

لكل حالة: MCP، ولا skill، ولا الاتنين؟ (1) الـ agent يعمل events في Google Calendar. (2) الـ agent يكتب commit messages على convention الفريق. (3) الـ agent يدير issues في Jira بـ workflow الـ triage بتاع الفريق. (4) الـ agent يستخدم ffmpeg المثبّت عندك.

Solution

(1) MCP (الخدمة بتوفّر remote MCP بـ OAuth). (2) skill pure. (3) الاتنين: MCP للقدرة وskill للـ triage workflow. (4) skill بتعلّم أداة موجودة؛ مفيش داعي لـ "ffmpeg MCP" [mohl2026, Connectors vs. Manuals].

Exercise: Steelman the other side

اكتب حجتين لصالح CLI + skill بدل MCP server.

Solution

مثلًا: (1) الـ CLI موجودة أصلًا ومتجرّبة ومستخدمة من البشر كمان، فمفيش كود جديد تصونه. (2) الـ CLI بتشتغل offline ومن غير ما تدّي طرف تالت صلاحيات على حسابك. دي مش حجج المقالة؛ هي الطرف التاني للنقاش.

Review questions ​

  1. إيه الفرق بين "pure" skill وskill بتعتمد على CLI عند الكاتب؟
  2. ليه Xcode MCP بيعرف حاجات مستحيل xcode-cli يعرفها؟
  3. إيه فكرة "manual for a connector"، وإمتى تكتب skill زي دي؟
  4. أنهي ميزة من مميزات MCP عنده موجودة كمان في slides المحاضرة؟
