The Context Tax: When to Compact Your Coding Agent ​

ReviewedPublishedAI-assisted

دراسة حالة على 162 يوم من traces بتاعة Claude Code لمهندس واحد: تكلفة الـ context بتكبر كـ power law، والجزء المستخدم فعلًا ثابت تقريبًا، والـ compaction بيرفع التصحيحات بعده، والتوصية compaction بين 250k و450k حسب نوع الشغل.

In one paragraph ​

الـ coding agent بيبعت الـ context كله تاني مع كل خطوة، فالـ context مش "مساحة" بتملاها مرة، ده فاتورة متكررة بتكبر مع عمر الـ session. المقال ده بيقيس الفاتورة دي من 162 يوم من الـ traces بتاعة الكاتب نفسه، وبيقيس كمان الناحية التانية: الضرر اللي بيحصل بعد الـ compaction. الخلاصة إن الوصول لـ context أكبر بيكلف كـ power law (كل ما تضاعف الـ window، التكلفة التراكمية بتتضرب في 6 تقريبًا)، والجزء اللي الـ agent بيستخدمه فعلًا بيفضل حوالي 6,000 لـ 8,500 token مهما كبرت الـ window، بس الـ compaction نفسه بيخلّي التصحيحات تزيد لعشرات الخطوات بعده. والتوفيق بين الاتنين بيدّي range مش رقم: compaction بين 250k و450k token حسب نوع الشغل، ومعاه نصيحة أهم: احتفظ بجزء أخير من الـ history زي ما هو بدل ما تلخص كل حاجة [chaves2026research, §10].

Learning objectives ​

  • تشرح ليه تكلفة الـ context تراكمية، وليه الـ caching مابيحلش المشكلة.
  • تقرا الأربع قياسات اللي المقال بنى عليها التوصية، وتعرف أنهي واحد بيشد في أنهي اتجاه.
  • تفرّق بين اللي اتقاس فعلًا (28 خطوة rediscovery) واللي هو افتراض في الـ model (55 أو 145 خطوة).
  • تعرف حدود الدراسة: شخص واحد، وjudge آلي، وبيانات observational.

Problem ​

السؤال العملي: الـ harness يعمل compaction إمتى؟ فيه معسكرين، والمقال بيوصفهم كده [chaves2026research, §1]:

  • Cost control: معظم الـ context مالوش لازمة، فاعمل compaction بدري وكتير.
  • Fidelity: التلخيص بيضيّع حاجات مش باينة لحظتها، فاستخدم الـ window الكبيرة. ناس كتير في المعسكر ده بيشتغلوا عند 500,000 token وأكتر، بالتجربة مش بالقياس.

الكاتب نفسه كان بيعمل compaction عند 500k لـ 600k بالتجربة، لأن الـ agent كان بيبان أسوأ لما يعمله بدري [chaves2026, The part that complicates it]. والمقال بيحاول يقيس الحجتين بدل ما يختار واحدة.

The incident that started it ​

الدراسة بدأت من حادثة: في يوم واحد الـ agents بتوعه استهلكوا 2.25 billion token، و82% منهم من subagents مش من حاجة هو كتبها [chaves2026research, §3]. اتنين بس من 34 subagent أكلوا 1.14 billion. الاتنين كانوا forked subagents، يعني اتعملوا وهم شايلين نسخة كاملة من محادثة الـ parent: بدأوا عند 523,544 و304,404 token بدل حوالي 30,000 لـ subagent جديد، وواحد فيهم وصل لـ 997,634 token (أقل من حد الموديل بـ 0.3%)، واشتغل 10.7 ساعة و1,301 API call. وكل pnpm test عند متوسط الـ context بتاعه كان بيكلف حوالي 568,000 token قبل ما الـ tests نفسها تشتغل [chaves2026research, §3].

الدرس اللي الكاتب بيطلع بيه: ولا قرار من التلاتة غلط لوحده (الـ fork بيحافظ على context اتبنى في ساعات، والـ worker الطويل مش محتاج re-briefing، والشغل من الـ shell طبيعي)، بس مجموعهم هو اللي فجّر التكلفة [chaves2026research, §3].

Method ​

البيانات: كل الـ agents على جهاز الكاتب بيعدّوا على wrapper بيبعت OpenTelemetry spans لـ LangWatch، ومعاها الـ session transcripts المحلية بتاعة Claude Code. المدة 162 يوم (2026-01-18 لـ 2026-08-01)، و287,748 API call على 2,451 agent وthread، و873 compaction [chaves2026research, §2.1].

تفاصيل مهمة في الطريقة [chaves2026research, §2.2, §2.3]:

  • الـ context في كل call = cache_read_input_tokens + cache_creation_input_tokens + input_tokens.
  • الـ transcript بيكرر نفس الـ usage object في كل سطر content block، فالجمع الساذج بيضخّم الأرقام حوالي 1.7x. الأرقام كلها متصفّية بالـ message id.
  • الـ corpus اتقسم لـ 3,036 run (من بداية session أو compaction للي بعدها)، وكل run اتصنف لنوع من خمسة: code understanding، وresearch، وbuilding، وQA and dogfooding، وdriving a PR.

وبعدين أربع قياسات مستقلة:

  1. Cost cycle model: معادلة لتكلفة كل خطوة مفيدة عند threshold معين، وparameters بتاعتها كلها مقاسة من الـ 873 compaction [chaves2026research, §5.1].
  2. File re-reference distance: لكل ملف الـ agent لمسه، المسافة بالـ tokens لآخر مرة لمسه. مافيهاش model ولا judge [chaves2026research, §5.2].
  3. Utility audit: judge من نوع Opus شاف بالظبط اللي الـ agent كان شايفه في 201 خطوة، وعلّم أنهي عناصر من الـ context الخطوة استخدمتها فعلًا. النسب اتحسبت من قايمة العناصر، مش من نسبة الـ judge قالها [chaves2026research, §6.1].
  4. Behavioural proxies: معدل الـ tool errors، ومعدل رسايل الكاتب اللي فيها تصحيح (بالـ phrase match)، على 128,853 observation من 700 transcript، مقاسين بعدد الخطوات من آخر compaction [chaves2026research, §7.2].

Diagram ​

تلات قياسات بتقول "اعمل compaction بدري"، وواحد بيشد للناحية التانية. التوفيق بينهم بيحصل بإعادة تشغيل الـ cost model بعقوبة أكبر للـ compaction [chaves2026research, §8].

Results ​

1. Context cost is a power law ​

التكلفة التراكمية (median) للوصول لكل حجم context [chaves2026research, Fig. 2]:

Context reachedCumulative tokens

300k26M

من 100k لـ 800k الـ window زادت 8 مرات والتكلفة حوالي 240 مرة (338M على 1.4M؛ المقال بيقربها لـ "250 times"). الـ fit هو power law بـ exponent 2.55 وR2=0.994، وثابت بين 2.36 و2.66 لو اتعمل على أجزاء من المدى، فكل مضاعفة للـ context تكلف حوالي 6 أضعاف (22.55≈5.9) [chaves2026research, §4.1]. والمقال بيرفض كلمة "exponential" اللي الناس بتقولها: الداتا على power law بالشكل ده مش exponential.

ليه الـ exponent أكبر من 2؟ لو كل خطوة بتضيف كمية ثابتة كان هيبقى quadratic (الحساب ده في Agent Loop). بس الكمية اللي بتتضاف لكل خطوة بتقل مع امتلاء الـ window: من حوالي 3,200 token تحت 50k لـ 1,470 فوق 200k، فآخر جزء من الـ window بيتجمع على خطوات كتير صغيرة، وكل خطوة منهم بتدفع تمن الـ window كلها [chaves2026research, §4.2].

Caching does not cancel the tax

الـ cache reads أرخص حوالي 10 مرات للـ token، بس في يوم الحادثة كانوا 95% من كل الـ tokens. الـ cached token لسه token بتشتريه تاني في كل خطوة. الـ caching بيغيّر الـ constant، مش الـ exponent [chaves2026research, §4.3].

ونسبة الـ tokens المقروءة لكل token طالع شكلها U: أقل حاجة حوالي 217:1 عند 75k تقريبًا، وبتوصل 2,290:1 عند 900k. والناحية الشمال مهمة: تحت 50k الـ agent لسه ماجمعش حاجة كفاية يطلع بيها شغل حقيقي، فالـ windows الصغيرة جدًا مش كفء برضه [chaves2026research, §4.3].

وعدد الخطوات نفسه مش متوقع: على 2,107 subagent كل واحد معاه directive واحد، الـ median 20 call، والـ P90 72، والـ P99 359، وأسوأ واحد 1,545، وأعلى 10% مسؤولين عن نص الـ calls [chaves2026research, §4.4]. فأي context بتبدأ بيه الـ agent بيتضرب في رقم ماتقدرش تعرفه مقدمًا.

2. The cost-only optimum ​

الـ cycle تحت threshold ثابت: الـ session بتنزل بعد الـ compaction عند median 65,588 token، وبتكبر 1,470 token لكل خطوة، وبعد كل compaction الـ agent بيصرف حوالي 28 خطوة زيادة بيعيد فيهم قراية ملفات وبيرجّع حالة كان عارفها (ده الـ rediscovery penalty المقاس) [chaves2026research, §5.1].

f(T)=n⋅S+T2+(T+SUMM)+P⋅Sn−P,n=T−SD

T هو الـ threshold، وS حجم الـ context بعد الـ compaction، وD الزيادة لكل خطوة، وSUMM حجم الملخص (4,382 token)، وP عقوبة الـ rediscovery بالخطوات [chaves2026research, §5.1].

النتيجة: الحد الأدنى عند 220,000 token، وأي حاجة من 170k لـ 316k في حدود 10% منه، وتحت حوالي 110k الـ cycle بيبوظ خالص لأن الـ rediscovery بياكل خطوات أكتر من اللي الـ cycle بيديها. والمنحنى مش متماثل: إنك تعمل compaction بدري بـ 90k بيكلف 1.79x، ومتأخر بـ 96k بيكلف 1.10x بس. يعني لو مش متأكد، اتأخر [chaves2026research, §5.1].

والقياس المستقل (re-reference distance) على 10,037 مرة رجوع لملف: الـ median 7,430 token بس، بس الـ tail طويل. window بـ 100k بتمسك 72.4%، و200k بتمسك 77.6%، و500k بتمسك 82.6%، والـ 17% الباقيين بعيد بملايين الـ tokens ومافيش window هتمسكهم. والتغطية لكل وحدة تكلفة أعلاها عند 240,000 [chaves2026research, §5.2]. قياسين مالهمش parameters مشتركة وصلوا لـ 220k و240k.

ده أهم رسم في المقال، وعنوانه "You pay 16x more to carry the same 7,000 useful tokens" [chaves2026, But is any of that context useful?]:

الـ window كبرت 16.6 مرة (من 38,886 لـ 644,962)، والـ active context اتحرك من 7,949 لـ 8,452 بس، يعني كنسبة نزل من 47.5% لـ 2.5% [chaves2026research, §6.2, Fig. 6]. (قيم الـ judged minimum متقرية من الرسم؛ النص بيقول "near 1,500 tokens in every band but the largest".)

والنزول ده موجود في الخمس أنواع شغل. الـ code understanding بيحتفظ بقيمة الـ context القديم أطول (لسه 18% عند 150k لـ 350k) لأن القراية تراكمية، والـ QA والـ PR بيقلّوا أسرع لأن كل check أو رد على review بيقفل على نفسه [chaves2026research, §6.3].

4. When raw context beats a summary ​

الـ judges اتسألوا لكل خطوة: هل النص الأصلي القديم (verbatim) كان بيعمل حاجة الملخص مش هيعملها؟ [chaves2026research, §6.4, Fig. 8]

Kind of workVerbatim old context needed
Building20%
Code understanding19%
QA / dogfooding18%
Research10%
Driving a PR2%

الإجمالي 28 خطوة من 195 (14%). والحالات دي متجمعة حوالين نسخ نص بالحرف: تعديل لازم الـ search text بتاعه يطابق ملف اتقرا قبل كده حرف بحرف، أو command بيعيد استخدام connection string من 390 عنصر فات. لما الاعتماد كان على قرار أو قيد أو معلومة مش نص حرفي، الملخص كان كفاية [chaves2026research, §6.4].

مثال من عندي (مش من المقال): أداة edit_file في Minimal coding agent محتاجة old_str يطابق الملف بالظبط، فملخص زي "فيه function بتعالج الداتا" مش هينفع. لكن "المستخدم اختار PostgreSQL" يعيش كويس في ملخص.

والسؤال الافتراضي اللي اتسأل لكل judge: لو كل حاجة غير آخر 30k اتبدلت بملخص 5,000 token؟ 85% من الخطوات ماتأثرتش، و15% اتأثرت شوية، و4 من 195 اتأثروا بشكل مؤثر، وصفر بقت مستحيلة [chaves2026research, §6.4]. لحد هنا كل حاجة بتقول: اعمل compaction بدري، حوالي 150k لـ 220k.

5. The behavioural cost of compaction ​

هنا المقال بيقلب. الـ audit عنده survivorship bias: الـ judges قيّموا خطوات اتعملت فعلًا. خطوة راحت غلط بهدوء عشان حاجة اتلخصت مش هتبان كخطوة وحشة؛ هتبان كخطوة عادية ونتيجتها تظهر بعدين في الـ review أو الـ production [chaves2026research, §7.1]. فالكاتب قاس السلوك بدل الجودة:

  • في أول 5 خطوات بعد الـ compaction، 41.9% من رسايله فيها تصحيح، مقابل baseline 17.7% (2.37x). الارتفاع بيفضل 30 خطوة على الأقل، ومارجعش خالص حتى بعد 120 خطوة [chaves2026research, §7.2].
  • في نفس الفترة معدل الـ tool errors ثابت بين 2.6% و3.2%. يعني الـ calls شغالة، بس القرارات اللي وراها بقت أسوأ [chaves2026research, §7.2].

والسبب واضح لما تقيس الـ compaction نفسه: الـ median بياخد window بـ 574,875 token ويطلع ملخص 4,382 token، يعني أقل من 1% بيعيش (0.8%)، وكل compaction بياخد median 142 ثانية [chaves2026research, §7.3]. والمقال بيسمي الفترة دي "post-compaction fog" [chaves2026, The part that complicates it]: عند threshold 220k الـ cycle حوالي 105 خطوة، فحوالي 29% من شغلك جوه الـ fog؛ عند 577k الـ cycle 348 خطوة والنسبة 9% [chaves2026research, §7.3].

6. Everything depends on one parameter ​

الـ optimum بيتحدد تقريبًا بالكامل بسؤال واحد: الـ compaction الواحد بيضيّع كام خطوة شغل؟ [chaves2026research, Table 1]

If one compaction costsCost-optimal threshold
28 steps (rediscovery only, measured)220,000
31 steps (plus visibly caught rework)232,000
65 steps350,000
113 steps500,000
138 steps577,000
145 steps600,000

الكاتب صريح هنا: اللي قدر يقيسه حوالي 31 خطوة. اللي بيشتغل عند 600k (زيه) بيفترض ضمنيًا إن الـ compaction بيكلف حوالي 145 خطوة، خمس أضعاف المقاس. افتراض مش غير معقول مع تصحيحات لسه عالية بعد 100 خطوة، بس مش مثبت [chaves2026research, §7.4].

وعلى حساب الـ tokens بس، الـ window الواسعة ماتجيبش تمنها: من threshold 232k لـ 600k بتدفع 139M token زيادة لكل 1,000 خطوة مفيدة وبتشيل 6.1 disruption، يعني حوالي 23M token لكل disruption. عشان ده يبقى مكسب، bug واحد بيهرب لازم يكلف بين 46M و229M token، وجلسة debugging كاملة بتكلف كام مليون. فالدفاع عن الـ window الواسعة لازم يبقى على تكلفة الـ defect الحقيقية (ساعات مهندسين، وثقة العملاء)، مش على الـ tokens [chaves2026research, §7.5].

7. The recommendation ​

لما الـ cost model اتعاد بعقوبة 55 خطوة بدل 28 (لأن التصحيحات بتقول إن الضرر أبعد من إعادة القراية)، الـ optimum اتنقل من 220k لـ 314k، والمنطقة في حدود 10% بقت من 239k لـ 453k. ومنها جه الجدول [chaves2026research, §8, Table 2]:

Kind of workSuggested thresholdBasis
Driving a PR200k to 250k2% verbatim dependence, zero materially degraded
Research250k to 300kself-contained, zero materially degraded
QA and dogfooding250k to 350kfast decay, but 6% materially degraded
Building300k to 450khighest verbatim dependence, exact-string edits
Code understanding300k to 450kslowest decay, value remains cumulative

تحت 200k تقريبًا الـ fog بيبدأ ياكل وقت الشغل، وفوق 600k بتدفع premium كبير على فايدة ماحدش قاسها [chaves2026research, §8]. وفيه حد أدنى: عند عقوبة 55 خطوة، threshold 146k بيدّيك بالظبط 55 خطوة في الـ cycle، فكل الـ cycle بيتصرف في التعافي من الـ compaction اللي بدأه [chaves2026research, §8].

8. The bigger lever: what survives the cut ​

المقال بيقول إن الـ threshold مش أهم knob [chaves2026research, §8.1]:

  • Preserved tail: الضرر متركز لحظة القطع، لأن 0.8% بس من الـ window بيعيش. لو احتفظت بآخر 30k لـ 60k token زي ما هم بدل ملخص 4,382 token، الـ disruption بيبقى أقل عمقًا مش بس أقل تكرارًا. وفي نفس الـ model، threshold 350k مع tail 60k بيكلف أقل بـ 25% لكل وحدة شغل من 600k مع ملخص بس.
  • Where an agent starts: أكبر عامل في تكلفة الـ agent هو بيبدأ منين. subagent جديد بيبدأ حوالي 30k؛ subagent متعمله fork من parent مليان بيبدأ مطرح ما الـ parent كان.

والكاتب بيقول إن ده "not exposed as a setting in any harness we are aware of" [chaves2026research, §10].

Technical example ​

الـ cycle model ده كتبته بنفسي من المعادلة والـ parameters المنشورة في المقال، عشان أتأكد إني فاهمها. اتشغّل يوم 2026-11-07 بـ Python 3.12، والـ output تحت هو اللي طلع فعلًا:

python
S, D, SUMM = 65_588, 1_470, 4_382   # measured medians (research §5.1)

def cost_per_productive_step(T, P):
    n = (T - S) / D                       # steps from S to the threshold T
    if n <= P:
        return float("inf")               # rediscovery eats the whole cycle
    return (n * (S + T) / 2 + (T + SUMM) + P * S) / (n - P)

for P in (28, 55):
    grid = range(100_000, 1_000_001, 1_000)
    best = min(grid, key=lambda T: cost_per_productive_step(T, P))
    fbest = cost_per_productive_step(best, P)
    near = [T for T in grid if cost_per_productive_step(T, P) <= 1.10 * fbest]
    print(f"P={P}: optimum {best:,}  within 10%: {near[0]:,} to {near[-1]:,}")
text
P=28: optimum 220,000  within 10%: 168,000 to 316,000
P=55: optimum 314,000  within 10%: 239,000 to 453,000

الأرقام بتطابق المنشور (220k و170k–316k مقربة، و314k و239k–453k) [chaves2026research, §5.1, §8]. جرّب تغيّر P أو S لأرقام الـ harness بتاعك وشوف الـ optimum بيتحرك قد إيه.

Course connection ​

المقال ده كان ضمن الـ reading بتاع Week 2 في CS146S Fall 2026 [cs146s-site]. والمحاضر في محاضرة 9/29 اتكلم عن "a solid blog post" عن الـ compaction مبني على traces أصحابه، وقال إن التوصية كانت بين 250,000 و450,000 token، وإن الخلاصة "compact often" [cs146s-0929]. الـ range ده هو نفس range المقال. بس فيه فرقين في كلام المحاضر: قال إن الـ range "depending on the model" والمقال بيقسمه حسب نوع الشغل؛ وقال إن الـ context المفيد "may be closer to half a million" token، والرقم ده مش في المقال (المقال قاس الـ active context بحوالي 6,000 لـ 8,500 token) [cs146s-0929; chaves2026research, §6.2]. الشرح في Advanced Prompting and Context Engineering، والمفهوم نفسه في Context Compaction.

Limitations ​

Stated by the author [chaves2026research, §9]:

  • Single subject: استخدام مهندس واحد، أغلبه agentic coding على الـ LangWatch codebase، على harness وmodel family معينين. الـ constants بتاعته هو؛ الكاتب متوقع إن الأشكال (الـ power law، وخط الـ useful context الثابت، والـ spike بعد الـ compaction) تتنقل أحسن من الأرقام.
  • Confounding: نوع الشغل وحجم الـ window مرتبطين؛ الـ building بس بيغطي كل الـ bands.
  • Survivorship bias في الـ audit: مابيشوفش الخطوات اللي باظت بعدين.
  • Reverse causation: أحيانًا بيعمل compaction لأن الدنيا بايظة أصلًا، وده لوحده يرفع التصحيحات بعده. الحل اللي بيقترحه: harness بيعمل compaction عند trigger ثابت.
  • Noisy proxy: التصحيحات متلقطة بـ phrase match.

My assessment:

  • المصدر vendor blog: LangWatch بتبيع أداة tracing، والمقال بيقول إنك تقدر تعيد التحليل بـ npx langwatch claude (في أول المقال) [chaves2026]. ده مابيبطلش الأرقام، بس الدراسة ماعدّتش على peer review.
  • الـ "used context" تقدير من LLM judge، مش قياس لاعتماد الموديل الداخلي على الـ tokens.
  • التوصية بالـ tail (25% أقل) نتيجة model، مش تجربة اتعملت. محتاجة replication.
  • الأرقام مربوطة بنسخة Claude Code والموديلات وقتها؛ أي تغيير في الـ compaction prompt أو الـ defaults ممكن يغيّر الـ constants.

Exercises ​

Exercise: Doubling cost

لو الـ fit T(C)∝C2.55 صح، الوصول لـ 400k بيكلف قد إيه مقارنة بـ 100k؟ وقارن بالرقم المقاس في الجدول.

Solution

42.55≈34. المقاس: 49M على 1.4M يعني حوالي 35. قريبين جدًا، وده معنى R2=0.994.

Exercise: Measured versus assumed

الكاتب بيشتغل عند 600k. إيه الافتراض اللي ده بيعمله ضمنيًا عن تكلفة الـ compaction، وليه ده مش نفس الحاجة اللي اتقاست؟

Solution

بيفترض إن الـ compaction الواحد بيضيّع حوالي 145 خطوة (Table 1). المقاس فعلًا حوالي 28 خطوة rediscovery، أو 31 مع الـ rework اللي اتمسك. الـ 145 ممكن تبقى معقولة لأن التصحيحات عالية لأكتر من 100 خطوة، بس مفيش قياس بيثبتها.

Exercise: Forked or fresh

عندك coordinator وصل 400k، وعايز subagent يراجع unit tests في ملف واحد. تعمله fork ولا fresh؟ وإيه اللي تحطه في الـ briefing؟

Solution

Fresh، لأن الـ fork هيبدأ من 400k وكل خطوة هتدفع التمن ده، وعدد الخطوات مش متوقع. الـ briefing: الملف، والهدف، والقيود (مثلًا ماتغيرش الـ API)، ومعيار التوقف، وحد أقصى للخطوات أو الـ tokens.

Review questions ​

  1. ليه الـ context "recurring charge" مش resource ثابت؟
  2. إيه الفرق بين الـ cumulative cost اللي بيقيسها الـ power law وتكلفة call واحدة عند نفس الحجم؟
  3. ليه الـ audit لوحده كان هيوصلك لتوصية غلط؟
  4. ليه ثبات الـ tool error rate مع ارتفاع التصحيحات معلومة مهمة؟
  5. إيه النوع من المعلومات اللي الملخص بيشيله كويس، وإيه اللي محتاج verbatim؟
