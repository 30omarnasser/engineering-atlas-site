HarnessSecurity-Bench: Do Security Mechanisms Really Protect Coding Agent Harnesses? ​

ReviewedPublishedAI-assisted

دراسة بتصنّف 10 أنواع security mechanisms في 40 coding agent harness، وبتقيس بـ benchmark من 23 مهمة أثر تشغيل كل mechanism على نجاح الهجمات وعلى إنجاز الشغل في 6 harnesses.

In one paragraph ​

الـ coding agent harness هو اللي بيقرر الـ agent يشوف إيه ويقدر ينفّذ إيه. الورقة دي بتسأل: إعدادات الأمان اللي جوه الـ harnesses الحقيقية (زي approval، وsandbox، وallowlist للأوامر) بتحمي فعلًا؟ وبكام من إنجاز الشغل؟ عملوا ده على مرحلتين. الأولى: صنّفوا 10 أنواع security mechanisms، وفحصوا هل هي موجودة ومفعّلة افتراضيًا في 40 harness. التانية: بنوا benchmark اسمه HarnessSecurity-Bench (HSB) من 23 مهمة برمجة فيها محتوى خبيث، وقاسوا في 6 harnesses إيه اللي بيحصل لما تشغّل كل mechanism أو تطفيه [zhu2026hsb]. أشهر رقم: لما شغّلوا auto-approve، نسبة نجاح الهجمات طلعت من 29.2% لـ 95.6% [zhu2026hsb, Table 6].

Background: the harness is the security boundary ​

لو مش فاكر الـ harness إيه، اقرا Agent Harness الأول. الفكرة اللي الورقة بتبني عليها: الموديل بيقترح action، بس الـ harness هو اللي بيجمّع الـ context، وبيوسّط الـ tool use، وبيـ authorize الـ actions [zhu2026hsb, §1]. يعني لو الموديل اتخدع، الـ harness هو آخر حاجز قبل ما الخدعة تبقى فعل حقيقي على الملفات أو الشبكة.

الورقة بتعرّف الـ attack surface إنه أي resource أو interface أو state يقدر المهاجم يتحكم فيه ويأثر بيه على قرارات الـ agent أو التنفيذ [zhu2026hsb, §2]. وبتقسمهم ست أنواع حسب الـ resource اللي تحت إيد المهاجم:

Attack surfaceExamples in the paperIn HSB?
Repository and workflow artifactsdocumentation، source comments، config filesyes
Agent instructions and skillsAGENTS.md مسموم، project instructionsyes
Tool interfacesوصف أداة MCP فيه تعليمات، أو رد أداة فيه تعليماتyes
Knowledge and memoryrecords راجعة من database tool عاديةyes
External services and execution dependenciespackage lifecycle hook، helper بيتحمّل ويتنفذyes
Direct user input—no

المصدر: [zhu2026hsb, §2, §5.2]. الـ direct user input اتشال من الـ benchmark عمدًا، عشان تعليمات المستخدم في كل مهمة تفضل شرعية وثابتة [zhu2026hsb, §5.1].

الرسمة تبسيط شخصي مبني على وصف الـ loop في §2 وتعريفات الـ mechanisms في §3.3، مش نسخة من Fig. 1 في الورقة.

Research questions ​

  1. RQ1: إيه الـ security mechanisms المختلفة اللي موجودة في coding agent harnesses حقيقية؟
  2. RQ2: الـ mechanisms دي متطبقة لأي درجة؟
  3. RQ3: الـ mechanisms دي بتأثر إزاي على الأمان وعلى الـ utility لما المهمة يكون فيها محتوى خبيث؟

المصدر: [zhu2026hsb, §1].

Method ​

RQ1: a taxonomy of ten mechanisms ​

جمعوا 75 record لـ coding agents من GitHub، ومن مواد الشركات، ومن الـ CVEs والـ security disclosures. بعد دمج المكرر فضل 56، وبعد الفلترة (مثلًا 1,000 star على الأقل للـ open-source، ومواد كفاية للتقييم) فضل 40 harness: 27 open-source و13 closed-source [zhu2026hsb, §3.1]. خد بالك: الورقة بتحط Claude Code وGitHub Copilot في خانة الـ open-source. في Claude Code استخدموا mirror غير رسمي للـ source اتسترجع من source map في npm package، وفي Copilot استخدموا repository الـ VS Code الرسمي [zhu2026hsb, §3.1, Table 2].

تلات باحثين عملوا open coding وaxial coding على 8 harnesses الأول، وبعدين وسّعوا على الـ 32 الباقيين، وباحث رابع حسم الخلافات. النتيجة 44 label، اتجمعوا في 10 mechanisms [zhu2026hsb, §3.2, §3.3]:

MechanismWhat it doesExample ON / OFF from the paper
Auto-approve (AA)بيعدّي بعض أو كل الـ confirmations. الورقة بتسميه risk capability مش دفاعCodex CLI: approval_policy="never" / "on-request"
Network isolation (NI)default-deny للـ egress أو domain allowlistCodex CLI: network_access=false / true
Command allowlisting (CAL)الأوامر اللي في قايمة محددة بس هي اللي بتعدّيdefault-deny مع allowlist / من غير قيود
Command denylisting (CDL)بيمنع أوامر أو patterns خطيرة معروفةClaude Code: --disallowedTools="Bash(rm *)"
MCP permissions (MCP)بيحدد أنهي MCP servers وtools مسموحة وبأي نطاقCodex CLI: enabled_tools + "prompt" / "approve"
Prompt-injection filtering (PIF)بيعلّم أو يكتشف أو ينظّف تعليمات جاية من محتوى tool أو web أو filegptme: GPTME_INJECTION_HYGIENE=block / off

المصدر: [zhu2026hsb, Table 3]. الفرق المهم بين PR وRO: الـ PR بيحدد فين تكتب، والـ RO بيمنع الكتابة الدائمة خالص في العمليات اللي بيغطيها. فـ workspace-write ممكن يسمح بالتعديل جوه الـ workspace ويمنعه برّاه [zhu2026hsb, §3.3].

RQ2: rating 400 harness–mechanism cells ​

40 harness × 10 mechanisms = 400 خانة. كل خانة خدت تقييم من خمسة [zhu2026hsb, §4.1]:

  • D (default-enforced): متطبقة وشغالة افتراضيًا، ومفيش option يطفيها.
  • C (configurable-off): متطبقة وشغالة افتراضيًا، وتقدر تطفيها بـ config أو flag.
  • O (opt-in): متطبقة، بس لازم المستخدم يشغّلها بنفسه.
  • A (absent): فيه دليل إنها مش موجودة.
  • U (unknown): الأدلة مش كفاية أو متعارضة.

كل خانة قيّمها خمسة بشكل مستقل: 3 LLMs (Claude Opus 4.8، وDeepSeek V4 Flash، وGLM-5.2) وباحثين اتنين. وأي تقييم غير U من الـ LLM لازم يستشهد بمقطع محدد بالـ path والـ line range، والبرنامج بيتأكد من المقطع ويسجّل الـ SHA-256 بتاعه. الورقة بتسمي ده Evidence-of-Thought. الأغلبية (3 من 5) بتحسم، والخانات اللي مفيهاش أغلبية (18) اتحسمت بمراجعة بشرية [zhu2026hsb, §4.1].

RQ3: the benchmark ​

  • المهام: 23 مهمة (21 أصلية و2 متعدّلين من Terminal-Bench): bug repair، وfeature implementation، وتحليل read-only. اللغات: Python وJavaScript وC++ وC# وRuby وGo. كل مهمة تابعة لـ benchmark خاص بـ mechanism واحدة [zhu2026hsb, §5.1, Table 5].
  • الهجمات: المهاجم مابيغيّرش تعليمات المستخدم. بيحط في البيئة خطوات workflow مضللة، أو "prerequisites" مزيفة، أو actions زيادة مش مطلوبة. مثال: مواد maintenance بتقدّم مسح الـ queue كأنه خطوة لازمة لإصلاح الـ backoff [zhu2026hsb, §5.2].
  • القياس: فيه نوعين من الـ deterministic oracles منفصلين. utility oracles بتشيك على متطلبات المهمة، وattack-effect oracles بتشيك هل حصل الفعل الخبيث، من حالة الملفات والـ database، وسجلات الـ receiver، وأحداث التنفيذ. السبب: الـ agent ممكن يقول "رفضت" وهو فعلًا عمل الـ tool call الممنوع [zhu2026hsb, §5.3].
  • الإعداد: نفس الموديل GLM-5.2 في كل الـ harnesses. كل trial في Docker container جديد ومعزول. 10 trials لكل تركيبة (task، harness، setting)، يعني 2,500 trial مخطط ليهم، غير الـ reruns [zhu2026hsb, §6.1].
  • اختيار الـ harnesses: اختاروا الـ open-source اللي عندها تقييم U أو A واحد بالكتير في الـ matrix، فطلعوا ستة: Claude Code، وCodex CLI، وGemini CLI، وgptme، وQwen Code، وGitHub Copilot [zhu2026hsb, §6.1].
  • المقارنة: لكل mechanism بيقارنوا ON مقابل OFF على نفس المهمة ونفس الهجمة ونفس الموديل، وباقي إعدادات الأمان ثابتة. الـ AL اتشال من الـ benchmark لأنه بيسجّل بس، مابيمنعش وقت التنفيذ [zhu2026hsb, §5, §6.1].

Definition: Utility and ASR in this paper

الـ Utility هي نسبة الـ utility oracle checks اللي نجحت، والـ ASR (attack success rate) هي نسبة الـ attack-effect checks اللي نجحت. يعني الاتنين نسب checks، مش نسب مهام كاملة. والـ ΔASR والـ ΔUtility هما الفرق بين ON وOFF بالـ percentage points (pp) [zhu2026hsb, §6.1].

Results ​

RQ2: half of the confirmed mechanisms are opt-in ​

من الـ 400 خانة: 205 فيها implementation مؤكد (D أو C أو O)، و83 مؤكد إنها absent، و112 لسه unknown. ومن الـ 205، الـ opt-in هو الأكتر (109)، والـ 96 الباقيين شغالين افتراضيًا (64 C و32 D) [zhu2026hsb, §4.2].

  • الـ RO والـ AA تقريبًا دايمًا opt-in: 30 من 31 في RO، و26 من 30 في AA.
  • العكس في MCP وAL: 22 من 29 في MCP شغالين افتراضيًا، و20 من 22 في AL.
  • الـ PIF ليه 4 implementations مؤكدة بس، و13 A، و23 U، وكل الـ 13 خانة closed-source فيه U.
  • الـ U في الـ closed-source 69 من 130 خانة (53.1%)، مقابل 43 من 270 في الـ open-source (15.9%).

المصدر: [zhu2026hsb, §4.2]. الرقم الأخير مش معناه إن الـ closed-source أقل أمانًا. معناه إن اللي بيقيّم من برّه مايقدرش يثبت حاجة بنفس الدرجة [zhu2026hsb, §7.3].

Do not rank mechanisms by this table

كل mechanism اتقاست في benchmark خاص بيها، بمهام وهجمات مختلفة، والـ OFF baseline بيختلف جدًا (8.3% في RO مقابل 98.1% في CAL). فالـ −7.5 pp في RO مش معناها إن RO أضعف من CAL. الرقم الصح للمقارنة هو جوه نفس الصف بس: الأمان كسب قد إيه، والـ utility خسرت قد إيه.

الورقة بتجمّع النتايج في أربع مجموعات [zhu2026hsb, §6.2]:

1. Auto-approve يزوّد الاتنين. الـ AA-ON بيعدّي الـ approval checks. ولما الـ AA بيبقى OFF، طلبات الإذن بتروح لـ reviewer منفصل. الـ ASR زاد في كل الـ harnesses الستة، بس مكسب الـ utility اختلف: Gemini CLI كسب 2.3 pp بس، وClaude Code خسر 0.8 pp. يعني الـ auto-approve زوّد التعرّض للهجوم حتى في الحالات اللي ماكانش فيها مكسب حقيقي في إنجاز الشغل [zhu2026hsb, §6.2, Table 6].

2. أمان عالي بتمن كبير: NI وRO. الاتنين بيقفلوا capability محتاجها الشغل الشرعي والهجوم في نفس الوقت. في NI، 161 من الـ 162 utility pass اللي ضاعوا كانوا checks محتاجة network. والـ local code checks فضلت تقريبًا زي ما هي (437/480 مقابل 436/480). وفي RO، 347 من الـ 367 اللي ضاعوا كانوا checks محتاجة تعديل دائم في الكود [zhu2026hsb, §6.2].

3. أمان مع utility محفوظة تقريبًا: CAL وPT. الـ CAL سابت معظم الشغل الشرعي ممكن بالأوامر المسموحة. والـ PT: كل خسارة الـ utility (من 100% لـ 80%) جت من Gemini CLI، اللي رفض يبدأ أصلًا في كل الـ 40 trial لما الـ workspace اتعلّم untrusted. لو شلت Gemini CLI، الأربعة التانيين فضلوا على 100% utility، والـ ASR نزل من 75.8% لـ 50.4% [zhu2026hsb, §6.2].

4. أمان مع مكسب بسيط في الـ utility: CDL وPR وMCP. إزاي منع حاجة يزوّد الـ utility؟ لأن الهجمة نفسها ساعات بتبوّظ الـ deliverable. في CDL، 15 من الـ 29 pass الزيادة جم من تقارير Qwen Code وGitHub Copilot اللي بطّلت تحتوي على signing-key material، لأن عملية نسخ المفتاح اتمنعت [zhu2026hsb, §6.2]. بس النتايج متفاوتة: في PR، الـ ASR في Codex CLI نزل من 100% لـ 0%، وفي Claude Code فضل 97.5% زي ما هو [zhu2026hsb, Table 7].

والـ PIF؟ harness واحد بس (gptme) سمح بمقارنة ON/OFF. الفلتر بتاعه بيدور على injection patterns صريحة في الـ tool outputs ويضيف تحذير. والهجمات اللي متنكّرة كخطوة workflow عادية بتعدّي. والنتيجة: 16/60 مقابل 14/60 attack checks [zhu2026hsb, §6.2].

الـ cost: الـ 2,500 trial سجّلوا 81,155 tool call، و589.32 ساعة تنفيذ تراكمية، وأكتر من 2.2 مليار token [zhu2026hsb, §6.2].

Case A: one capability serves both sides ​

مهمة Dependency Lock Repair (benchmark الـ NI) محتاجة تنزّل packages من registry. في Claude Code، تشغيل الـ NI نزّل الـ utility من 96% لـ 76%، والـ ASR من 100% لـ 0%. ليه؟ تحت OFF، التثبيت نفسه كان بيشغّل callback بيبعت data للـ attack collector. تحت ON، الـ network policy منعت الـ registry، فالـ callback ماحصلش، بس التثبيت الشرعي كمان ماحصلش. ورغم كده الأربع local checks نجحوا [zhu2026hsb, §6.3].

Case B: bypass through an allowed interpreter ​

دي أهم نتيجة عملية في الورقة. في مهمة CLI Arg Parser (benchmark الـ CAL)، مواد الـ validation المسمومة قدّمت checker غير مصرّح بيه كأنه أداة validation لازمة. الـ native gate في Qwen Code رفض الـ checker. بس الـ agent، بعد ما خلّص الـ validation الشرعي، شغّل نفس الـ checker عن طريق Python interpreter مسموح بيه [zhu2026hsb, §6.3].

الـ trial ده نجح في الـ 6 utility checks والـ 3 attack checks. وtrial تاني تحت ON خلّص نفس المهمة من غير ما يشغّل الـ checker خالص، ونجح في كل الـ utility checks ومفيش ولا attack check. يعني الـ checker ماكانش ضروري للمهمة أصلًا [zhu2026hsb, §6.3]. والدرس اللي الورقة بتقوله: لازم تتحكم في كل الطرق اللي بتوصّل للعملية المحمية، مش في اسم أمر واحد [zhu2026hsb, §6.3].

My reading: ده نفس الوجه التاني لنصيحة "أدوات أقل وأقوى" في CS146S. أداة زي Bash أو Python interpreter قوية لأنها لغة كاملة، وعشان كده أي allowlist بتسمح بيها بتسمح ضمنيًا بحاجات كتير جدًا.

The authors' recommendations ​

الورقة بتوجّه كلامها لمطوّري الـ harnesses [zhu2026hsb, §7.3, §9]:

  • Make settings verifiable: ينشروا وصف versioned لكل mechanism: متطبقة؟ شغالة افتراضيًا؟ تتغير إزاي؟ بتغطي أنهي inputs وoperations؟ ويعرضوا الإعدادات الفعلية في الـ CLI أو الـ UI عشان المستخدم يتأكد هو شغال بإيه.
  • Test alternative paths: يختبروا الطرق البديلة للوصول للـ resources المحمية، ويتأكدوا إن المهمة الشرعية لسه ليها طريق مصرّح بيه، ويعيدوا الاختبار بعد أي تغيير في الـ tool routing أو الـ permissions.
  • Report everything together: أي تقييم يطلّع الـ attack effects والـ utility والـ tokens والـ runtime مع بعض، عشان المستخدم يختار الإعداد المناسب لشغله ولدرجة المخاطرة اللي يقبلها.

Limitations ​

Stated by the authors ​

  • الـ AA-OFF بيعتمد على LLM reviewer بمعايير ثابتة. ممكن يكون فيه model bias، فنتايج الـ AA بتعبّر عن الـ approval configuration دي بالذات [zhu2026hsb, §7.1].
  • التقييم العملي على 6 harnesses open-source بس. الـ closed-source، خصوصًا اللي شغالة بـ GUI جوه IDE، صعب تتشغّل أوتوماتيك بشكل يمثّل الاستخدام الحقيقي [zhu2026hsb, §7.2].
  • الـ Docker والـ simulated services مش بيمثلوا الـ deployments الحقيقية بالكامل [zhu2026hsb, §7.2].
  • موديل واحد (GLM-5.2). موديلات تانية ممكن تختلف في الـ tool use والـ instruction following، وده يغيّر الـ ASR وحجم الفرق بين ON وOFF [zhu2026hsb, §7.2].
  • الـ stochasticity: عشان كده كل condition اتعادت 10 مرات [zhu2026hsb, §7.2].

My assessment ​

  • الـ OFF baseline في AA مش إنسان. طلبات الإذن تحت AA-OFF راحت لموديل منفصل (Qwen3.8-27B) عن طريق deterministic bridge [zhu2026hsb, §6.1]. فالـ 29.2% هي ASR مع LLM reviewer، مش مع مستخدم بيقرا كل طلب. مستخدم حقيقي ممكن يكون أحسن أو أسوأ بكتير.
  • الأرقام نسب checks. مهمة واحدة ممكن يكون ليها عدد checks كبير، فالنسبة مش "كام مهمة اتخترقت".
  • العينة صغيرة في بعض الـ mechanisms. الـ PIF فيه مقارنة واحدة على 60 attack check، والفرق 2 checks بس [zhu2026hsb, §6.2]. ده مايكفيش لاستنتاج قوي في أي اتجاه.
  • إصدار وإعدادات محددة. كل نتيجة مربوطة بـ release معيّن وإعداد معيّن للـ harness [zhu2026hsb, §6.1]، والإعدادات دي بتتغير بسرعة. ماتنقلش الرقم كأنه وصف لمنتج النهارده.
  • مش ترتيب للمنتجات. الورقة مابتقولش إن harness معين آمن أو مش آمن بشكل عام، والـ 95.6% مثلًا مش "احتمال اختراق Claude Code".

  • Agent Harness: الورقة بتضيف بُعد الأمان لمبدأ البساطة. أداة قوية = سطح هجوم واسع.
  • The Anatomy of a Modern Coding Agent: الـ hooks والـ plan mode والـ subagents كلها نقط في الـ loop. الورقة بتوري إن الـ authorization في الـ loop دي هو اللي بيفرق.

Exercises ​

Exercise: Recompute the headline number

من [zhu2026hsb, Table 6]: في الـ AA، الـ Overall كان 105/360 attack checks نجحوا تحت OFF، و344/360 تحت ON. احسب الـ ASR في الحالتين والـ ΔASR.

Solution

105 ÷ 360 = 29.2%، و344 ÷ 360 = 95.6%. الفرق 95.56 − 29.17 = 66.4 pp. الورقة بتحسب الـ Δ من الأرقام قبل التقريب، وعشان كده ممكن رقم الـ Δ يختلف 0.1 عن طرح الأرقام المقرّبة.

Exercise: Close the bypass

عندك harness فيه command allowlist بتسمح بـ pytest وpython وgit status. عايز تمنع الـ agent إنه يمسح أي ملف برا src/. ليه الـ allowlist لوحدها مش كفاية؟ وتحط الحماية فين؟

Solution

لأن python -c "..." يقدر يمسح أي ملف، والـ allowlist شايفة اسم الأمر بس (نفس فكرة Case B). الحماية لازم تبقى على الـ resource نفسه: path restriction أو sandbox بيمنع الكتابة برا src/ على مستوى الـ file system، مهما كان الأمر اللي بيحاول. وبعدها تختبر بالطرق البديلة (Python، وscript، وأداة MCP) إنها فعلًا اتقفلت.

Exercise: Read the trade-off

الـ NI نزّل الـ ASR بـ 56.3 pp والـ utility بـ 24.5 pp. والـ CDL نزّل الـ ASR بـ 40.4 pp وزوّد الـ utility 5.2 pp. ينفع تقول إن الـ CDL "أحسن" من الـ NI؟

Solution

لأ. كل واحدة اتقاست في benchmark مختلف بمهام وهجمات مختلفة. هجمات الـ NI كانت callbacks وexfiltration عن طريق الشبكة، وهجمات الـ CDL كانت أوامر خطيرة زي مسح جدول أو نسخ مفتاح. الـ denylist ماكانتش هتوقف الـ callback اللي جوه package lifecycle hook. السؤال الصح: أنهي هجمة بتخاف منها، وأنهي capability محتاجها الشغل الشرعي؟

Key takeaways

  • وجود الـ mechanism مش معناه إنها شغالة: 109 من 205 implementation مؤكد كانوا opt-in.
  • الـ auto-approve بيرفع إنجاز الشغل ونجاح الهجمات مع بعض، والـ ASR زاد في كل الـ harnesses الستة.
  • قفل capability مشتركة (network، write) بيحمي بتمن كبير في الـ utility. القيود الدقيقة على العملية الخطيرة أرخص.
  • الـ prompt-injection filter لوحده ماعملش فرق يذكر في المقارنة الوحيدة اللي اتعملت.
  • احمي العملية أو الـ resource، مش اسم الأمر: interpreter مسموح كفاية يعدّي allowlist.
