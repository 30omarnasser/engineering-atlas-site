How Always-On Agents Work ​

ReviewedPublishedAI-assisted

Week 3 of CS146S, guest lecture by Lee Robinson: how the week-one agent loop becomes an always-on agent that runs on a server, wakes on events, has its own computer, keeps memory and skills in files, and engineers its context for caching.

Overview ​

المحاضرة دي guest lecture من Lee Robinson. بتبدأ من الـ agent اللي بنيناه في أول أسبوع: messages، وwhile True، وtool calls. والـ slide بتقول عيبه في جملة: "This agent stops when you close the terminal" [cs146s-1008, slide 3]. السؤال بقى: إزاي تبني agent يفضل شغال، ويصحى على أحداث، وليه ده بيخليه نوع تاني من المنتجات؟

Sources for this page

مفيش transcript منشور للمحاضرة دي، فالمصدر هو الـ 46 slide. كل نقطة منسوبة للمحاضرة موجودة على slide. الـ study notes كانت مبنية على transcript جزئي عند صاحبها بيقف عند الكلام عن الـ triggers؛ الكلام اللي في الـ notes ومش على الـ slides متعلّم إنه توضيحي أو اتشال.

Learning objectives ​

  • تقارن agent التيرمنال بالـ always-on agent في 6 نقط.
  • ترسم الـ lifecycle: trigger، وrouter، وqueue، وturn، وsave، وsleep.
  • تشرح الأجزاء التلاتة: الـ apps، والـ server، والـ agent's computer، وليه الـ agent بيشتغل على الـ server.
  • تشرح قواعد الـ harness هنا: أداة واحدة للكلام مع المستخدم، وتحميل الأدوات وقت الحاجة، والأمان.
  • تطبّق أفكار الـ context engineering: prefix ثابت للـ caching، وcontext رئيسي صغير، وmemory في ملفات.

Prerequisites ​

  • Building a Minimal Coding Agent: الـ loop اللي المحاضرة بتبدأ منه.
  • The Anatomy of a Modern Coding Agent وAgent Harness: الـ subagents والـ compaction والـ skills.

Key ideas ​

1. Your agent vs an always-on agent ​

الـ slide بتحط الاتنين قصاد بعض [cs146s-1008, slide 4]:

Week-one agentAlways-on agent
شغال في التيرمنال على اللابتوب بتاعكشغال على server، فبيعيش بعد crash أو deploy أو لما تقفل اللابتوب
بيستخدم جهازكعنده cloud computer خاص بيه: VM صغيرة فيها desktop وbrowser وملفات
فاكر الـ messages list بسبيحفظ الـ state والـ memory والـ skills، وبيلخص الرسايل القديمة
بيطبع كل رد من الموديلمابيكلمكش غير لما ينادي send tool، فيقدر يسكت
بيبدأ لما تكتببيبدأ على events: رسالتك، أو schedule، أو Slack، أو مكالمة، أو شغل خلص
مهمة واحدة وبيخرجبيشتغل شهور بنفس الـ memory عبر محادثات كتير

2. How we got here ​

الـ slide بتقسم شغل المطورين مع الـ AI لمراحل حسب "الـ AI بيعمل قد إيه" [cs146s-1008, slide 7]:

  1. 2022–23، Copy and paste: chat في tab، وإنت بتنقل الكود رايح جاي بإيدك.
  2. 2024–25، Agents in the terminal: الـ agent بيعدّل ملفات ويشغّل أوامر في loop، وإنت بتوافق على كل خطوة.
  3. 2025–26، Apps built for agents: agents كتير بتشتغل بالتوازي في الـ background أو الـ cloud، وإنت بتراجع النتيجة.
  4. Now، Always-on agents: بتبعت رسالة لـ agent عنده computer وأدوات وmemory، وبيكمّل بعد ما تمشي.

والنقلة اللي في slide 8: من إنك توافق على كل خطوة لإنك توجّه: الـ agent بيشتغل ساعات، وإنت بتبعتله "Actually, make it Thursday" وهو شغال، وفيه auto-review بيوافق على حاجات بدل ما يستناك [cs146s-1008, slide 8]. والخلاصة: "As models get more capable, the interface gets simpler". والـ implementation بتاعتهم للـ always-on agent اسمه "Bot" [cs146s-1008, slide 9].

3. Six new model capabilities ​

الـ slide بتعدّ 6 قدرات خلت ده ممكن [cs146s-1008, slide 11]:

  1. Work for hours: يشتغل ساعات ويفضل ماشي ورا تعليمات معقدة طول الوقت.
  2. Hand off to helpers: agent رئيسي بيدّي مهام لـ helpers كل واحد بـ fresh context، فالشغل الكلي مش محدود بـ context window واحد.
  3. Use real tools: shell وملفات وbrowser وapp APIs عن طريق MCP.
  4. Use a computer: يبص على الـ screen ويعمل click، فيقدر يستخدم apps مالهاش API.
  5. Keep knowledge in files: الـ skills والـ memories ملفات نصية الـ agent بيقراها ويحدّثها بنفسه.
  6. Learn by watching: توريه إزاي بتعمل مهمة على الـ computer بتاعه، فيحفظ الخطوات كـ skill.

Correction to the study notes

الـ notes عدّت الـ 6 كده: instruction following، وsubagents، وtool use، وcomputer use، وfile-based memory، و"Skills & Routines". القدرة السادسة على الـ slide هي Learn by watching، والـ skills والـ memories مع بعض هما الخامسة [cs146s-1008, slide 11].

4. What the agent knows lives in files ​

مثال مبسّط على الـ slide [cs146s-1008, slide 12]: folder اسمه memory/ فيه profile.md (دايمًا في الـ prompt) وlog/2026-10.md (حقائق بتاريخ، واحدة في كل سطر)، وfolder skills/ فيه skills زي linkedin-sourcing/SKILL.md، وfolder routines/ فيه مثلًا morning-brief (prompt + "weekdays 8:00"). والأفكار جنبه:

  • الموديلات شاطرة جدًا في Linux والـ shell commands، والنص العادي بيخليك إنت والـ agent تقروا وتدوّروا وتعدّلوا. والشعار: "Everything is computer".
  • الـ agent بيحدّث الملفات بنفسه: تقوله تفضيل مرة، يحفظه في الـ memory.
  • الـ skills بتتحمل وقت الحاجة بس، "so having many of them is cheap". ودي نفس فكرة الـ progressive disclosure من المحاضرة اللي فاتت.

الفرق بين الـ تلاتة (تنظيم توضيحي): الـ memory معلومات عنك وعن الشغل اللي فات، والـ skill طريقة تعمل بيها نوع شغل، والـ routine مهمة بتتشغّل على schedule أو trigger.

5. How it stays always on ​

"Always on" مش معناها إن الموديل شغال 24 ساعة. الـ slide بتوضح [cs146s-1008, slide 14]:

  • الـ agent process بيصحى على trigger، بيحمّل الـ state، بيشتغل turn وبيحفظ كل خطوة، وبيقف بعد دقيقتين idle.
  • الـ agent's computer بينام (بيتحفظ على الـ disk)، وبيرجع بس لما أداة تحتاجه. routine مش محتاجة الـ computer ممكن تخلص وهو نايم.
  • الـ saved state (database وstorage: محادثات، وmemory، وroutines، وskills) دايمًا على الـ server.

والجملة اللي تحت الـ slide: "When nothing is happening, nothing runs".

إيه اللي بيصحّيه [cs146s-1008, slide 15]: رسالة منك من أي app، أو routine (schedule أو webhook)، أو mention في Slack، أو مكالمة أو meeting، أو agent تاني، أو شغل في الـ background خلص، أو check-in متجدول. الـ router بيشيل التكرار ويختار المحادثة، والـ queue بتاعة المحادثة بتشغّل turn واحد في المرة، وفي الآخر سؤال: "Anything worth saying?"؛ لو لأ، يسكت. وكل wake-up بيتسجل مصدره، عشان الـ agent يعرف إذا كنت إنت اللي طلبت، ولا routine، ولا خدمة برا.

6. The agent's computer ​

الـ slide بتوصف الـ computer [cs146s-1008, slide 16]:

  • Firecracker virtual machine، واحدة لكل user، بتتحفظ على الـ disk لما تبقى idle. جواها Linux (Debian) container، وفيه supervisor بيخليه شغال.
  • File server للملفات والـ app connections والـ live desktop view، وcommand runner للـ shell والملفات والـ screenshots والـ clicks، وscreens كل واحدة بـ Chrome خاص بيها (screen لكل agent شغال).
  • النوم: بعد كام دقيقة من آخر نشاط، وأبدًا مش في نص turn: الملفات بتتزامن مع الـ cloud storage، والـ memory والـ disk بيتحفظوا snapshot، والـ VM بتقف.
  • الصحيان: مع أول tool call: الـ snapshot بيرجع مكانه، والـ logins والأدوات المتثبتة لسه موجودة، والـ conversation state جاي من الـ server.

7. Three parts of the system ​

الرسمة مبنية على slide 17: الـ agent بيشتغل على الـ server، وبيستخدم الأدوات على الـ computer بتاعه، وكل الـ apps بتعرض نفس المحادثة [cs146s-1008, slide 17]. والأسباب اللي بتخلي الـ agent على الـ server مش على الجهاز [cs146s-1008, slide 18]: thin client وthick server؛ تقفل اللابتوب والشغل يكمّل؛ تنقل بين الكمبيوتر والموبايل؛ تنزّل كود من غير App Store review؛ الـ agent loop منفصل تمامًا عن كود الـ app؛ وagents بتشتغل شهور مايقدروش يبقوا على device. والقاعدة: "Save everything on the server. The virtual machine can then always be rebuilt" [cs146s-1008, slide 19].

8. Sending, ordering, and surviving crashes ​

لما تدوس send [cs146s-1008, slide 20]:

  1. الـ app بيعرض الرسالة على طول وبيحفظها locally بـ unique ID، والـ server بيرمي أي ID شافه قبل كده، فالـ retries آمنة.
  2. الرسالة بتدخل queue المحادثة، والـ agent بيشغّل turn (model، tools، repeat) وكل خطوة بتتحفظ.
  3. الـ server بيبعت signal صغير "something changed" من غير data، فضياعه مش مشكلة، وكل app بيجيب الرسايل الجديدة بنفسه.
  4. كل update ليه sequence number؛ لو رقم ناقص، الـ app بيعمل reload من الـ database.

ولو الـ server وقع في نص turn؟ الـ slide بتقارن [cs146s-1008, slide 21]: الـ job queue بيبدأ من الأول ويعيد شغل خلص، والـ durable workflow بيكمّل من آخر خطوة متسجلة. والشرط إن كل خطوة تبقى idempotent: تشغيلها مرتين مايعملش ضرر. والـ engines زي Temporal فيها timers وcancellation وhealth checks جاهزة.

وقواعد الرسايل الجديدة وهو شغال [cs146s-1008, slide 22]: إنت في محادثة 1:1 بتتخطى الطابور وتقدر توقف أو تقاطع الـ turn؛ الباقيين (group chats، وSlack threads، وroutines، وhelpers) بيقفوا في الطابور؛ وكذا رسالة سريعة ورا بعض بيتجمعوا في turn واحد.

Correction to the study notes

الـ notes قالت إن الصورة مش بتحدد إذا كانت الرسايل بتتنفذ بالترتيب ولا إزاي المقاطعة بتحصل. الـ slides بتحدد: turn واحد في المرة لكل محادثة، والـ batch بيتشغّل مع بعض، وإنت بس في الـ 1:1 تقدر تقاطع [cs146s-1008, slides 20-22].

9. The harness ​

أداة واحدة للكلام معاك [cs146s-1008, slide 24]: فيه أدوات كتير للشغل (Shell، Files، Browser، Desktop، Memory، Skills، helper agents، web search...)، وأداة واحدة بس للكلام: SendToUser. والنتيجة: تفكير الموديل العادي مابيوصلكش، والسكوت مسموح لو مفيش جديد، والرسايل ممكن تبقى rich (ملفات، اختيارات، إدخال password آمن)، وآخر رسالة ممكن تنهي الـ turn من غير model call زيادة.

أدوات بـ UI مخصص [cs146s-1008, slide 25]: لو محتاج تشوف أو توافق، الأداة بتطلع control مناسب: sign-in form الـ password فيها مابيوصلش للموديل، ومشتريات بتستنى Allow أو Deny، وdraft إيميل تختار Send أو Discard.

حمّل تفاصيل الأداة وقت الحاجة [cs146s-1008, slide 26]: الأسماء الأول والتفاصيل on demand، بدل ما كل الأدوات تتحمل من الأول (الـ slide بتقول إن الرسمة illustrative). نفس روح الـ search + execute في محاضرة MCP.

جرّب الأرخص الأول [cs146s-1008, slide 27]: سلّم من 6 درجات: اللي يعرفه، وAPI الـ app (connector)، وweb search، والـ browser بتاعه المتسجل فيه، والـ desktop كله، وفي الآخر يسألك. كل ما تطلع بتبقى أبطأ وأغلى وأخطر. ولو connector بايظ، مايلفّش حواليه بالـ browser؛ يقولك ويسأل.

تلات طرق لاستخدام الـ computer [cs146s-1008, slide 28]: يقرا structure الصفحة (الأزرار والـ links والـ fields) ويضغط عليها مباشرة، وده أسرع وأوثق من الـ screenshots؛ أو mouse وkeyboard على شاشة 1280×800 للـ desktop apps؛ أو يسأل إنسان عند الـ logins والـ codes والـ captchas والدفع. وفيه helper منفصل بيعمل الـ clicking، عشان الـ screenshots ماتملاش context الـ agent الرئيسي.

Agent رئيسي وhelpers كتير [cs146s-1008, slide 29]: الرئيسي بيرد على الأسئلة السريعة بنفسه، وبيدّي المهام الكبيرة لـ helper عشان يفضل فاضي يكلمك: general helper، وcomputer-use helper، وvideo helper، وcloud coding agent في VM لوحده. وكل helper بيرجّع تقرير قصير. الشرح العام للـ subagents في The Anatomy of a Modern Coding Agent.

نصايح لتصميم الأدوات [cs146s-1008, slide 30]:

  • ماتضيفش أو تشيل أدوات بين الـ turns؛ لو أداة مش متاحة دلوقتي، خليها ترجّع error واضح.
  • وصف كل أداة والـ schema بتاعها أقل من 4,000 حرف.
  • استخدم أداة مخصصة لحفظ الـ state بدل shell commands، عشان اللي بيراجع يشوف إيه بيتغير.
  • رسايل الـ error تقول تعمل إيه بعدها: "The computer is asleep. Use Shell or Read to wake it, then try again."

الأمان [cs146s-1008, slide 31]: موديل منفصل بيراجع الأفعال الخطرة قبل ما تتنفذ، ولو منع حاجة بيوصلك approval request، ولو مارديتش في 15 ثانية تبقى ممنوعة. النص الجاي من الإيميلات والـ webhooks متعلّم إنه untrusted، والـ memories بتتعامل كمعلومات مش تعليمات. مابيبعتش إيميلات أو رسايل لناس إلا لو طلبت، والـ routines الجديدة محتاجة موافقتك. والـ passwords بتروح environment variables، عمرها ما بتوصل للموديل.

10. Context engineering ​

خلي بداية الـ prompt ثابتة [cs146s-1008, slide 33]: الترتيب: tool definitions، وsystem prompt (فيه snapshot من الـ memory والـ routines)، وأول رسالة (تفاصيل البيئة وأسماء الأدوات)، وبعدين الـ history، وفي الآخر الرسالة الجديدة (الوقت، وملاحظات قصيرة عن اللي اتغير، ورسالتك). الـ providers بياخدوا أقل وبيردوا أسرع لما بداية الـ prompt تطابق prompt قريب، فالثابت أولًا والجديد آخرًا.

خلي الـ context الرئيسي صغير [cs146s-1008, slide 34]: الـ outputs الطويلة تروح ملفات والـ context يحتفظ بالـ path؛ الرسايل القديمة تتلخص؛ الـ screenshots تروح لـ helper؛ الـ memories القديمة تفضل searchable؛ الشغل التقيل على الأدوات يروح لـ helpers؛ والتعليمات تبقى skills والـ prompt يحتفظ بـ pointer من سطر واحد.

Treat a cache miss like a bug [cs146s-1008, slide 35]: لحد الملخص الجاي، الأدوات والـ system prompt وأول رسالة لازم يفضلوا زي ما هما بالظبط. لو deploy غيّر وصف أداة، المحادثات الشغالة تاخد note بدل النص الجديد. كل حاجة بتتبني بترتيب ثابت ومتسورتة، وكل section ليه hash لوحده عشان تعرف إيه اللي اتغير. والأدوات عمرها ما بتتضاف أو تتشال لـ turn واحد؛ الأداة المش متاحة بترجّع error. ولما تفتح الشات أو تبدأ تكتب، الـ server بيجهّز الـ prompt بدري عشان يسخّن الـ cache.

لخّص وإنت مش موجود [cs146s-1008, slide 36]: لو turn كبير خلص والـ prompt عدّى 100,000 token، بعد حوالي 10 دقايق (والـ cache لسه warm) بيكتب ملخص بنفس بداية الـ prompt فيستفيد من الـ cache، ورسالتك الجاية تبدأ من الملخص. آخر كام رسالة ليك بتتحفظ كلمة بكلمة. ولو turn طوّل جدًا، ممكن يلخص في النص. والخطوة دي بتتلغي لو فيه شغل background هيصحّي الـ agent كده كده.

إزاي بيفتكر [cs146s-1008, slide 37]:

LayerWhat it holds
Profileحقائق أساسية عنك، دايمًا في الـ prompt: لحد 100 fact في 4,000 حرف
Logأحداث بتاريخ؛ أهم 30 حديثة بتدخل الـ prompt
Notesتفاصيل قصيرة المدى بتبهت بسرعة
Everything elseبيتلاقى بأداة memory search وقت الحاجة

وبعد كل turn فيه pass بيضيف حقائق ويستبدل القديمة، وبيقدر يشيل بس الحقائق اللي اتعرضت عليه. الحقائق المهمة ترتيبها أعلى، والقديمة ترتيبها بينزل بالراحة. والحقائق عنك مشتركة بين كل الـ agents بتوعك، بس كل agent بيكتب في ملفه هو. والموديل متقاله إن الـ memories معلومات، مش تعليمات.

11. Where this is going ​

  • تدريب الموديل للمنتج [cs146s-1008, slide 39]: pre-training، وبعدين supervised fine-tuning على الـ harness (الأدوات وformats بتاعتها، وإمتى ترد بسرعة)، وبعدين reinforcement learning على مهام حقيقية (تعليمات طويلة، skills وmemories، grounding في الـ clicks). الرئيسي متظبط للردود السريعة، والـ helpers للمهام الطويلة.
  • المنتج والموديل بيتحسنوا مع بعض [cs146s-1008, slide 40]: كل bot بيغلط يبقى eval؛ الـ evals بتصلّح المنتج النهارده، وبتدرّب الموديل الجاي. فيه loop داخلي كل يوم (غلطة، eval، تصليح في الـ harness أو الـ prompt أو الـ inference، شيك على الـ evals، ship)، وloop خارجي كل كام شهر (درّب الموديل الجاي على الـ harness والـ evals، وحطّه في المنتج، والناس تستخدمه بطرق جديدة زي "group chats full of bots"، فيطلع سلوك جديد يتقاس ويتدرّب عليه).
  • "Delete the product." افترض إن الموديلات هتتحسن جدًا، وابني أقل حاجة ممكنة حواليها، وشيل اللي مابقتش محتاجاه [cs146s-1008, slide 41].
  • توقعات لـ 6 لـ 12 شهر [cs146s-1008, slide 42]: مشاريع أطول (agent على مشروع واحد شهور، مش مهمة دقايق)، وmemory أحسن (بيفتكر إزاي إنت وفريقك بتشتغلوا)، وأدوات أقوى (أي حاجة بتتعمل على كمبيوتر، أسرع وأوثق)، وinterfaces أبسط (texting النهارده، ويمكن voice بس بعد كده)، وskills ماتدرّبش عليها (يتعلم وهو شغال)، ومعرفة متكتوبة (الناس والشركات هيكتبوا اللي يعرفوه عشان الـ agents تستخدمه).
  • Open problems [cs146s-1008, slide 43]: اختبار agents بتشتغل أسابيع، وmemory صحيحة (تستبدل القديم وتنسى لما تتطلب وماتألفش)، والـ prompt injection، وإمتى يتكلم، والتنسيق بين agents كتير على computer وmemory واحدة، والتكلفة (الـ always-on بينفع بس لو الـ idle شبه ببلاش).
  • الـ building blocks الجديدة [cs146s-1008, slide 44]: زي ما كل web app كان فيه server وdatabase وcache وCRUD interface، كل agent product هيبقى فيه: durable workflows، وقدرة يستخدم كمبيوتر، وmemory وskills، وtriggers وscheduled jobs، وconnectors وauth، وقنوات text وvoice، وpayments وidentity، وevals وobservability. منتجات كتير هتشبه بعض بس هتبني القطع دي بشكل مختلف جدًا.
  • الـ takeaways [cs146s-1008, slide 45]: لما الكود يبقى رخيص، الـ architecture الصح هي اللي بتفرق؛ ابدأ من الـ week-one agent وضيف server وcomputer وmemory، والـ always-on agents الـ open-source حلوة تتعلم منها؛ واتعلم الأساسيات.

Exercises ​

Exercise: Design the queue rules

عندك always-on agent في Slack channel. في نص turn، 3 رسايل وصلت: واحدة منك في DM بتقول "stop"، وواحدة من زميل في الـ thread، وroutine أسبوعي حان وقته. رتّبهم حسب قواعد slide 22.

Solution

رسالتك في الـ 1:1 بتتخطى الطابور وتوقف الـ turn. رسالة الزميل والـ routine بيستنوا في الطابور ورا الـ turn الحالي، ولو جم ورا بعض بسرعة ممكن يتجمعوا في turn واحد [cs146s-1008, slide 22].

Exercise: Find the cache breakers

إيه من دول بيكسر الـ prompt cache حسب slide 33 و35: (1) إضافة أداة جديدة للـ turn ده بس. (2) رسالة جديدة من المستخدم. (3) تحديث وصف أداة بعد deploy في نص محادثة. (4) إضافة الوقت الحالي في آخر الـ prompt.

Solution

(1) بيكسر، وعشان كده القاعدة إن الأدوات ماتتضافش لـ turn واحد. (3) كان هيكسر، فالمحادثات الشغالة بتاخد note بدل النص الجديد. (2) و(4) لأ، لأنهم في آخر الـ prompt [cs146s-1008, slides 33, 35].

Exercise: Job queue or durable workflow

agent بيعمل 5 خطوات: يقرا إيميل، يكتب رد، يبعته، يحدّث CRM، يبلّغك. الـ server وقع بعد الخطوة 3. إيه اللي يحصل في job queue، وفي durable workflow؟ وأنهي خطوة لازم تبقى idempotent أكتر من غيرها؟

Solution

الـ job queue هيبدأ من الأول وممكن يبعت الإيميل مرتين. الـ durable workflow هيكمّل من الخطوة 4. وخطوة "يبعته" لازم تبقى idempotent (مثلًا unique ID للرسالة) عشان أي retry مايبعتش تاني [cs146s-1008, slide 21].

Review questions ​

  1. ليه "always on" مش معناها إن الموديل شغال طول الوقت؟
  2. إيه دور الـ router والـ conversation queue؟
  3. ليه فيه أداة واحدة بس للكلام مع المستخدم، وإيه الفايدة؟
  4. اشرح "Treat a cache miss like a bug" بمثال.
  5. إيه الطبقات الأربعة للـ memory، وليه الـ memories بتتعامل كمعلومات مش تعليمات؟
