Overview ​

المحاضرة اللي فاتت كانت proof of concept: شوف تقدر تعمل إيه في 200 سطر. المحاضرة دي بتنقلنا لـ coding agent حديث، وبتشرّحه عشان نشوف إيه اللي بيحصل جوه، كل حاجة ما عدا الموديل نفسه، لأن ده private وشغال على servers [cs146s-0924]. اللي نقدر نشوفه هو الـ harness اللي حوالين الموديل.

والطريقة اللي المحاضر استخدمها عملية جدًا: اشتغل مع Claude Code على to-do app صغير، وسجّل كل الـ requests والـ responses في ملفات JSON (trace)، وبعدين فتحها قدام الطلبة [cs146s-0924, 20:40]. والـ assignment بيطلب من الطلبة يعملوا نفس الحاجة بنفسهم [cs146s-0924].

Learning objectives ​

  • تعدّد مكونات الـ harness الحديث وتشرح كل واحد بيظهر فين في الـ request الحقيقي.
  • تفهم إن كل اللي الموديل "بيعرفه" عن البيئة جاي من نص الـ harness بيحقنه، حتى لو إنت مكتبتوش.
  • تشرح ازاي الـ subagents والـ compaction والـ skills بيديروا الـ context كل واحد بطريقة.
  • تطبّق مبدأ البساطة لما تصمم harness أو تضيف أدوات.

Prerequisites ​

  • Building a Minimal Coding Agent: المحاضرة دي بتبني عليها مباشرة.
  • Agent Loop وTool Calling.

Key ideas ​

1. Same loop, more around it ​

الـ slide الأولى بعد المراجعة بتعيد نفس صورة المحاضرة اللي فاتت: مستخدم، وclient، وloop مع LLM، وtool calls بتتنفذ برا الموديل. الجديد إن الـ harnesses الحديثة أعقد، والمكونات اللي بقت standard تقريبًا هي: system prompt، وconfiguration files زي AGENTS.md، وtool list، وplan mode، وsubagents، وskills، وhooks، وcompaction [cs146s-0924].

التعريف المختصر لكل مكون في صفحة Agent Harness. هنا هنمشي ورا الـ trace.

2. What one request actually contains ​

أول حاجة الطلبة سألوا عنها: هو كل ده جوه request واحد؟ والإجابة: أيوه [cs146s-0924, 24:11]. الـ request الواحد فيه:

  • اسم الموديل، وقايمة الـ messages زي الـ conversation اللي بنيناها في المحاضرة اللي فاتت.
  • الـ system prompt.
  • الأدوات كلها: حوالي 40 أداة built-in، وبعدها أدوات كل MCP server ضفته، حتى لو third-party. وكل ده بيتبعت مع كل request [cs146s-0924, 25:58].

المحاضر قسّم الـ 40 أداة لمجموعات: أدوات للملفات، وBash للـ shell، وأدوات monitoring وscheduling بأسلوب cron، وweb search، وLSP search (Language Server Protocol) عشان يفهم الكود، وأدوات خاصة بالـ agents والتخطيط والعزل، وأدوات للتفاعل مع المستخدم زي الأسئلة والـ notifications، وأدوات لتشغيل الـ skills وقراءة MCP resources [cs146s-0924]. والأهم من القايمة: الفريق اللي بنى Claude Code اختار الأدوات دي، والموديل نفسه متدرب إنه يستخدمها كويس [cs146s-0924].

Why this matters for you

لما تضيف MCP server فيه 30 أداة، إنت مش بس بتضيف قدرات؛ إنت بتضيف 30 وصف بيتبعتوا في كل call. ده موضوع المحاضرة الرابعة (MCP, Tool Calling, and Beyond).

3. The system prompt ​

الـ system prompt هو blueprint لسلوك الموديل: block نصي بيعرّف الـ harness وسلوكه، والـ guardrails، ومعلومات عن البيئة (إنت فين، والنظام إيه). والـ harness بيحقنه من غير ما تشوفه [cs146s-0924, 34:30].

4. Configuration files: CLAUDE.md and AGENTS.md ​

CLAUDE.md خاص بـ Claude، وAGENTS.md هو الـ standard الأعم. المحاضر بيقول إن كله كان متفق على AGENTS.md ما عدا Anthropic، وبعدين من كام أسبوع بدأوا يدعموه هما كمان، وإن الاتنين عمليًا نفس الحاجة باسمين، ومن الحلول إنك تعمل symlink من واحد للتاني [cs146s-0924, 42:44].

الجملة المهمة: ده النسخة اللي إنت بتتحكم فيها من الـ system prompt. الاتنين بيتحقنوا، بس الـ system prompt static من الـ harness، والـ CLAUDE.md إنت اللي كاتبه [cs146s-0924, 44:22].

وفي الـ trace بان حاجة مفاجئة: أول رسالة كتبها المحاضر كانت "What are the core components of this to-do app?"، بس قبلها جوه نفس الـ user block فيه نص هو ماكتبهوش: "system reminder" ومحتوى الـ CLAUDE.md، ومعاه جملة بتقول إن التعليمات دي override الـ default behavior ولازم تتنفذ زي ما هي [cs146s-0924, 46:09]. يعني الـ harness بيحط تعليماتك جوه رسالتك قبل ما توصل للموديل.

قواعد الاكتشاف والتحميل لكل أداة (Codex وClaude Code) ودقة الكلام عن الدعم في Agent Instruction Files.

5. Plan mode ​

أغلب الـ harnesses ضافت plan mode من حوالي تسع شهور أو أكتر: وضع لتطوير specs، والنقاش مع المستخدم عشان يوضّح الـ requirements والـ architecture قبل التنفيذ. وفي الـ trace، الـ plan mode prompt طلع "literally a block of text"، وفيه أداة للدخول في الوضع ده، والفكرة نفسها موجودة في Codex وغيره [cs146s-0924].

والـ prompt بتاع Claude بيوصف workflow للتخطيط على مراحل [cs146s-0924, 48:03]:

  1. Understand requirements: فهم المطلوب، ومن ضمنها إن الـ agent يطلق agents تستكشف الـ codebase.
  2. Design.
  3. Review.
  4. Final plan، وبعدها تعليمات للخروج من الـ plan mode.

والمخرج المهم في الآخر هو plan file: artifact مكتوب للخطة [cs146s-0924, 50:12]. (الـ study notes ذكرت نفس الأربع مراحل، والـ transcript بيأكدها.)

6. Skills and progressive disclosure ​

الـ skill هو إجراء مكتوب الـ agent بينفذه: prompt فيه tool calls أو تشغيل scripts محلية، وممكن يتشغّل لوحده أو بطلب صريح [cs146s-0924]. وهنا المحاضر قال ملاحظة تاريخية مهمة: MCP جه الأول، والـ skills جت بعده، ومن أسباب ظهورها progressive disclosure. أدوات الـ MCP بتتحط كلها في كل request، إنما الـ skill في الأول بيظهر منه metadata صغيرة بس بتوصف هو بيعمل إيه، والتفاصيل بتتحمل لما تكون ليها علاقة بالمهمة [cs146s-0924, 25:58].

7. Subagents ​

الـ subagents بتخليك توزع أجزاء من المهمة. فيه orchestrator رئيسي (الـ control loop بتاع Claude Code)، وبيستدعي workers كل واحد بـ fresh context window، وده بيسمح بالتوازي وبسلوك مخصص لكل نوع شغل. لما الـ worker يخلص، بيرجّع الـ output للـ agent الرئيسي [cs146s-0924, 53:40].

الميزة الحقيقية مش السرعة بس: الاستكشاف بيحصل برا الـ control flow الرئيسي، فكل الملفات اللي الـ subagent قراها مابتملاش الـ context بتاع الـ agent الرئيسي [cs146s-0924, 53:40]. والتمن: الـ slides بتقول إن التوازي بيزوّد تكلفة الـ tokens [cs146s-0924]. وفي الـ trace، الـ subagent اتنادى بـ tool call عادي، عمل شغله، ورجّع النتيجة [cs146s-0924].

8. Hooks ​

الـ hooks هي prompts أو أجزاء كود بتتحط في نقط مختلفة من دورة حياة الـ harness، ومفيدة لو محتاج pre-processing أو post-processing [cs146s-0924]. المحاضر عدّى عليها بسرعة، ووعد يرجعلها بعدين.

مثال توضيحي (مش من المحاضرة): hook بيشغّل الـ formatter بعد كل تعديل ملف. الفرق بينه وبين تعليمة في AGENTS.md إن الـ hook بيتنفذ في كل مرة بالكود، مش متوقف على إن الموديل يفتكر.

9. Compaction ​

لما الـ context يطول، الـ compaction بيجمّعه ويلخصه. بيحصل بطريقتين: تلقائي لما تقرب تعدّي الـ context window، أو يدوي لما تطلبه. فيه prompt كامل بيحدد إزاي الملخص يتعمل، والملخص بيحل محل الجزء اللي اتلخص. والمحاضر ضرب مثال توضيحي: ممكن 500,000 token يتضغطوا لـ 150,000، وده اللي الموديل هيشوفه بعد كده [cs146s-0924, 55:25].

الـ slides بتنبّه إن الـ compaction "can be lossy"، وإنك ممكن تحتاج تعمل طريقتك الخاصة [cs146s-0924]. التفاصيل (إمتى تعمل compact، وبيكلّف إيه، وبيأثر على جودة القرارات إزاي) في صفحة Context Compaction وتحليل مقال The Context Tax.

10. The principle: simplicity ​

آخر slide هي أهم واحدة [cs146s-0924]:

  • أدوات أقل وأقوى. Bash وSQL أمثلة: بـ Bash والـ file system تقدر تعمل عمليات معقدة جدًا، لأن Bash لغة كاملة. والـ 40 أداة في Claude أقل من نسخ أقدم من الـ harness. والنصيحة: ابدأ بتلات لخمس أدوات قوية ووسّع بعدين.
  • خلي بالك من الـ context window. الـ tool bloat بيوصلك للـ "dumb zone"، الاسم غير الرسمي للمنطقة اللي الموديل بيبقى فيها أقل كفاءة.
  • الـ prompts بتتغير. الاتجاه دلوقتي نحو prompts أقصر، وده بيخليها أسهل في التعديل كمان.

والسبب اللي المحاضر قاله: مصممين الـ harnesses بقوا معتمدين أكتر على قدرات الموديل نفسه [cs146s-0924].

Technical example ​

تقدر تشوف "الـ harness كنص" بنفسك في الـ lab بتاع المحاضرة الأولى: الـ system prompt بيتولّد من الأدوات. التمرين التاني تحت بيخليك تبني trace صغير بنفس فكرة المحاضرة.

python
import json, time

def traced(llm):
    """Wrap any llm(conversation) function and log every request and response as JSON lines."""
    def call(conversation):
        reply = llm(conversation)
        with open("trace.jsonl", "a", encoding="utf-8") as f:
            f.write(json.dumps({"t": time.time(), "request": conversation, "response": reply}) + "\n")
        return reply
    return call

لو لفّيت الـ llm اللي في mini_agent.run_agent بـ traced(...)، هتلاقي كل request فيه الـ system prompt كامل والـ history كلها، ونفس الملاحظة اللي المحاضر وراها: الـ request بيكبر مع كل خطوة.

Limitations and open questions ​

  • المحاضر وضّح إنه بيشرح Claude Code كمثال، والفكرة بتتعمم على harnesses تانية زي Codex. التفاصيل (عدد الأدوات، أسماءها) خاصة بإصدار معين وبتتغير.
  • الـ hooks اتشرحت بسرعة، والـ "best practices" بتاعتها مؤجلة لمحاضرة لاحقة.
  • سؤال مفتوح: إمتى الأفضل تعمل compaction يدوي بدل ما تستنى التلقائي؟ المحاضر قال إنها هتتناقش بعدين [cs146s-0924, 55:25].

Exercises ​

Exercise: Map a real request

افتكر آخر مرة استخدمت فيها coding agent. اكتب كل حاجة من دول كانت موجودة في الـ request غالبًا، وإنت ماكتبتهاش: system prompt، تعليمات من ملفات، أوصاف أدوات، أدوات MCP، skills metadata.

Solution

غالبًا كلهم. النقطة إن الرسالة اللي إنت كتبتها جزء صغير من الـ request. المحاضر شاف CLAUDE.md بتاعه متحقن جوه نفس الـ user block بتاع رسالته الأولى [cs146s-0924, 46:09].

Exercise: Build your own trace

استخدم الـ traced wrapper فوق مع الـ lab بتاع المحاضرة الأولى، وشغّل الـ happy path. احسب حجم كل request بعدد الحروف. هل الحجم بيزيد خطوة بعد خطوة؟

Solution

أيوه. كل request فيه الـ system prompt + كل الرسائل اللي قبله، فالحجم بيزيد مع كل tool result. ده نفس السبب اللي بيخلي الـ compaction والـ subagents موجودين.

Exercise: Choose the mechanism

لكل موقف اختار: AGENTS.md، skill، subagent، hook، ولا compaction؟ (1) "شغّل pytest بعد أي تعديل، من غير استثناء". (2) "لما تعمل code review اتبع checklist من 12 خطوة". (3) "استكشف 200 ملف ورجّعلي ملخص". (4) "المشروع بيستخدم FastAPI وPostgreSQL". (5) جلسة طولها 3 ساعات بدأت تبطّأ وتلخبط.

Solution

(1) hook: لازم يحصل كل مرة بالكود. (2) skill: إجراء طويل يتحمّل وقت الحاجة. (3) subagent: الاستكشاف يفضل برا الـ context الرئيسي. (4) AGENTS.md: معلومة ثابتة عن المشروع. (5) compaction (أو session جديدة بملخص مكتوب، وده موضوع المحاضرة الجاية).

Review questions ​

  1. إيه الطريقة اللي المحاضر استخدمها عشان يشوف جوه Claude Code، وليه هي أدق من قراية الـ docs؟
  2. ليه أدوات الـ MCP بتكلّف context أكتر من الـ skills، بحسب كلام المحاضرة؟
  3. إيه الفرق بين subagent وcompaction كطريقتين لإدارة الـ context؟
  4. ليه Bash مثال على "أداة قوية"، وإيه علاقة ده بمبدأ البساطة؟
  5. إيه اللي ممكن يضيع في الـ compaction، وإزاي تقلل الخطر ده؟
