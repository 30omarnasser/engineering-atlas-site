MCP, Tool Calling, and Beyond ​

ReviewedPublishedAI-assisted

Week 2 of CS146S, second lecture: why MCP exists, how its tool-calling flow works, why mapping every API endpoint to a tool fails, how to design outcome-based servers, and how search-and-execute (code mode) loads tools on demand.

Overview ​

الـ LLMs عندها معرفة ضخمة بس ثابتة: مابتتحدثش غير لما الموديل يتدرب تاني. وعشان نبني أنظمة autonomous بجد، محتاجين طرق موثوقة ندخّل بيها بيانات متغيرة [cs146s-1001]. المحاضرة بتجاوب على سؤالين: إزاي نوصل الـ agent بأنظمة كتير من غير connector لكل واحدة؟ وإزاي نعمل ده من غير ما نغرّق الموديل في مئات الأدوات؟

Learning objectives ​

  • تشرح MCP في دقيقة: المشكلة، والأدوار، ودورة الـ tool call.
  • تشرح ليه الـ mapping واحد لواحد بين API endpoints وأدوات فشل.
  • تصمم أدوات MCP بأربع ممارسات: outcomes، وarguments صريحة، وتعليمات كأنها context، وأسماء تساعد الاكتشاف.
  • تشرح code mode (search + execute) وحدوده، وتقرا رقم "90%" بشكل نقدي.

Prerequisites ​

  • Model Context Protocol (MCP): التعريف والأدوار والـ transports بالتفصيل.
  • Tool Calling وThe Anatomy of a Modern Coding Agent.

Key ideas ​

1. MCP in one slide ​

الـ slides بتعرّف MCP كبروتوكول مفتوح بيخلّي الأنظمة تدّي context للموديلات بطريقة عامة عبر أي integration، و"in English": صيغة standard لعرض الأدوات للـ LLMs [cs146s-1001]. وفوايده في المحاضرة [cs146s-1001]:

  • من M×N connector لـ M+N.
  • مش محتاج تعيد كتابة الـ auth والـ error handling والـ rate limiting في كل connector.
  • output format ثابت عن طريق JSON-RPC.

المصطلحات: الـ host (Cursor، Claude Desktop)، والـ MCP client (library جوه الـ host)، والـ MCP server (wrapper خفيف قدام الأداة)، والـ tool (function ممكن تبقى data source أو API). والـ flow: الـ client بيبعت tools/list، والـ server بيرجّع JSON بيوصف كل أداة (اسم، ملخص، JSON schema)، والـ host بيحط الـ JSON ده في الـ context، والموديل بيطلع tool call منظم، والـ server بينفذ [cs146s-1001].

الصفحة دي هتركز على تصميم الـ servers. الشرح الكامل للبروتوكول في صفحة الـ concept.

2. The naive approach and tool bloat ​

في أول تلات أربع شهور من تصميم الـ MCP servers (2024 وأوائل 2025)، الناس كانت بتعمل لكل API endpoint أداة. والنتيجة: tool bloat، وcontext bloat، وموديلات متلخبطة، خصوصًا إن الموديلات وقتها كانت أضعف في التفريق بين الأدوات. المحاضر افتكر إن Cursor كان بيسمح بـ 88 أداة بس، وإن server GitHub لوحده كان بيدي حوالي 120 لـ 150 أداة [cs146s-1001].

والدرس الأساسي: MCP server مش REST API wrapper. الـ API endpoints معمولة للبشر (وأحيانًا مش كويسة للبشر كمان)، والموديل بيفكّر بالـ context اللي إنت بتديهوله، فالـ mapping واحد لواحد بيضيّع فرصة [cs146s-1001].

About the tool counts in the study notes

الـ notes فيها جدول بأعداد أدوات لكل server (GitHub 120، Slack 80...) ومكتوب تحته إنها أرقام توضيحية. الأرقام اللي اتقالت فعلًا هي GitHub (حوالي 120 لـ 150) وحد Cursor (88)، وده عن الأيام الأولى، مش النهارده [cs146s-1001]. (في محاضرة 9/24 نفس المحاضر قال "حوالي 110" لـ GitHub، فالرقم تقريبي.)

3. Design practice 1: outcomes, not operations ​

الـ slide: "Design for outcomes not operations" [cs146s-1001]. المثال بتاع الدفع:

في الطريقة الـ granular، لو معاك user ID بس، لازم تجيب الإيميل، وبعدين الحسابات، وبعدين تبعت الدفع بالـ account ID: تلات tool calls لازم تتعمل صح ورا بعض، وكل واحدة round trip كامل للموديل. الطريقة التانية call واحدة؛ إنت بتحوّل الـ outcome لأداة بدل ما تعرض كل خطوة [cs146s-1001]. والمحاضر لخصها إن الـ servers الأحسن بتركز على semantics: الموديل عايز يعمل إيه، مش البيانات متخزنة إزاي.

إضافة مهمة (مش من المحاضرة): دمج الخطوات مش مبرر لشيل الضوابط. في نظام مالي حقيقي، التحقق من المستلم والصلاحيات والتأكيد قبل التحويل لازم يفضلوا جوه الأداة.

4. Design practice 2: explicit arguments ​

افتكر أدوات المحاضرة الأولى: الـ arguments كانت typed صراحة. الـ type annotations والـ docstrings وأسماء الـ functions كلها جزء من الـ context اللي الموديل بيقرر بيه. استخدام *args و**kwargs سهل وشغال، بس بيلخبط الموديل. ومن أول المشاكل في الـ MCP servers: الموديل يختار الأداة الصح ويبعت arguments غلط. والحل: ابعد عن الـ dictionaries الضخمة اللي مالهاش types، واستخدم Pydantic أو type annotations [cs146s-1001].

python
# Hard for a model: what goes in kwargs?
def search(**kwargs) -> list[dict]:
    ...

# Easier: names, types, allowed values, and a docstring the model can read
from typing import Literal

def search_resources(query: str, resource_type: Literal["document", "ticket", "message"],
                     limit: int = 10) -> list[dict]:
    """Search indexed resources of one type and return at most `limit` matches."""
    ...

5. Design practice 3: instructions are context ​

"Instructions are context": الـ docstrings والـ error messages كلها prompts [cs146s-1001]. حتى إنك ترمي Exception عام بدل ValueError أو custom error type بيفرق، لأن نوع الـ error بيدّي الموديل hint يفهم بيه المشكلة ويصلّحها [cs146s-1001].

WeakBetter
Error: FailedDocumentNotFoundError: document 123 does not exist; call list_documents to see valid ids
raise Exception("bad input")raise ValueError("limit must be between 1 and 50, got 500")

6. Design practice 4: name tools for discovery ​

الـ slide: استخدم أسماء فيها prefix الخدمة (service-prefixed) [cs146s-1001]. لما يبقى فيه أداتين اسمهم search من servers مختلفين، الموديل مش هيعرف يفرّق؛ jira_search وdrive_search أوضح.

7. Consolidate from traces ​

المحاضر بيعترف إنك غالبًا هتبالغ في الأول: هتعمل أدوات تغطي كل حالة، وتلاقي نفسك عندك 100 أداة. ساعتها تبص في الـ traces بتاعة الموديل وتدوّر على أنماط. مثلًا: 3 أدوات منفصلة للبحث في الـ meetings والـ transcripts والـ Slack threads ممكن يبقوا أداة واحدة search_resource والـ resource نوعه parameter [cs146s-1001].

python
search_resource(query="project deadline", resource_type="meeting")
search_resource(query="project deadline", resource_type="slack")

8. Beyond: search and execute (code mode) ​

لما عدد الـ servers يكبر جدًا، حتى الأدوات المصممة كويس هتملا الـ context. الفكرة التانية في المحاضرة: meta MCP server بين الموديل وكل الـ servers، بيعرض أداتين بس: search بيلاقي الـ servers والأدوات والتعريفات المناسبة، وexecute بينفذ العملية بكود متولّد [cs146s-1001]. والواجهة دي مش فارق معاها عندك كام server، لأن أي عدد ممكن يتعمله index للبحث. والمصطلح اللي المحاضر قال افتكره: code mode، يعني توليد الـ tool calls وطلبات الـ servers على شكل كود [cs146s-1001].

المثال: "Find a Jira ticket and update it with information from Google Drive" [cs146s-1001]:

  1. Search: الموديل بيكتب كود يدوّر في الأدوات المتاحة ويفلترها. في المثال الفلترة كانت lexical: الكود بيدوّر على كلمات "jira" و"drive" بـ includes، وممكن تبقى semantic [cs146s-1001].
  2. Execute: لو البحث رجّع أدوات للبحث في Jira بـ JQL، وقراية محتوى Drive، وتحديث ticket، الموديل بيكتب كود تاني يربطهم ببعض. الكود ده بيتنفذ كـ process، غالبًا في VM، مش جوه الموديل، والموديل ماحمّلش الأدوات كلها في الـ context أبدًا [cs146s-1001].

الفكرة في الأصل من Cloudflare: حوّل أدوات الـ MCP لـ TypeScript API، وخلي الموديل يكتب كود بينادي الـ API ده، والكود بيتنفذ في sandbox آمن [varda2025]. وتصميم الـ search/execute ومثال Jira وDrive نفسه موجودين في مقال Cloudflare عن الـ enterprise MCP [goldberg2026].

9. Reading "90%" critically ​

الـ slide بتقول "90+% token reduction"، والمحاضر قالها كده: "Some studies of this technique report more than 90% token reduction" [cs146s-1001]. الأرقام الحقيقية في المصادر:

  • Anthropic: في مثال واحد (نسخ transcript اجتماع من Google Drive لـ Salesforce)، الـ tokens نزلت من 150,000 لـ 2,000، يعني 98.7%، لأن الـ agent بيستكشف الأدوات كملفات ويحمّل اللي محتاجه بس [jones2025].
  • Cloudflare: 52 أداة كانوا بياخدوا حوالي 9,400 token، وبقوا أداتين portal بحوالي 600 token، يعني 94% [goldberg2026].
  • Cloudflare 2025 (المقال الأصلي): مافيهوش رقم للتخفيض [varda2025].

الخلاصة: "أكتر من 90%" حقيقي في الأمثلة دي، مش وعد عام. التخفيض بيعتمد على عدد الأدوات، وطول تعريفاتها، وقد إيه البيانات الوسيطة كانت هتعدّي على الموديل.

Code mode مش بديل لـ MCP؛ هو طبقة فوقه بتكتشف الأدوات وتنسق استخدامها، وممكن تعتمد على MCP تحت.

What the lecture skipped ​

المحاضر عدّى على آخر slides بسرعة لأن الوقت خلص [cs146s-1001]:

  • MCP gateways / server portals: الموظف بيوصل الـ client بتاعه بـ portal واحد يوريه كل الـ servers المسموحله بيها، مع logging مركزي وpolicy enforcement وحماية من تسريب البيانات. المحاضر قال إنه موضوع لوحده وهيرجعله بعدين.
  • Agent skills وAPIs vs MCP vs skills: مؤجلين لمحاضرة الـ skills في الأسبوع التالت. الـ slide بتلخصها: الـ API إنت اللي بتناديه وبتقرر الـ auth والـ retries؛ والـ MCP تعريفات أدوات الموديل بيناديها بطريقة standard؛ والـ skills إجراءات قابلة لإعادة الاستخدام بتعلّم الـ agent يعمل مهمة، وغالبًا بتنسق أكتر من أداة.

Limitations and open questions ​

  • المحاضرة وصفت الـ MCP client بإنه بيحتفظ بـ stateful session لكل server؛ الـ spec الحالي بقى stateless (التفاصيل في صفحة الـ concept) [mcp-spec].
  • سؤال مفتوح: لو code mode بقى الافتراضي، هل وصف الأدوات هيبقى أقل أهمية؟ غالبًا لأ: الـ search لسه بيعتمد على أسماء وأوصاف واضحة عشان يلاقي الأداة الصح.
  • الأمان: تشغيل كود من الموديل محتاج sandbox وصلاحيات محدودة وتحقق قبل العمليات الخطيرة. المحاضرة ذكرت إن التنفيذ بيحصل في VM، بس ماتعمقتش في الضوابط.

Exercises ​

Exercise: Redesign a granular server

API فيه: get_customer(id)، list_orders(customer_id)، get_order(order_id)، refund(order_id, amount). الموديل غالبًا بيتطلب منه "رجّع فلوس آخر طلب للعميل ده". صمم أداة outcome-based واحدة، واكتب الـ signature والـ docstring.

Solution

مثال: refund_latest_order(customer_email: str, reason: str, amount: float | None = None) -> dict مع docstring بيقول إن amount=None معناها المبلغ كامل، وإن الأداة بترفض لو الطلب أقدم من سياسة الاسترجاع. والأهم: الأداة نفسها تطلب تأكيد أو تتأكد من الصلاحية قبل تنفيذ الـ refund.

Exercise: Write errors for a model

اكتب 3 رسائل error لأداة get_document(document_id: str): الـ id مش موجود، والمستخدم مالوش صلاحية، والخدمة مش متاحة مؤقتًا. كل رسالة لازم تقول للموديل يعمل إيه بعدها.

Solution

DocumentNotFoundError: no document with id 'abc'; call search_documents to find valid ids.PermissionDeniedError: the current user cannot read document 'abc'; do not retry, tell the user.ServiceUnavailableError: document service timed out; retry once after a few seconds.

Exercise: Threat-model code mode

الموديل في code mode بيكتب كود بيتنفذ في sandbox ومعاه صلاحيات على Jira وDrive. اكتب 4 مخاطر و4 ضوابط.

Solution

مخاطر: كود بيمسح أو يعدّل بيانات من غير قصد؛ تسريب بيانات لبرا (network)؛ prompt injection من محتوى مستند بيخلي الكود يعمل حاجة تانية؛ loop أو كود تقيل بيستهلك موارد. ضوابط: صلاحيات read-only افتراضيًا وتأكيد قبل الكتابة؛ منع الـ network إلا للـ servers المسموحة؛ معاملة محتوى المستندات كبيانات مش تعليمات؛ timeouts وحدود موارد وlogging لكل تنفيذ.

Review questions ​

  1. ليه الـ mapping واحد لواحد بين endpoints وأدوات فشل في الأيام الأولى؟
  2. اشرح "design for outcomes not operations" بمثال من شغلك.
  3. ليه نوع الـ exception بيفرق مع الموديل؟
  4. إزاي code mode بيقلل الـ tokens؟ اذكر مصدرين للتوفير.
  5. ليه "90% token reduction" محتاج سياق قبل ما تصدقه؟
