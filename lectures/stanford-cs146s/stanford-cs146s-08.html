Overview ​

الأسبوع السادس في CS146S عنوانه "Agentic Code Review"، والمواضيع اللي في الـ syllabus تلاتة: الـ AI review بيمسك إيه كويس وبيفوّت إيه، والـ architectures والـ custom rules للمراجعة، وإزاي الـ AI review يدخل في الـ PR workflow بتاع الفريق [cs146s2026]. المحاضرة دي (التلات 2026-10-27) هي النص النظري، والخميس كان guest lecture لـ Silas Alberti من Cognition [cs146s2026] (مش متغطي هنا).

مافيش transcript منشور للمحاضرة دي، فالصفحة دي بتنقل بس اللي على الـ slides. أي شرح زيادة مكتوب على إنه شرح، مش كلام المحاضر.

Not the same as the notes file

الـ study notes اللي اسمها AI wrote the code.md بتشرح إزاي إنت تراجع شغل agent جوه Claude Code (/diff، /code-review، /rewind). الكلام ده مش من المحاضرة دي، وغالبًا من كورس تاني. اتحقق من وثائق Claude Code واتحط في Agent Code Review. المحاضرة هنا عن الصورة الأكبر: الـ review في فريق بيكتب أغلب كوده بالـ agents.

Learning objectives ​

  • تشرح ليه الـ code review من أعلى الأنشطة قيمة في الفريق، مش بس عشان الـ bugs.
  • تشرح ليه الـ review بقى الـ bottleneck لما الـ agents بقوا يكتبوا الكود.
  • توصف سلم النضج (Stage 0 لـ Stage 2) وتعرف كل مرحلة ناقصها إيه.
  • تصمم reviewer بالـ agents: تنوع الموديل، والـ context، والتحقق، وتوزيع الموديلات حسب التكلفة.
  • تعرف إزاي تقيّم reviewer قبل ما تثق فيه.

Prerequisites ​

  • Advanced Prompting and Context Engineering for Complex Codebases: هناك المحاضر فرّق بين اختبار السلوك والـ code review، وعرض review skill.
  • Subagents: الـ multi-agent review مبني عليهم.

Key ideas ​

1. Why code review ​

الـ slides بتبدأ بجملة: الـ software code review "one of the highest leverage activities" عشان تبقى مهندس أحسن وتحسّن جودة كود الفريق. وليه سببين: إنك تكتشف وتصلح bugs، وإن الفريق يبني shared mental model [cs146s-1027].

والـ review بيمسك خمس حاجات [cs146s-1027]:

  • logic and correctness errors
  • readability and maintainability
  • performance
  • security
  • best practices، أو الـ "tribal knowledge" بتاعة الفريق

وslide تانية بتنقل عن Blake Smith (من قراءات الأسبوع) إن الـ review بيساعد الفريق يحدّث فهمه للنظام وهو بيتغير، وبيتأكد إن التغيير بيحل المشكلة فعلًا، وبيفتح نقاش عن نقط قوة وضعف الـ design، وبيمسك الـ bugs قبل الـ production، وبيحافظ على consistency في الستايل والتنظيم [cs146s-1027].

My reading: الأسباب الاجتماعية دي (mental model مشترك، ونقاش الـ design) هي اللي بتضيع لو الـ review بقى agent بيبعت findings وخلاص. الـ agent ممكن يمسك الـ bug، بس مش هيخلي الفريق يفهم النظام أحسن.

2. Review is the new bottleneck ​

الفكرة المركزية: "Code review is the new bottleneck"، لأنه ماواكبش سرعة توليد الكود [cs146s-1027]. لما كل مهندس بقى معاه agent بيكتب features في ساعة، كمية الـ diffs اللي محتاجة مراجعة زادت أضعاف، وعدد البشر اللي بيراجعوا زي ما هو.

3. The maturity ladder ​

الـ slides بتوصف تلات مراحل [cs146s-1027]:

StageWhat it isLimitation (from the slides)
0human reviews everything"Impossible to scale"
1single agent reviewأحسن، خصوصًا مع auto-fix loop، بس "still leaves gains on the table"
2multi-agent risk-tiered review، فيه self-improvementالـ engineering standards متخزنة في skill knowledge base؛ وده الـ best practice اللي شركات كتير بتتجه ليه

والـ slide دي بتشاور على post لـ Addy Osmani عن layered code review وhuman oversight حسب الـ risk، وهو من قراءات الأسبوع [cs146s-1027; cs146s2026].

كلمة "risk-tiered" معناها (شرح، مش من الـ slide) إن مش كل PR بياخد نفس المعاملة: تغيير في نص صفحة مايحتاجش نفس مستوى المراجعة اللي محتاجه تغيير في الـ auth. الـ agents بتراجع كله، والبشر بيركزوا على اللي الـ risk بتاعه عالي.

4. Multi-agent review architecture ​

الشكل اللي الـ slides بتعرضه: الـ pull request بيروح لـ agents منفصلة، كل واحد متخصص في جانب (security، architecture، code quality، performance)، وبعدين "aggregate judge" بيجمّع [cs146s-1027]. والمثال المذكور من Cloudflare ومعاه slide عن الـ security review agent بتاعهم [cs146s-1027].

ليه agents منفصلة بدل agent واحد بـ prompt طويل؟ (شرح) كل reviewer بياخد context مركّز على جانب واحد، فمايتشتتش، وكل واحد ممكن يتظبط ويتقيّم لوحده. والـ judge بيشيل التكرار ويرتب الأولويات، عشان البني آدم يشوف عدد معقول من المشاكل الحقيقية مش حيطة من الملاحظات. ونفس فكرة "agents متخصصة وواحد بيجمّع" اتقالت في محاضرة RePPIT كوصف لاللي الفرق بتعمله فعلًا (الأسبوع التاني).

5. Designing an agentic reviewer ​

الـ slides فيها اتنين بعنوان "Design of an agentic code reviewer"، وأولهم بيشاور على مقال Greptile عن بناء code review agent (من قراءات الأسبوع). المبادئ اللي فيهم [cs146s-1027]:

  • Diversify the model: استخدم موديل للمراجعة غير اللي ولّد الكود.
  • Model inverter: مصطلح مذكور على الـ slide من غير شرح، ومش واضح معناه بالظبط من غير الـ transcript.
  • Thoughtful context: اختار الـ context اللي الـ reviewer بيشوفه بعناية.
  • Verify: شغّل dev container عشان تختبر code flows مختلفة، بدل ما تكتفي بقراية الكود.
  • Cost efficiency: اختار الموديل حسب صعوبة المهمة:
TaskModel (from the slides)
Code contextcheap/fast model
Browser usesmaller/medium model, higher reasoning
Deep bug analysisfrontier model

ليه "diversify the model" مهمة؟ (شرح) الموديل اللي كتب الكود عنده نفس نقط العمى وهو بيراجع. ده نفس منطق المراجعة في context نضيف، بس خطوة أبعد: مش بس تاريخ مختلف، موديل مختلف كمان.

6. Evaluating the reviewer ​

إزاي تعرف إن الـ reviewer كويس؟ الـ slides بتقترح مصدرين للـ evaluation data [cs146s-1027]:

  • Historical PRs with known bugs: PRs قديمة عارف إن فيها bugs. هل الـ reviewer مسكها؟
  • Detected incidents with reverts: تغييرات اتعملها revert بعد incident. هل كان هيمنعها؟

(شرح) الميزة إن الـ ground truth موجود عندك في الـ git history، مش محتاج تعمل labels من الصفر. والتقييم لازم يقيس الاتجاهين: الـ bugs اللي اتمسكت، والـ false positives اللي بتضيع وقت الفريق.

Technical example ​

مثال صغير على Stage 1 على جهازك: Claude Code فيه /code-review اللي بيراجع التغييرات على الـ branch بتاعك في subagent ليه context خاص بيه، و/code-review 1234 بيراجع PR بالرقم [cc-code-review]. والـ effort level بيعمل نفس الموازنة اللي في الـ slides بين التغطية والدقة: low بيبلّغ بس عن اللي واثق منه، ومن medium لـ max بيوسّع [cc-code-review].

text
/code-review low                  # fewer, higher-confidence findings
/code-review high main...feature  # broader review of one branch against another
/code-review --fix                # also apply the findings (still through your permission mode)

ولتقريب الـ evaluation في §6: اختار 5 commits من الـ history اتعملهم revert، وشغّل الـ review على كل واحد (/code-review abc1234^..abc1234)، وشوف كام مرة الـ finding الأساسي كان هو سبب الـ revert.

Limitations and open questions ​

  • مافيش transcript، فمانعرفش المحاضر قال إيه حوالين كل slide. مثلًا "model inverter" مش مشروح، وأمثلة Cloudflare وAugment Code (Cosmos) متشاور عليها بس.
  • الـ maturity ladder وصف لاتجاه الصناعة كما يراه المحاضر، مش نتيجة دراسة.
  • سؤال مفتوح: لو الـ agents بقت تراجع أغلب الكود، إزاي الفريق يحافظ على الـ shared mental model اللي الـ slides نفسها بتعتبره سبب أساسي للـ review؟
  • سؤال مفتوح: الـ "self-improvement" في Stage 2 بيتعمل إزاي عمليًا؟ الـ slides بتذكر knowledge base من الـ standards في skill، بس مش بتشرح الـ loop.

Exercises ​

Exercise: Place your team on the ladder

فريق فيه 4 مهندسين، كل واحد بيستخدم coding agent، والـ PRs بتستنى review من 2 seniors بس. فين الفريق ده على السلم، وإيه أول تغيير تقترحه؟

Solution

Stage 0: البشر بيراجعوا كل حاجة، والـ seniors هما الـ bottleneck. أول خطوة واقعية Stage 1: agent review على كل PR قبل الـ seniors، عشان يمسك المشاكل الواضحة. وبعدها risk tiers: PRs قليلة الخطورة تعدّي بالـ agent ومراجعة سريعة، والحساسة تاخد وقت الـ seniors.

Exercise: Route the models

عندك reviewer فيه تلات مراحل: يجمع context عن الملفات المتأثرة، يفتح الـ app في browser ويجرب الـ flow، ويحلل bug معقد في الـ concurrency. أنهي موديل لكل مرحلة، حسب الـ slides؟

Solution

جمع الـ context: cheap/fast. الـ browser: smaller/medium بـ reasoning أعلى. تحليل الـ bug: frontier [cs146s-1027]. الفكرة إن مش كل خطوة محتاجة أغلى موديل.

Exercise: Build an evaluation set

اقترح طريقة تعمل بيها evaluation set لـ reviewer من repo إنت شغال عليه، من غير ما تكتب labels بإيدك.

Solution

دوّر في الـ git history على commits اتعملها revert، أو على fixes بتشاور على commit سبّب bug. كل commit سبّب مشكلة هو test case: شغّل الـ reviewer على التغيير الأصلي، وشوف هل مسك المشكلة. ده المصدرين اللي في الـ slides: historical PRs with known bugs، وincidents with reverts [cs146s-1027].

Review questions ​

  1. ليه الـ code review بقى bottleneck بعد الـ coding agents؟
  2. إيه الفرق بين Stage 1 وStage 2، وإيه اللي Stage 1 بيفوّته؟
  3. ليه تقسيم المراجعة على agents متخصصة ممكن يكون أحسن من agent واحد؟
  4. ليه تستخدم موديل للمراجعة غير اللي كتب الكود؟
  5. إزاي تقيّم reviewer باستخدام الـ git history؟
