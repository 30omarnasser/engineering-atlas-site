Overview ​

في المحاضرة اللي فاتت شفنا إزاي MCP بيوصّل الـ agent بأنظمة برا. المحاضرة دي بتجاوب على السؤال اللي بعده: لو الـ agent بقى عنده الأدوات، مين يعلّمه يستخدمها بالترتيب الصح في شغل متكرر؟ الإجابة هي الـ skills. الـ slide الأولى بعد اللوجستيات بتقول السبب في سطرين: MCP كويس للـ 3rd-party integrations، والـ LLMs "amazingly good" في إنها تمشي ورا إجراءات طويلة، وعرض القدرة دي جزء مهم من أي harness [cs146s-1006, slide 4].

What this page can and cannot attribute to the lecture

المحاضرة دي مالهاش transcript منشور، والمتاح هو الـ 15 slide بس. فكل نقطة منسوبة للمحاضرة هنا موجودة على slide. الـ demos (slides 6 و10 و11) حصلت في المحاضرة بس محتواها مش معروف، فمش موصوفة هنا. وأي مثال في الصفحة مش عليه citation هو شرح توضيحي، مش كلام المحاضر.

Learning objectives ​

  • تشرح ليه الـ skills موجودة جنب MCP، ومش بديل ليه.
  • تعرف شكل الـ skill: folder فيه SKILL.md وملفات اختيارية، وبيتحمل إمتى.
  • تفرّق بين الأربع فئات اللي المحاضرة عرضتها، وتدّي مثال حقيقي لكل واحدة.
  • تطبّق الـ best practices: scope ضيق، وtrigger phrases واضحة، وprogressive disclosure، وverification skill.
  • تفرّق بين API وMCP وskill من حيث مين بيستخدمها وإيه دورها.

Prerequisites ​

  • MCP, Tool Calling, and Beyond: الـ skills بتبني فوق الأدوات.
  • Advanced Prompting and Context Engineering for Complex Codebases: RePPIT، اللي بيرجع هنا كـ skills.
  • الشرح الكامل للمفهوم (الـ format، والـ triggering، والتقييم) في صفحة Agent Skills.

Key ideas ​

1. Why skills: procedures, not just connections ​

الـ slide بتحط الاتنين جنب بعض [cs146s-1006, slide 4]:

  • MCP كويس للـ 3rd-party integrations: بيدّي الـ agent قدرة يوصل لخدمة.
  • الـ LLMs شاطرة جدًا في إنها تتبع إجراءات طويلة، والـ harness محتاج طريقة يعرض بيها الإجراءات دي.

يعني أداة jira_search بتخلي الـ agent يقدر يدوّر، بس مابتقولوش إزاي يعمل تقرير أسبوعي محترم: يجيب إيه، ويصنّف إزاي، ويتأكد من إيه قبل ما يقول "خلصت". ده شغل الـ skill. (المثال ده توضيحي، مش من الـ slides.)

2. What a skill is ​

الـ slide بتعرّف الـ agent skills كـ "A standard for dynamically loaded agent capabilities"، وبتوصفها بتلات حاجات: domain-specific، وبتجمع code وprompts، والـ agent بيحمّلها لما يحتاجها. والـ use cases اللي عليها: كتابة مستندات، وعمل PowerPoint، وتحليل بيانات. والتشبيه اللي في الآخر: "Like scripts for agents" [cs146s-1006, slide 5].

الـ "standard" هنا هو الـ Agent Skills format المفتوح. الـ skill عبارة عن folder فيه على الأقل ملف SKILL.md: فوق frontmatter فيه name وdescription (الاتنين required)، وتحته تعليمات Markdown؛ وممكن الـ folder يكون فيه scripts/ وreferences/ وassets/ [agentskills-spec].

markdown
---
name: weekly-report
description: Build the weekly status report from the issue tracker. Use when the user asks
  for a weekly report, a status update, or a summary of this week's issues.
---

# Weekly report

1. Fetch issues updated in the last 7 days.
2. Group them by status; list blockers first.
3. Do not mark an issue done because a comment says so; check its status field.
4. For the output format, read references/report-template.md.

(الـ skill ده مثال توضيحي.) Claude Code بيمشي على نفس الـ standard: personal skills في ~/.claude/skills/<name>/SKILL.md، وproject skills في .claude/skills/<name>/SKILL.md، وتقدر تشغّل أي skill بإيدك بـ /skill-name أو تسيب Claude يحمّله لوحده لما يكون relevant [cc-skills].

3. Progressive disclosure ​

من الـ best practices على الـ slides: "Progressive disclosure: reference specific files as needed with additional context" [cs146s-1006, slide 13]. والـ spec بيشرح الفكرة على تلات مستويات: الـ name والـ description بس بيتحملوا في الأول (حوالي 100 token لكل skill)، والـ SKILL.md كله بيتحمل لما الـ skill يتفعّل، والملفات التانية بتتحمل لما خطوة معينة تحتاجها [agentskills-spec].

ده نفس الكلام اللي اتقال في محاضرة 9/24: MCP بيحط كل تعريفات الأدوات في كل request، والـ skill بيظهر منه metadata صغيرة لحد ما يبقى relevant (The Anatomy of a Modern Coding Agent). التفاصيل والرسمة في صفحة Agent Skills.

Progressive disclosure is not compaction

الـ progressive disclosure بيمنع معلومة تدخل الـ context من غير لازمة. الـ compaction بيلخّص معلومة دخلت خلاص. الاتنين بيوفروا context، بس في مرحلتين مختلفتين.

Code understanding and planning ​

RePPIT skills: الـ workflow بتاع الأسبوع التاني (Research، Propose، Plan، Implement، Test) ممكن كل مرحلة فيه تبقى skill، بدل ما تفتكر الخطوات كل مرة. الشرح الكامل لـ RePPIT في محاضرة 9/29. (تقسيمه لـ skills منفصلة اقتراح توضيحي؛ الـ slide بتقول "RePPIT skills" بس.)

grill-me وgrill-with-docs: من الـ repo بتاع Matt Pocock، واتنين من القراءات المقترحة للأسبوع. الـ grill-me بيخلي الـ agent "يستجوبك" عن خطة أو تصميم لحد ما كل فرع في شجرة القرارات يتحسم. والـ grill-with-docs نفس الفكرة، بس وهو بيسألك بيبني الـ domain model بتاع المشروع: بيظبط المصطلحات، وبيحدّث GLOSSARY.md والـ ADRs أثناء الجلسة [mattpocock-skills]. ودي الترجمة العملية لجملة الـ slide: "Develop a mental model of a task" [cs146s-1006, slide 8].

Verification ​

الـ slide بتذكر create-verification-skill بس [cs146s-1006, slide 9]. الـ skill ده موجود في pstack (قراءة الأسبوع)، وفكرته إنه مابيتحققش هو، ده بيولّد skill تاني خاص بالمشروع (verify-<app>) يشغّل الـ app زي ما المستخدم بيستخدمه ويجمع دليل. الـ skill المتولّد فيه أقسام: Launch، وDoctor (فحص read-only إن النسخة شغالة صح)، وDrive، وEvidence، وCleanup. وآخر خطوة إنه يشغّل الـ skill المتولّد مرة كاملة قبل ما يسلّمه، لأن "A generated skill that was never executed is a draft, not a deliverable" [pstack].

الفرق بين testing وverification (شرح توضيحي، مش من الـ slides): الـ tests بتجاوب "الـ tests اللي موجودة عدّت؟". الـ verification بتجاوب "الحاجة اللي اتطلبت اتعملت فعلًا؟"، وده ممكن يشمل إنك تشغّل الـ app وتجرب الـ feature من ناحية المستخدم، وتتأكد من الـ scope. الـ test suite ممكن تعدّي والـ feature نفسها بايظة لو مفيش test بيغطيها.

Code style ​

الـ skill هنا بيكتب best practices على مستوى الكود، والـ slide بتقول إنها مفيدة لـ code review agents [cs146s-1006, slide 10]. يعني بدل ما الـ reviewer agent يحكم بذوقه العام، بيحكم بقواعد الفريق المكتوبة.

Miscellaneous: browser parsing ​

المثال هو browse.sh [cs146s-1006, slide 11]: CLI من Browserbase بيدّي الـ agent أوامر للتحكم في المتصفح (click، type، screenshot، network)، ومعاه catalog مفتوح من الـ "web skills" لكل موقع (browse skills add <site>). الموقع بيقول إن الـ selectors والـ XHR requests المقترحة بتقلل تكلفة الـ tokens 50 مرة؛ ده رقم من الـ vendor نفسه ومش متقاس هنا [browse-sh].

5. Best practices for writing skills ​

الـ slides فيها 2 slides للـ best practices [cs146s-1006, slides 12-13]:

  • Keep scope focused: "One skill, one clearly defined task". الـ skill اللي بيعمل كل حاجة صعب يتفعّل في الوقت الصح.
  • Maintain your own collection تقدر تنقلها بين المشاريع. والـ slide بتقتبس poteto (صاحب pstack): "Chefs bring their own knives between kitchens".
  • Mine your own transcripts: الـ skills هي processes مكتوبة Markdown، فارجع لمحادثاتك وشوف إنت تدخلت أو صححت للـ agent فين. كل تصحيح بيتكرر مرشح يبقى skill.
  • Don't reinvent the wheel: ماتصرفش tokens ووقت على حاجة موجودة. و"Equip agents with a CLI tool and wrap the boilerplate in a skill".
  • Include trigger situations and request phrases: اكتب في الـ skill المواقف والجمل اللي المفروض تشغّله.
  • Progressive disclosure: ارجع لملفات معينة وقت الحاجة بس.
  • Modularize and compose skills.
  • Maintain a verification skill عشان الـ agent يراجع شغله بنفسه، وده بيعمل improvement loop.

The CLI part of the week ​

الـ syllabus بيحط "Working effectively from the CLI" ضمن موضوعات الأسبوع، والـ slides بتربطه بالـ skills في جملة واحدة: ادّي الـ agent أداة CLI، ولف الشغل المتكرر حواليها في skill [cs146s-1006, slide 12]. My reading: الـ CLI بيدّي سلوك deterministic بكود حقيقي، والـ skill بيقول للـ agent إمتى وإزاي يستخدمه. وده مكمّل لمبدأ "أدوات أقل وأقوى" من محاضرة 9/24: أداة زي Bash أو CLI واحد قوي، مع skill بيشرح استخدامه، بدل عشرات الأدوات المتخصصة. وbrowse.sh مثال على النمط ده بالظبط.

Limitations and open questions ​

  • من غير transcript، مانعرفش المحاضر قال إيه في الـ demos، ولا شرح الـ code-style skill بمثال إيه.
  • الـ skill مش ضمان: الـ description ممكن مايشغّلوش، أو يشغّله في وقت غلط. وعشان كده التقييم (should-trigger وshould-not-trigger، ومقارنة with/without skill) مهم؛ التفاصيل في Agent Skills.
  • سؤال مفتوح: إمتى قاعدة تتحط في AGENTS.md، وإمتى في skill، وإمتى في hook؟ (Claude Code docs بتقول: لو قاعدة لازم تتنفذ كل مرة، الـ hook أضمن [cc-skills].)

Exercises ​

Exercise: Mine one correction

ارجع لآخر 5 محادثات مع coding agent. اكتب كل مرة صححت فيها حاجة. اختار تصحيح اتكرر مرتين على الأقل، واكتبه كـ SKILL.md: name، وdescription فيه جمل الـ trigger، و5 خطوات بالكتير، وشرط نجاح واحد يتقاس.

Solution

مثال: "مابتشغّلش الـ tests قبل ما تقول خلصت". الـ description: "Use before saying a coding task is done, fixed, or ready for review." الخطوات: حدد الـ tests المتعلقة، شغّلها، اقرا النتيجة الفعلية، راجع الملفات اللي اتغيرت، بلّغ بالفشل بصراحة. شرط النجاح: التقرير فيه أمر الـ test اللي اتشغّل ونتيجته.

Exercise: Classify into the four categories

صنّف دول على الفئات الأربعة: (1) skill بيسألك أسئلة عن feature قبل ما يكتب كود. (2) skill بيشغّل الـ app في متصفح ويصوّر الـ screen بعد كل تعديل. (3) skill فيه قواعد التسمية والـ error handling في الفريق. (4) skill بيجيب أسعار من موقع مالوش API.

Solution

(1) code understanding and planning (زي grill-me). (2) verification. (3) code style. (4) miscellaneous / browser parsing (زي browse.sh).

Exercise: API, MCP, or skill?

لكل جملة قول API ولا MCP ولا skill: (1) "الـ agent محتاج يقرا الـ calendar بتاعي". (2) "عايز الـ agent يعمل release notes بنفس الشكل كل مرة". (3) "الـ backend بتاعي محتاج يبعت SMS".

Solution

(1) MCP server للـ calendar (أو CLI). (2) skill: إجراء متكرر بشكل output ثابت. (3) API: كود إنت كاتبه بينادي الخدمة، والـ agent مش طرف.

Review questions ​

  1. ليه المحاضر بيقول إن MCP لوحده مش كفاية؟
  2. إيه التلات مستويات في الـ progressive disclosure، وكل مستوى بيتحمل إمتى؟
  3. create-verification-skill بيولّد إيه، وليه بيشغّل الناتج قبل ما يسلّمه؟
  4. إزاي "mine your own transcripts" بيساعدك تختار الـ skills اللي تكتبها؟
  5. اشرح الفرق بين API وMCP وskill بمثال واحد فيه التلاتة.
