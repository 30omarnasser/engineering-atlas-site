Definition ​

Definition: Agent code review

الـ agent code review هو إنك تتحقق من التغيير كله اللي عمله coding agent قبل ما تقبله: إيه اللي اتغير فعلًا، وهل كل تغيير مبرر ومطلوب، وهل الاختبارات لسه بتختبر حاجة. القاعدة اللي بتلخصه: AI wrote the code ≠ AI verified the code. إن الـ agent كتب الكود وقال "كل الاختبارات نجحت" ده ادعاء، مش دليل.

الكلمة المهمة هنا "كله". الملخص اللي الـ agent بيكتبه في الآخر ممكن يكون صح، بس مش لازم يكون كامل: ممكن يذكر الـ feature اللي طلبتها وينسى إنه غيّر config أو شال اختبار. عشان كده المراجعة بتبدأ من الـ diff، مش من الملخص.

Learning objectives ​

  • تشرح ليه ملخص الـ agent مش بديل عن قراية الـ diff.
  • تعدّد أنواع التغييرات اللي محتاجة مراجعة خاصة دايمًا.
  • تشرح ليه المراجعة في context نضيف أحسن من إنك تطلب من نفس الـ session تراجع نفسها، وإيه حدود ده.
  • تفرز نتائج أي review لـ fix now وask why وleave it، وتعرف إن الـ reviewer نفسه ممكن يغلط.
  • تعرف إزاي ترجع تغيير غلط، وإمتى الـ checkpoints مش كفاية ولازم git.

Intuition ​

تخيل مهندس جديد في الفريق قدّم pull request وكتب في الوصف: "ضفت الـ login، وضفت tests، وكله أخضر". إنت مش هتعمل approve من الوصف. هتفتح الـ diff، وهتلاقي مثلًا إنه كمان غيّر DATABASE_URL لقيمة ثابتة عشان يشغّل الـ tests عنده، وعمل skip لاختبار كان بيفشل. الوصف ماكدبش، بس ماقالش كل حاجة.

الـ coding agent بالظبط كده، مع فرق مهم: بيشتغل أسرع بكتير، فبيعمل تغييرات جانبية أكتر في وقت أقل. وكمان لو طلبت منه في نفس المحادثة "راجع شغلك"، هو هيراجع وهو لسه مقتنع بكل القرارات اللي خدها وهو بينفذ. زي ما تطلب من الكاتب يعمل proofreading لمقاله بعد ما خلّصه بدقيقة.

Formal explanation ​

1. Start from the diff, not the summary ​

الـ diff هو الفرق بين الكود قبل وبعد: السطور اللي اتشالت والسطور اللي اتضافت، من غير ما تقرا الملف كله.

diff
--- a/config.py
+++ b/config.py
-DATABASE_URL = os.getenv("DATABASE_URL")
+DATABASE_URL = "sqlite:///test.db"

السطر ده لوحده ممكن يعدّي في ملخص زي "ظبطت إعدادات الاختبار"، بس هو بيكسر الـ production: بدل ما يقرا الـ environment variable، بقى عنوان ثابت.

في Claude Code، الأمر /diff بيعرض التغييرات اللي في الـ working tree، ومنها التعديلات اللي Claude عملها لحد دلوقتي ومعاها أي حاجة إنت لسه ماعملتلهاش commit. وبيقدر يوريك تعديلات كل turn لوحده (T1، T2...). التغييرات بتتقري من git، فالـ diff panel محتاج git repository [cc-diff]. وخلي بالك: الـ turn views جاية من أدوات التعديل بتاعة Claude، فالتغيير اللي حصل عن طريق shell command بيظهر بس في الـ Current view [cc-diff]. ولو مش في Claude Code، git diff بيعمل نفس الشغل.

2. What to always look at ​

تلات أنواع تغييرات تستاهل تقف عندها في أي diff عمله agent:

Red flagExampleWhy it matters
Unrequested changesطلبت login، فلقيت تعديل في الـ database config أو في helper ملوش علاقةمش كل تغيير زيادة غلط، بس لازم تعرف سببه
Weakened testsاختبار اتعمله skip، أو assertion اتبدل بواحد أضعف، أو سطور اتشالت من ملف testأخطر نوع: الـ agent "صلّح" الاختبار بدل ما يصلّح الكود، فالنتيجة خضرا والـ bug موجود
New dependencies and hardcoded valuespackage جديد عشان وظيفة بسيطة، API URL أو secret مكتوب في الكود بدل الـ configمشاكل تشغيل وأمان، ومش بتظهر في الـ tests

النوع التاني هو اللي بيخلي "كل الاختبارات نجحت" جملة ملهاش قيمة لوحدها. السؤال مش "نجحت؟"، السؤال "لسه بتختبر نفس الحاجة؟".

3. Independent review in a clean context ​

الفكرة: اللي كتب الكود مايبقاش هو اللي بيحكم عليه. لما الـ agent يشتغل ساعتين على feature، الـ context بتاعه مليان بالافتراضات والقرارات والمحاولات الفاشلة. لو طلبت منه يراجع في نفس المحادثة، هيبص على الكود من نفس الزاوية اللي كتبه بيها. مراجع جديد مايعرفش التاريخ ده هيبص على الكود زي ما هو.

في Claude Code، الأمر /code-review بيعمل ده: بيراجع التغييرات اللي على الـ branch بتاعك (الـ commits اللي قبل الـ upstream، والتغييرات اللي مش committed) ويدور على correctness bugs [cc-code-review]. وفي terminal session بيشتغل كـ background subagent ليه context window خاص بيه، فمش بيملا المحادثة بتاعتك، والنتايج بتوصلك لما يخلص [cc-code-review]. والمهم إن الـ subagent ده ما بيشوفش تاريخ المحادثة: الـ skill بيشتغل بـ context: fork، ودي معناها subagent جديد بياخد تعليمات الـ skill بس، مش نسخة من المحادثة [cc-skills]. (الاسم مضلل شوية: الـ "fork" هنا مش fork للمحادثة.) وبيتبع CLAUDE.md بتاعك [cc-code-review].

A clean context is not a correct reviewer

الـ context النضيف بيشيل نوع واحد من الانحياز: إن المراجع متأثر بقرارات التنفيذ. مابيضمنش إن المراجعة صح. المراجع ممكن يقول إن function مش بتعمل trim() وهي بتعملها فعلًا قدامك في الكود. أي finding هو ادعاء محتاج يتأكد، زي ملخص الـ agent بالظبط.

4. Coverage versus confidence ​

الـ reviewer دايمًا بيوازن بين حاجتين: يلاقي مشاكل أكتر، ولا يقلل الـ false positives. في /code-review ده بيتحدد بالـ effort level: عند low بيبلّغ بس عن الحاجات اللي واثق منها جدًا، فبتشوف false positives أقل، ومن medium لحد max بيوسّع التغطية [cc-code-review]. ولو ماكتبتش level، بيستخدم آخر level كتبته من low لـ max، حتى من session قديمة [cc-code-review].

LevelUse it when
lowتغيير عادي وعايز أوضح المشاكل بس
high (or above)تغيير كبير أو حساس (auth، migrations، security) ومستعد تفرز ملاحظات أكتر، بعضها غلط

5. Triage the findings ​

النتايج مش أوامر. قسّم كل finding لواحدة من تلاتة (التقسيم ده طريقة عملية للشرح، مش مصطلح رسمي في الـ docs):

  • Fix now: مشكلة حقيقية ومؤثرة. اختبار اتعمله skip، أو API_URL اتغير لـ localhost.
  • Ask why: مش متأكد إنها حقيقية. ارجع للكود وتأكد قبل ما تطلب إصلاح. لو الـ reviewer قال إن الـ email مش بيتعمله trim() والكود فيه value.trim()، يبقى الـ finding غلط.
  • Leave it: حقيقية بس صغيرة ومش مؤثرة دلوقتي، زي لون مكتوب hex بدل CSS variable. سجّلها وكمّل.

بعد الإصلاح، اطلب دليل: الاختبارات تتشغل تاني فعلًا، مش "المفروض تشتغل". ولو الإصلاح نفسه كبير، راجعه تاني قبل الـ commit.

6. Rolling back a bad change ​

لو التغيير كله غلط، Claude Code بيعمل checkpoint قبل كل prompt بتبعته، و/rewind (أو Esc مرتين والـ prompt فاضي) بيفتح قايمة تختار منها نقطة، وبعدين: ترجّع الكود والمحادثة، أو المحادثة بس، أو الكود بس [cc-checkpointing].

بس الـ checkpoints ليها حدود مهمة [cc-checkpointing]:

  • Bash changes: ملف اتغير عن طريق shell commands بس (مش عن طريق أدوات التعديل) مابيترجعش. ده بيشمل حاجات زي ملفات بيعدلها package manager.
  • Subagent edits: تعديلات الـ subagents غالبًا مش جوه الـ checkpoints، ومنها /code-review --fix لما يشتغل في الـ background.
  • Not version control: الـ docs نفسها بتقول إنها للـ recovery السريع جوه الـ session، مش بديل عن git.

يعني اعمل commit قبل أي مهمة كبيرة، وخلي git هو شبكة الأمان الحقيقية.

7. When review is worth the cost ​

مش كل تغيير محتاج review آلي كبير. تعديل نص زرار يكفيه نظرة على الـ diff. إنما auth، أو database migrations، أو تغييرات security، أو features كبيرة، المراجعة المستقلة تستاهل الوقت والـ tokens.

ولما المراجعة تبقى على مستوى فريق، المشكلة بتكبر: كمية الكود اللي بتتكتب بالـ agents أكبر من اللي البشر يقدروا يراجعوه. محاضرة CS146S عن الموضوع بتوصف سلم نضج من "human reviews everything" لـ agent واحد، لـ multi-agent risk-tiered review [cs146s-1027]. التفاصيل في Agentic Code Review.

Diagram ​

الرسمة في القسم الخامس بتلخص الـ workflow كله. والفكرة الأساسية فيها إن فيه نقطتين إنت فيهم اللي بتحكم: قراية الـ diff، والفرز. الـ agent بينفذ والـ reviewer بيقترح، بس القرار عندك.

Limitations and common misconceptions ​

  • "All tests passed, so it works." لو الاختبارات نفسها اتغيرت، النجاح ده مابيقولش حاجة. بص على ملفات الـ tests في الـ diff الأول.
  • "The reviewer agent found nothing, so it's fine." الـ reviewer ممكن يفوّت، وكمان ممكن يغلط في الاتجاه التاني ويبلّغ عن مشاكل مش موجودة.
  • "A fresh context means an unbiased reviewer." بيقلل انحياز واحد (قرارات التنفيذ)، بس الـ reviewer غالبًا نفس الموديل بنفس نقط العمى. المحاضرة بتقترح تنوّع الموديل اللي بيراجع عن اللي بيكتب [cs146s-1027].
  • "/rewind is my undo, I don't need git." الـ checkpoints مابترجعش تغييرات الـ shell commands ولا أغلب تعديلات الـ subagents [cc-checkpointing].
  • تفاصيل الأوامر (/diff، /code-review، الـ effort levels) خاصة بإصدار معين من Claude Code وبتتغير بسرعة. الفكرة نفسها (diff، مراجعة مستقلة، فرز، rollback) بتتطبق على أي agent.

Exercises ​

Exercise: Pick the files to review

طلبت من agent يعمل validation لـ signup form: صيغة الـ email صح، والـ password 8 حروف على الأقل، ورسائل الخطأ تحت الحقول. قال إن كل الاختبارات نجحت، والـ diff فيه 8 ملفات، منهم: SignupForm.tsx، SignupForm.test.tsx (اتشالت منه سطور)، package.json (dependency جديدة)، package-lock.json، config.ts (إعدادات اتغيرت)، وstyles.css. أنهي تلات ملفات تبدأ بيهم؟

Solution

SignupForm.test.tsx لأن الاختبارات ممكن تكون اتضعفت، وpackage.json لأن الـ dependency الجديدة محتاجة سبب، وconfig.ts لأن الإعدادات ممكن تأثر على الـ production. الـ package-lock.json تابع للـ dependency الجديدة، فبتراجعه مع package.json. الدرس: نجاح الـ feature مش معناه إن كل التغييرات اللي جت معاها سليمة.

Exercise: Triage four findings

الـ review رجّع أربع ملاحظات. صنّف كل واحدة fix now أو ask why أو leave it: (1) اختبار "مايبعتش form بـ email فاضي" اتعمله skip، وassertion اتبدل بواحد أضعف. (2) "الـ email مش بيتعمله trim()"، والكود اللي قدامك فيه value.trim(). (3) API_URL اتغير من environment variable لـ http://localhost:3000. (4) لون رسالة الخطأ مكتوب #d32f2f بدل var(--color-danger).

Solution

(1) fix now: الاختبار اتضعف، فالنتيجة الخضرا مابقتش دليل. (2) ask why، وبعد ما تبص هتلاقيه finding غلط: الـ reviewer نفسه غلط. (3) fix now: هيكسر أي بيئة غير جهازك. (4) leave it (أو اصلحه بعدين): مشكلة consistency صغيرة. النقطة الأهم هي (2): ماتنفذش توصيات الـ review بشكل أعمى.

Exercise: Why not the same session

ليه "راجع الكود اللي كتبته" في نفس المحادثة أضعف من /code-review؟ وإيه اللي /code-review برضه مايقدرش يضمنه؟

Solution

في نفس المحادثة، الموديل شايف كل افتراضاته وقراراته القديمة، فبيراجع من نفس الزاوية. /code-review بيشتغل في subagent مابيشوفش تاريخ المحادثة [cc-skills; cc-code-review]. بس مابيضمنش إن النتايج صح: ممكن يفوّت bugs، وممكن يبلّغ عن bugs مش موجودة، فالفرز والتحقق لسه عليك.

Key takeaways

  • ملخص الـ agent ادعاء؛ الـ diff هو الدليل.
  • دايمًا دوّر على: تغييرات ماطلبتهاش، واختبارات اتضعفت، وdependencies أو قيم ثابتة جديدة.
  • افصل اللي بينفذ عن اللي بيراجع: مراجعة في context نضيف.
  • الـ findings محتاجة فرز وتحقق، مش تنفيذ أعمى.
  • الـ checkpoints للـ recovery السريع؛ git هو شبكة الأمان.

Review questions ​

  1. ليه ممكن ملخص الـ agent يكون صح ومع ذلك مضلل؟
  2. ليه الاختبارات اللي اتضعفت أخطر من الاختبارات اللي فشلت؟
  3. إيه الفرق بين low وhigh في /code-review، وإمتى تختار كل واحد؟
  4. إيه أنواع التغييرات اللي /rewind مابيرجعهاش؟
  5. إزاي الـ subagents بتخلي المراجعة المستقلة ممكنة؟ (شوف Subagents.)
