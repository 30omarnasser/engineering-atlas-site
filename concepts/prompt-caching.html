Prompt Caching ​

ReviewedPublishedAI-assisted

Letting the model provider resume from a prompt prefix it processed recently, so a request that starts with the same tools, system prompt, and history costs less and answers faster; any change early in the prompt invalidates everything after it.

Also known as
prefix caching, cache_control, cache-aware prompt design

Definition ​

Definition: Prompt Caching

الـ model مابيفتكرش حاجة بين الـ requests، فالـ agent بيبعت الـ prompt كله في كل مرة. الـ prompt caching بيخلي الـ provider "resume from specific prefixes in your prompts" [anthropic-prompt-caching, intro]: لو بداية الـ request مطابقة بالظبط لبداية request قريب اتعمله cache، الجزء ده بيتحسب أرخص وبيتعالج أسرع. أي تغيير في البداية بيلغي الـ cache لكل اللي بعده.

Learning objectives ​

  • تشرح ليه ترتيب الـ prompt (الثابت أولًا والمتغير آخرًا) بيحدد إذا كان فيه cache hit.
  • تحسب تكلفة سلسلة requests بالـ cache ومن غيره من أسعار منشورة.
  • تعرف إيه اللي بيكسر الـ cache في agent: تغيير الأدوات، تغيير الـ system prompt، الـ compaction.
  • تشرح أفكار المحاضرة: "Treat a cache miss like a bug"، وتسخين الـ cache، والتلخيص وهو لسه warm.

Intuition ​

تخيل إنك بتبعت لزميل نفس الـ 90 صفحة كل شوية، وتضيف في الآخر سؤال جديد. لو هو لسه فاكر الـ 90 صفحة من آخر مرة، مش محتاج يقراهم تاني: يقرا السؤال بس. بس لو غيّرت ولو كلمة في الصفحة الأولى، مش هيقدر يثق إن اللي بعدها زي ما هو، فهيقرا من الأول.

ده بالظبط الـ prefix caching: الـ cache مربوط بـ بداية الـ prompt كلها لحد نقطة معينة، مش بأجزاء متفرقة. وعشان كده المحاضرة بتقول: الثابت أولًا، والجديد آخرًا [cs146s-1008, slide 33].

Formal explanation ​

The prefix hierarchy ​

في Claude API الـ cache بيغطي "the entire prompt: tools, system, and messages (in that order)"، لحد البلوك اللي عليه cache_control [anthropic-prompt-caching, How prompt caching works]. والتغيير في أي مستوى "invalidate that level and all subsequent levels" [anthropic-prompt-caching, What invalidates the cache]. يعني:

What changesToolsSystemMessages
Tool definitions (اسم، وصف، parameters)✘✘✘
System prompt✓✘✘
رسالة جديدة في الآخر✓✓الجديد بس

والـ write بيحصل عند الـ breakpoint بس، والـ read بيدوّر لورا لحد 20 block على entry اتكتب قبل كده؛ عشان كده لو حطيت الـ breakpoint على بلوك بيتغير كل request (زي timestamp)، عمرك ما هتاخد hit [anthropic-prompt-caching, How automatic prefix checking works].

نفس الفكرة في Claude Code: الـ request مترتب طبقات، system prompt (فيه الأدوات)، وبعدين project context (CLAUDE.md والـ memory)، وبعدين المحادثة؛ "A change to the system prompt invalidates everything" [cc-prompt-caching, How the cache is organized].

Lifetime and price ​

  • الـ cache بيعيش 5 دقايق by default، "refreshed for no additional cost each time the cached content is used"، وفيه option ساعة بسعر أعلى. والمدة بتتحسب من بداية الـ request مش من آخر الرد [anthropic-prompt-caching, How prompt caching works].
  • الـ cache write بـ 1.25 × سعر الـ input (5 دقايق) أو 2 × (ساعة)، والـ read بـ 0.1 × (وفيه موديلات أرخص من كده) [anthropic-prompt-caching, Pricing].
  • فيه حد أدنى للطول بيختلف حسب الموديل (من 1,024 لـ 4,096 token)؛ الأقصر مابيتعملوش cache ومن غير error [anthropic-prompt-caching, Cache limitations].

A worked example with real prices ​

بأسعار Claude Haiku 4.5 المنشورة يوم الوصول: input بـ $1 / MTok، والـ 5-minute cache write بـ $1.25 / MTok، والـ cache read بـ $0.10 / MTok [anthropic-prompt-caching, Pricing]. agent بيبعت 10 requests ورا بعض (كل واحد في خلال 5 دقايق من اللي قبله)، كل request فيه 90,000 token ثابتين (أدوات وsystem prompt ومستندات) و10,000 token بيتغيروا، والـ breakpoint في آخر الجزء الثابت:

Request 1Requests 2-10 (each)Total for 10
No caching100k × $1 = $0.100$0.100$1.000
With caching90k write × $1.25 + 10k × $1 = $0.122590k read × $0.10 + 10k × $1 = $0.019$0.2935

أول request أغلى بالـ cache ($0.1225 بدل $0.100) لأنك بتدفع write. من التاني بيبقى أرخص بكتير، وبعد 10 requests التوفير حوالي 71%. ولو الـ requests بعدت عن بعض أكتر من 5 دقايق، كل واحد بيدفع write من جديد وبيبقى أغلى من غير cache خالص. (الأرقام دي حساب من الأسعار المنشورة، مش قياس؛ وسعر الـ output مش داخل.)

Cache-aware agent design (from the lecture) ​

المحاضرة بتعامل الـ cache كجزء من الـ architecture مش optimization جانبي:

  • ترتيب ثابت [cs146s-1008, slide 33]: tool definitions، وsystem prompt (فيه snapshot من الـ memory والـ routines)، وأول رسالة، والـ history، وفي الآخر الرسالة الجديدة (الوقت، وملاحظات عن اللي اتغير، ورسالتك).
  • "Treat a cache miss like a bug" [cs146s-1008, slide 35]: لحد الملخص الجاي، الأدوات والـ system prompt وأول رسالة يفضلوا زي ما هما بالظبط؛ deploy غيّر وصف أداة؟ المحادثات الشغالة تاخد note بدل النص الجديد؛ الأدوات مابتتضافش ولا بتتشال لـ turn واحد (الأداة المش متاحة ترجّع error)؛ كل حاجة بتتبني بترتيب ثابت ومتسورتة؛ وكل section ليه hash لوحده عشان تعرف بالظبط إيه اللي اتغير.
  • تسخين الـ cache [cs146s-1008, slide 35]: لما تفتح الشات أو تبدأ تكتب، الـ server بيجهّز الـ prompt بدري. والـ API نفسها فيها ده: request بـ max_tokens: 0 بيكتب الـ cache ويرجع من غير output، وبيتحسب عليه write لو الـ prefix مش موجود [anthropic-prompt-caching, Pre-warming the cache].
  • لخّص وإنت مش موجود [cs146s-1008, slide 36]: turn كبير خلص والـ prompt عدّى 100,000 token؛ بعد حوالي 10 دقايق، والـ cache لسه warm، بيكتب ملخص بنفس بداية الـ prompt فيستفيد من الـ cache؛ والخطوة دي بتتلغي لو فيه شغل background هيصحّي الـ agent كده كده.

والـ compaction نفسه بيكسر طبقة المحادثة "by design"، لأن الـ history الجديد أقصر ومابيشاركش prefix مع القديم [cc-prompt-caching, Compacting the conversation]. عشان كده توقيته مهم، وده موضوع Context Compaction.

Tools and the cache ​

بما إن الأدوات في أول الـ prompt، أي تغيير فيها بيلغي كل حاجة. Claude Code مع الـ tool search بيحتفظ بقايمة الأدوات من أول request طول المحادثة، فـ MCP server بيتوصل أو بيقع في النص مابيبوظش اللي اتعمله cache؛ من غير tool search، إضافة definition بتلغي الـ cache [cc-prompt-caching, Connecting or removing an MCP server]. وده نفس منطق قاعدة المحاضرة: الأداة المش متاحة ترجّع error واضح بدل ما تختفي [cs146s-1008, slide 30]. وفيه tradeoff: تحميل تفاصيل الأدوات وقت الحاجة [cs146s-1008, slide 26] بيوفر context، بس لو آلية الاكتشاف ضعيفة الـ agent ممكن مايلاقيش الأداة الصح (شرح من عندي).

Technical example ​

الـ hash لكل section (فكرة slide 35) بالـ standard library: بيقولك أول طبقة اتغيرت، وبالتالي من فين الـ cache اتلغى.

python
import hashlib
import json

ORDER = ("tools", "system", "first_message")   # fixed order, most stable first


def digest(value) -> str:
    text = json.dumps(value, sort_keys=True, ensure_ascii=False)   # sorted: same input, same text
    return hashlib.sha256(text.encode("utf-8")).hexdigest()[:12]


def section_hashes(prompt: dict) -> dict:
    return {name: digest(prompt[name]) for name in ORDER}


def first_changed(prev: dict, cur: dict):
    for name in ORDER:
        if prev[name] != cur[name]:
            return name          # this section and everything after it miss the cache
    return None


before = {"tools": [{"name": "Shell", "description": "Run a command"}],
          "system": "You are Bot.", "first_message": "env: linux"}
after = {**before, "tools": [{"name": "Shell", "description": "Run a shell command"}]}

print(first_changed(section_hashes(before), section_hashes(after)))   # -> tools

تغيير كلمة في وصف أداة واحدة كفاية إن الـ output يبقى tools، يعني الـ request الجاي كله miss. ده سبب قاعدة الـ note بدل النص الجديد في المحادثات الشغالة.

Diagram ​

اقرا الرسمة من فوق لتحت: كل طبقة بتعتمد على اللي فوقها. تغيير في الأدوات (فوق خالص) بيلغي الخمس طبقات؛ رسالة جديدة (تحت خالص) مابتلغيش حاجة، بتتضاف بس.

Limitations and common misconceptions ​

  • "الـ cache بيخلي الـ model يفتكر." لأ. الـ model لسه بيقرا الـ context كله كـ input؛ الـ cache بيرخّص ويسرّع معالجة الـ prefix بس.
  • "الـ caching بيحل مشكلة الـ context الطويل." بيرخّص إعادة القراية، بس الـ context لسه طويل، وده موضوع Context Compaction وThe Context Tax.
  • الـ breakpoint على الجزء المتغير بيخليك تدفع write كل مرة من غير ولا read [anthropic-prompt-caching, How automatic prefix checking works].
  • الأرقام خاصة بالـ provider والموديل والتاريخ: الأسعار والـ TTL والحد الأدنى للطول بيتغيروا.
  • التسخين مش ببلاش: لو المستخدم مابعتش حاجة، دفعت write على الفاضي.

Exercises ​

Exercise: Where to put the timestamp

agent بيحط الوقت الحالي في أول الـ system prompt. إيه اللي بيحصل للـ cache، وإيه الحل؟

Solution

الـ system prompt بيتغير كل request، فالـ system والـ messages بيبقوا miss دايمًا (الأدوات بس اللي ممكن تفضل cached). الحل اللي في المحاضرة: الوقت يروح في آخر الـ prompt مع الرسالة الجديدة [cs146s-1008, slide 33].

Exercise: Break-even

بنفس أسعار المثال، لو agent بيبعت request واحد بس كل 10 دقايق بـ 5-minute TTL، الـ cache بيوفر ولا بيخسر؟ وإيه البديل؟

Solution

بيخسر: كل request بيلاقي الـ cache انتهى، فبيدفع write بـ 1.25 × بدل 1 × من غير read أبدًا. البديل الـ 1-hour TTL (write بـ 2 × مرة واحدة، وبعدها reads بـ 0.1 × طول الساعة)، أو إنك ماتعملش cache خالص [anthropic-prompt-caching, Pricing].

Exercise: A deploy changed a tool description

عندك 500 محادثة شغالة، وdeploy غيّر وصف أداة. ليه المحاضرة بتبعت note بدل ما تحدّث النص؟

Solution

تحديث الوصف بيغيّر أول طبقة، فالـ 500 محادثة كلهم هيدفعوا write للـ prompt كله في الـ request الجاي. الـ note بتتضاف في الآخر فالـ prefix يفضل زي ما هو، والوصف الجديد يدخل مع الملخص الجاي [cs146s-1008, slide 35].

Key takeaways

  • الـ cache مربوط ببداية الـ prompt: tools ثم system ثم messages.
  • الثابت أولًا والمتغير آخرًا؛ أي تغيير بدري بيلغي كل اللي بعده.
  • الـ write أغلى من الـ input العادي، والتوفير بييجي من الـ reads اللي جوه الـ TTL.
  • في agent بيشتغل طويل، الـ cache miss غلطة في التصميم: ثبّت الأدوات، وابعت notes، ولخّص والـ cache warm.

Review questions ​

  1. ليه تغيير وصف أداة واحدة أغلى من رسالة جديدة طويلة؟
  2. إمتى الـ prompt caching بيزوّد التكلفة بدل ما يقللها؟
  3. إيه علاقة الـ compaction بالـ cache، وليه توقيته مهم؟
  4. ليه الـ hash لكل section أحسن من hash واحد للـ prompt كله؟
