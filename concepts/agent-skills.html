Agent Skills ​

ReviewedPublishedAI-assisted

A folder with a SKILL.md file (plus optional scripts, references, and assets) that packages a repeatable procedure; the agent sees only its name and description until a task needs it, then loads the instructions and files step by step.

Definition ​

Definition: Agent skill

الـ skill هو folder فيه ملف SKILL.md: فوق frontmatter فيه name وdescription، وتحته تعليمات Markdown، ومعاه لو محتاج scripts/ وreferences/ وassets/ [agentskills-spec]. الـ agent بيشوف الاسم والوصف بس لحد ما مهمة تحتاج الـ skill، وساعتها بيحمّل التعليمات، وبعدين الملفات اللي خطوة معينة محتاجاها [agentskills-home]. الـ slides بتاعة CS146S بتلخصه: "Like scripts for agents" [cs146s-1006, slide 5].

الـ prompt العادي بيقول للـ agent يعمل حاجة دلوقتي. الـ skill بيعلّمه يعمل نوع شغل كل مرة بنفس الطريقة.

Learning objectives ​

  • تكتب SKILL.md صحيح حسب الـ spec، وتعرف كل حقل بيعمل إيه.
  • تشرح الـ progressive disclosure بمستوياته التلاتة، وليه وجود skills كتير رخيص.
  • تكتب description بيشغّل الـ skill في الوقت الصح ومايشغّلوش في الوقت الغلط.
  • تفرّق بين الـ skill وAGENTS.md والـ MCP والـ hook والـ subagent.
  • تقرر إمتى prompt يستاهل يبقى skill، وتقيّم skill بمقارنة with وwithout.

Intuition ​

تخيل موظف جديد. كل مرة بتطلب منه code review بتقوله نفس الكلام: اقرا المطلوب، شوف الملفات اللي اتغيرت، شغّل الـ tests، وماتقولش إنها عدّت إلا لو شغلتها. بعد كام مرة، الأحسن تكتب الكلام ده في ورقة اسمها "إزاي نعمل code review هنا" وتحطها في الدرج. الموظف مش هيقراها كل يوم الصبح؛ هيبص على عنوانها بس، ولما يجيله review هيفتحها.

ده بالظبط الـ skill: العنوان (الـ description) دايمًا قدام الـ agent، والورقة نفسها (الـ SKILL.md) بتتفتح وقت الحاجة، والملاحق (الـ references/) بتتقري لو خطوة معينة احتاجتها.

Formal explanation ​

Anatomy of a skill ​

حسب الـ spec، الـ skill folder فيه على الأقل SKILL.md [agentskills-spec]:

PartRule
namerequired؛ لحد 64 حرف، lowercase وأرقام وشرطة بس؛ لازم يطابق اسم الـ folder
descriptionrequired؛ لحد 1024 حرف؛ بيقول الـ skill بيعمل إيه وإمتى يتستخدم
license، compatibility، metadata، allowed-toolsاختياريين؛ allowed-tools لسه experimental
Bodyتعليمات Markdown من غير قيود شكل؛ الأحسن أقل من 500 سطر و5,000 token
scripts/كود الـ agent بيشغّله
references/توثيق إضافي بيتقرا وقت الحاجة؛ ملفات صغيرة ومركزة، ومستوى واحد من الـ SKILL.md
assets/templates وصور وبيانات

Claude Code بيمشي على نفس الـ standard وبيزوّد عليه: أماكن الـ skills (personal في ~/.claude/skills/، وproject في .claude/skills/، وplugins)، وتشغيل بـ /skill-name، وحقول زي disable-model-invocation وcontext: fork اللي بيشغّل الـ skill في subagent. والـ custom commands القديمة في .claude/commands/ اتدمجت في الـ skills [cc-skills].

Progressive disclosure ​

الفكرة الأساسية اللي بتخلي الـ skills تكبر من غير ما تاكل الـ context. Anthropic بتسميها "the core design principle that makes Agent Skills flexible and scalable" [zhang2025]:

  1. Metadata (حوالي 100 token لكل skill): الـ name والـ description لكل الـ skills في أول الجلسة.
  2. Instructions: الـ SKILL.md كله لما الـ skill يتفعّل.
  3. Resources: ملفات scripts/ وreferences/ وassets/ لما تتطلب بس [agentskills-spec].

والـ script بالذات مميز: الـ agent بيشغّله ومابيقراش الكود نفسه، فالـ output بس هو اللي بيدخل الـ context [zhang2025]. وعشان كده الـ slides بتاعة Lee Robinson بتقول إن الـ skills بتتحمل وقت الحاجة، "so having many of them is cheap" [cs146s-1008, slide 12]. الفرق عن MCP التقليدي، اللي بيحط كل تعريفات الأدوات في كل request، متشرح في The Anatomy of a Modern Coding Agent.

ومهم تعرف حاجة عملية في Claude Code: الـ skill لما يتحمل بيفضل في المحادثة لحد آخرها، وClaude Code مابيرجعش يقرا الملف تاني. ولما الـ compaction يحصل، بيرجّع أحدث نسخة من كل skill اتستخدم، بس أول 5,000 token منه، وفي budget مشترك 25,000 token، فالـ skills القديمة ممكن تقع [cc-skills]. يعني أهم التعليمات تتحط في أول الملف.

How a skill gets triggered ​

الـ agent بيقرر يحمّل الـ skill من الـ description لوحده، فالـ description شايل "the entire burden of triggering" [agentskills-desc]. ونصايح الكتابة [agentskills-desc; agentskills-spec]:

  • اكتبه كتعليمة للـ agent: "Use this skill when..." مش "This skill does...".
  • ركّز على اللي المستخدم عايزه، مش على تفاصيل التنفيذ.
  • اذكر المواقف صراحة، حتى لو المستخدم مش هيقول اسم المجال.
  • خليه مختصر: جملتين لفقرة قصيرة.

ونفس المعنى على الـ slides: "Include situations and request phrases that should trigger the skill" [cs146s-1006, slide 13]. وملحوظة مهمة: الـ agents غالبًا بتلجأ للـ skill لما المهمة محتاجة حاجة فوق قدرتها العادية؛ طلب بسيط زي "اقرا الـ PDF ده" ممكن مايشغّلش PDF skill حتى لو الوصف مطابق [agentskills-desc].

في Claude Code تقدر تتحكم مين يشغّل الـ skill [cc-skills]:

When does a prompt deserve to become a skill ​

الإشارة الأوضح: تصحيح بيتكرر. الـ slides بتقول "Mine your own transcripts": ارجع لمحادثاتك وشوف تدخلت فين [cs146s-1006, slide 12]. والـ agentskills.io بيقول نفس الكلام: كمّل مهمة حقيقية مع الـ agent، وبعدين استخرج الخطوات اللي نجحت والتصحيحات اللي عملتها والـ context اللي ادّيته [agentskills-bp].

وبعد ما تقرر، افصل جزئين:

  • Stable workflow: الخطوات اللي بتتكرر كل مرة. دي مكانها الـ SKILL.md.
  • Variable context: التفاصيل اللي بتختلف من مهمة للتانية. دي مايتفرضش عليها افتراض ثابت؛ الـ skill بيقول للـ agent يكتشفها أو يسأل عنها.

مثال: skill بيضيف كورس لموقع ملاحظات ممكن يفرض "اتأكد من المصدر الرسمي"، بس مايفترضش إن كل محاضرة ليها فيديو منشور.

وراجع كل skill بأربع أسئلة:

ElementQuestion
Trigger conditionsإمتى يشتغل، وإمتى مايشتغلش؟
Execution stepsإيه الخطوات وبأي ترتيب؟
Referencesإيه اللي يتحمّل وقت الحاجة بس؟
Acceptance criteriaإيه الدليل إن الشغل اتعمل صح؟

كل سؤال ليه أساس في التوثيق الرسمي: الـ description بيحدد الـ trigger [agentskills-desc]، والـ workflows والـ checklists للمهام متعددة الخطوات [agentskills-bp]، والـ references بتتقري لما يتقال للـ agent إمتى يقرا كل ملف [agentskills-bp]، والـ validation loops والـ verification skill للدليل [agentskills-bp; cs146s-1006, slide 13]. (الإطار ده بالأربع أسئلة وفكرة stable/variable جايين من صفحة study notes تانية في نفس ملف الـ notes، بتنسب نفسها لـ "Chinese study notes"، ومش من قراءات الكورس. أصلها مااتلاقاش، فالإطار هنا مسنود على المصادر الرسمية بس.)

A file is not evidence

إن الـ agent كتب تقرير أو عمل ملف مش معناه إن المهمة نجحت. الـ acceptance criteria لازم تبقى حاجة تتشاف: test اتشغل ونتيجته، أو محتوى اتقارن بالمصدر، أو شرط اتحقق.

Evaluating a skill ​

إن الـ skill اتفعّل معناه إن الـ agent لقاه، مش إنه عمل المطلوب. فيه سؤالين منفصلين: هل بيتفعّل على الـ prompts الصح؟ وهل الـ output أحسن لما يتفعّل [cc-skills]؟

  • Baseline comparison: شغّل كام prompt واقعي في session جديدة مرة بالـ skill ومرة من غيره، وقارن. الـ session الجديدة مهمة لأن الـ context اللي فاضل من كتابة الـ skill بيخبّي النواقص [cc-skills].
  • Should-trigger وshould-not-trigger: اكتب queries المفروض تشغّله، وqueries المفروض ماتشغلوش. وأهم الحالات السلبية هي الـ near-misses: طلبات فيها نفس الكلمات بس محتاجة حاجة تانية [agentskills-desc].
  • Evaluation-driven development: شغّل الـ agent من غير skill على مهام حقيقية، وسجّل الفشل، واعمل 3 سيناريوهات تختبره، وبعدين اكتب أقل تعليمات تعدّيهم [claude-skills-bp].
  • Versions: احتفظ بالنسخة القديمة وقارن. الـ skill-creator plugin بيعمل blind A/B بين نسختين، وبيولّد should-trigger وshould-not-trigger prompts ويقترح تعديلات على الـ description [cc-skills].
  • غيّر حاجة واحدة في المرة (نصيحة عامة في التجارب): لو غيّرت الـ skill والموديل والأدوات مع بعض، مش هتعرف إيه اللي فرق.

Security ​

الـ skill مش "مجرد Markdown". تعليماته ممكن تخلي الـ agent يشغّل أوامر أو يعدّل ملفات أو يبعت بيانات، وممكن يكون معاه scripts. Anthropic بتنصح تثبّت skills من مصادر موثوقة بس، ولو المصدر أقل ثقة، راجع كل الملفات والـ dependencies وأي تعليمات بتكلّم الـ network قبل الاستخدام [zhang2025].

Technical example ​

skill للمشكلة المشهورة: الـ agent بيقول "خلصت" من غير ما يشغّل حاجة. (مثال توضيحي؛ Superpowers فيها skill حقيقي بنفس الفكرة اسمه verification-before-completion [superpowers].)

text
verify-before-done/
├── SKILL.md
├── references/
│   └── project-test-commands.md
└── scripts/
    └── changed_tests.py
markdown
---
name: verify-before-done
description: Use before saying a coding task is done, fixed, passing, or ready for review.
  Also use when the user asks "did you test it?". Do not use for questions that only ask
  how code works.
---

# Verify before claiming done

1. Run `python scripts/changed_tests.py` to list the tests related to the changed files.
2. Run those tests. If you don't know the command, read references/project-test-commands.md.
3. Read the actual output. Count passed, failed, and skipped.
4. Check `git diff --stat` for changes outside the task's scope.
5. Report: the exact command, the result, and any failure, honestly.

Never write "tests pass" unless step 2 ran in this turn and its output shows it.

الأربع عناصر ظاهرة: الـ trigger في الـ description (ومعاه حالة سلبية)، والخطوات مرقمة، والـ reference بيتقري بس لو الأمر مش معروف، والـ acceptance criterion في الآخر. وأقل تقييم ليه:

QueryExpected
"Fix the failing login test and tell me when it's done"يتفعّل
"Did you actually run the tests?"يتفعّل
"What does parse_token do?"مايتفعّلش (near-miss: كود بس من غير claim إنه خلص)
"Write a test plan for the payment module"مايتفعّلش

Building a skill library ​

Recommendations, not course content

القسم ده مش من الكورس. أصله محادثة ChatGPT في الـ study notes بعنوان "Building Your Personal Engineering Skill Library — 2026 Edition". اتشال منه أي حاجة مااتأكدتش، والباقي اتراجع على الـ repos نفسها (الـ license والنشاط) يوم 2026-11-07. الأرقام والحالة بتتغير، فراجعها قبل ما تعتمد عليها.

عندك library شخصية متثبتة globally، وبتستخدم grill-me وgrill-with-docs، فالجدول ده مرجع للمقارنة والتحديث، مش قايمة تثبيت.

ملاحظات من المراجعة:

  • Overlap: فيه skills بتحل نفس المشكلة بفلسفات مختلفة: Superpowers brainstorming وgrill-with-docs، وSuperpowers test-driven-development وMatt tdd، وsystematic-debugging وdiagnosing-bugs[superpowers; mattpocock-skills]. ماتشغّلش اتنين متنافسين على نفس الـ feature.
  • اتشال: openai/skills (الـ README بيقول إن الـ repo deprecated ونقل للـ OpenAI Plugins repo)، وsentry-for-ai (موجود وMIT، بس مش skill library عامة)، وأي skill مااتأكدش وجوده.
  • Global قليل، project أكتر: الـ skills المتخصصة (security، frontend، Hugging Face) مكانها الـ project اللي محتاجها، لأن وصف كل skill بيتحمل في كل جلسة [agentskills-spec].

Limitations and common misconceptions ​

  • "A skill guarantees behavior." الـ skill context، مش كود. ممكن مايتفعّلش، أو يتفعّل ويتنسى في جلسة طويلة. القواعد اللي لازم تتنفذ كل مرة مكانها hook [cc-skills].
  • "More skills is better." الوصف بيتكلف قليل، بس skills كتير بأوصاف متداخلة بتصعّب اختيار الصح. والـ skill الواسع أوي صعب يتفعّل بدقة، والضيق أوي بيخلي مهمة واحدة تحمّل كذا skill [agentskills-bp].
  • "Longer instructions are safer." التعليمات الشاملة أوي ممكن تضر: الـ agent بيتلخبط وبيمشي ورا تعليمات مالهاش علاقة بالمهمة. خطوات مختصرة مع مثال شغال غالبًا أحسن [agentskills-bp].
  • "It's only Markdown, so it's safe." شوف قسم الـ Security فوق [zhang2025].
  • "Generate the skill with an LLM and you're done." الـ skill اللي اتكتب من معرفة الموديل العامة بيطلع عام ("handle errors appropriately"). الـ skill المفيد مبني على خبرة حقيقية وتصحيحاتك إنت [agentskills-bp].

Exercises ​

Exercise: Rewrite a weak description

الـ description ده: description: Helps with tests. اكتبه من جديد بحيث يشتغل لما المستخدم عايز يكتب tests لكود جديد، ومايشتغلش لما بيسأل عن نتيجة CI.

Solution

مثال: "Use when the user asks to write, add, or extend unit tests for new or changed code, even if they don't say 'unit test'. Do not use for reading CI results or explaining a failing pipeline." فيه تعليمة، ومواقف صريحة، وحد واضح مع الـ near-miss [agentskills-desc].

Exercise: Skill, AGENTS.md, or hook

لكل واحدة اختار: (1) "المشروع بيستخدم uv مش pip". (2) "شغّل ruff format بعد كل تعديل ملف". (3) "لما تعمل release، اتبع 9 خطوات وحدّث الـ changelog بشكل معين".

Solution

(1) AGENTS.md: حقيقة قصيرة. (2) hook: لازم يحصل كل مرة بالكود. (3) skill: إجراء طويل متكرر، وغالبًا بـ disable-model-invocation: true لأن الـ release ليه side effects [cc-skills].

Exercise: Design a trigger eval

للـ skill بتاع الـ technical example فوق، اكتب 3 should-trigger و3 should-not-trigger، منهم near-miss واحد على الأقل.

Solution

Should-trigger: "خلّصت الـ refactor؟"، "Is the bug fixed now?"، "Ready for review?". Should-not-trigger: "Explain this stack trace"، "What tests exist for auth?" (near-miss: فيها tests بس مفيش claim إنه خلص)، "Write a commit message".

Key takeaways

  • الـ skill = folder فيه SKILL.md (name + description + instructions) وملفات اختيارية.
  • الـ progressive disclosure بيخلي الوصف بس دايمًا في الـ context، والباقي وقت الحاجة.
  • الـ description شايل الـ triggering كله: اكتب إمتى يشتغل وإمتى لأ.
  • ابدأ من تصحيح بيتكرر، واكتب أقل تعليمات، وقيّم بمقارنة with وwithout.
  • الـ skill context مش ضمان؛ اللي لازم يحصل كل مرة مكانه hook.

Review questions ​

  1. إيه الحقلين الـ required في SKILL.md، وليه الـ description أهم واحد؟
  2. اشرح المستويات التلاتة للـ progressive disclosure، وإيه اللي بيدخل الـ context لما script يشتغل.
  3. إمتى تستخدم disable-model-invocation: true؟
  4. إيه الفرق بين "الـ skill اتفعّل" و"الـ skill اشتغل"؟ وإزاي تقيس الاتنين؟
  5. ليه الـ near-miss queries أهم من الـ queries السلبية العشوائية؟
