Context Window Observability ​

ReviewedPublishedAI-assisted

Definition ​

Definition: Context window observability

الـ context window observability معناها إنك تشوف وإنت شغال تلات حاجات: الـ context window مليانة قد إيه، إيه اللي مالّيها (instruction files، أدوات MCP، skills، ملفات، ولا المحادثة نفسها)، وفاضل قد إيه على الـ auto-compaction. الهدف إنك تختار إمتى تعمل compact أو clear، بدل ما الـ compaction يفاجئك في نص شغل مهم.

ده موضوع مختلف عن الـ cost monitoring. على Claude Max، الفلوس مش هي القضية؛ القضية جودة الشغل. كل ما الـ context تتملي، الموديل بيبقى أقل كفاءة، والمحاضر بيسمي المنطقة دي بشكل غير رسمي "dumb zone" (شوف The principle: simplicity). والـ compaction نفسه بيلخّص، والـ slides بتقول إنه "can be lossy" [cs146s-0924].

Learning objectives ​

  • تقرا الأرقام اللي Claude Code بيديها للـ status line وتعرف كل رقم بيتحسب إزاي.
  • تفرّق بين "نسبة من الـ context window كلها" و"نسبة من النقطة اللي الـ auto-compact بيشتغل عندها".
  • تعرف الأدوات الرسمية: /context، و/compact، و/autocompact، و/clear، والـ PreCompact hook.
  • تختار وقت الـ compaction على حدود المهام، مش على رقم ثابت بس.

Intuition ​

فكّر في عداد البنزين في العربية. العداد لوحده بيقولك فاضل قد إيه. بس السواق الشاطر عايز كمان يعرف إمتى لمبة الاحتياطي هتنور (ده الـ auto-compact)، وإيه اللي بيصرف أكتر (ده /context).

والأهم: السواق مابيستناش لحد ما العربية تقف. بيموّن في محطة مناسبة، يعني بين مشوار والتاني، مش في نص طريق سريع. وده بالظبط معنى "compact at task boundaries".

Formal explanation ​

What the numbers mean ​

Claude Code بيبعت للـ status line script بتاعك JSON على stdin، وفيه object اسمه context_window[cc-statusline, Available data]:

FieldMeaning
context_window.context_window_sizeحجم الـ window: 200000 افتراضيًا، أو 1000000 للموديلات اللي عندها extended context
context_window.used_percentageنسبة الاستخدام، محسوبة جاهزة
context_window.current_usageالـ tokens من آخر API call متقسمة حسب النوع (input، cache creation، cache read)
rate_limits.five_hour, rate_limits.seven_dayنسبة الـ 5-hour والـ 7-day limits وإمتى بيعملوا reset؛ بتظهر لمشتركين Pro وMax وUltra بس

تلات تفاصيل بتفرق [cc-statusline, Context window fields]:

  1. الـ used_percentage محسوبة من الـ input tokens بس (input + cache creation + cache read)، من غير الـ output tokens.
  2. النسبة دي من الـ window كلها، مش من النقطة اللي الـ auto-compact بيشتغل عندها. ولو ضبطت CLAUDE_CODE_AUTO_COMPACT_WINDOW، الـ docs بتقول صراحة إن النسبة دي مابقتش بتقولك الـ compaction هيحصل إمتى [cc-modelconfig, Set the auto-compact window].
  3. الـ current_usage بيبقى null في أول الـ session، وبعد /compact لحد أول API call.

والـ status line بيتحدّث مع الأحداث (رسالة جديدة، تغيير وضع، ...) بـ debounce 300 ms، ولو عايزه يتحدّث كمان على timer، فيه refreshInterval بالثواني [cc-statusline, How status lines work].

When auto-compaction fires ​

  • لو ماحددتش auto-compact window، Claude Code بيعمل compact لما المحادثة توصل لحد الموديل، مع استثناءات. أهمها: الموديلات اللي عندها native 1M window (زي Opus 4.7 وما بعده، وSonnet 5 وما بعده) بتعمل compact عند حوالي 967K token افتراضيًا [cc-modelconfig, Default auto-compact thresholds].
  • CLAUDE_AUTOCOMPACT_PCT_OVERRIDE بيخلي الـ compaction يحصل بدري (نسبة من الـ auto-compact window)، بس مايقدرش يأخّره [cc-envvars].
  • DISABLE_AUTO_COMPACT=1 بيقفل التلقائي ويسيب /compact اليدوي [cc-envvars].
  • فيه كمان idle compaction لمحادثة سايبها فاضية وحجمها كبير (الـ default من 200000 token، من v2.1.290) [cc-envvars].

My reading: عشان تعرف رقمك بالظبط، شغّل /context في session حقيقية وبص على صف الـ autocompact buffer، بدل ما تعتمد على رقم من مقال أو من أداة.

What survives compaction ​

مش كل حاجة بتتلخّص. الـ docs بتقول إن الـ system prompt بيفضل، والـ project-root CLAUDE.md والـ auto memory بيتقروا تاني من الـ disk، والـ plan بتاع plan mode بيرجع، وClaude Code بيعيد قراية لحد خمس ملفات من اللي اتقروا أو اتعدّلوا (الأحدث الأول). بس الـ rules اللي فيها paths: والـ nested CLAUDE.md بيتلخّصوا مع باقي المحادثة لحد ما ملف يطلبهم تاني [cc-contextwindow, What survives compaction].

يعني القرار المهم اللي لازم يفضل لازم يكون في ملف بيتقري تاني، مش في المحادثة بس (شوف Agent Instruction Files).

Compact at task boundaries ​

الـ docs نفسها بتقترح: اعمل /compact بتعليمات تركيز قبل ما تبدأ مهمة طويلة جديدة، واعمل /clear لما تنقل لشغل مالوش علاقة [cc-contextwindow, When your context fills up]. ونفس الفكرة في المحاضرة: بين المراحل، اكتب المهم في ملف وابدأ context جديد (Between phases: clear the context).

My reading: 80% في نص debugging صعب ممكن تبقى أحسن من compact، لأن الملخص هيضيّع تفاصيل الـ stack traces اللي لسه محتاجها. و55% بعد ما phase خلصت والـ tests نجحت ممكن تبقى أحسن وقت.

claude-context-monitor: the scoring ​

الـ score من 4 إشارات، وكل واحدة ليها حد أقصى من النقط [fomyio-monitor, How the scoring works]:

SignalMax pointsWhat it measures
Token pressure40الـ context مليانة قد إيه
Relevance drift30الـ prompt الجديد ليه علاقة بالـ session ولا لأ (بـ Claude Haiku)
Task completion20رد Claude الأخير بيقول إن المهمة خلصت ولا لأ
Conversation age10من إمتى آخر compact

الـ score من 26 بيطلع suggestion، ومن 80 ممكن يمنع الـ prompt لحد ما تعمل compact، بس ده opt-in (block_on_critical، مقفول افتراضيًا) [fomyio-monitor, Configuration].

حاجات لازم تعرفها قبل ما تفكر فيه:

  • Windows: الـ README بيقول "Windows is not yet supported" [fomyio-monitor, Requirements]، وإنت على Windows.
  • Drift check: محتاج ANTHROPIC_API_KEY وبيبعت fingerprint من المحادثة لـ Haiku (حوالي 0.0005 دولار للـ call حسب الـ README)؛ الـ token bar والـ notifications شغالين من غيره [fomyio-monitor, API key for the Haiku evaluation]. My reading: الـ API key ده بيتحاسب على حساب API منفصل، مش من الـ Max plan.
  • It costs context too: سطر الـ [CTX] بيتحقن في الـ context مع كل رسالة [fomyio-monitor, Features]. صغير، بس هو نفسه tokens.
  • الـ README بيقول إن الـ native compaction بيلخّص "the previous summary" فبيضيّع تفاصيل مع الوقت [fomyio-monitor, Smart Compact Instructions]. ماقدرتش أتأكد من ده من الـ docs الرسمية.

claude-status-line: the effective window ​

الفكرة إن الـ used_percentage الرسمي محسوب من الـ window كلها، بينما الـ compaction بيحصل قبل كده. الكاتب قاس الـ autocompact buffer على Claude Code 2.1.278 ولقاه 33,000 token ثابت، فالـ script بيقسم على الـ window ناقص 33K: 967K على موديل 1M، و167K على موديل 200K [lukaskraic-statusline, Why the denominator is not the full window]. وبيحترم CLAUDE_CODE_AUTO_COMPACT_WINDOW وautoCompactWindow وautoCompactEnabled [lukaskraic-statusline].

رقم الـ 967K متوافق مع الـ docs للموديلات اللي عندها 1M window [cc-modelconfig, Default auto-compact thresholds]. رقم الـ 167K للـ 200K window قياس الكاتب، والـ docs ماذكرتهوش؛ اتأكد منه بـ /context.

على Windows، Claude Code بيشغّل الـ status line command عن طريق Git Bash لو موجود، وإلا PowerShell، والـ docs بتنصح بـ forward slashes في الـ paths [cc-statusline, Windows configuration]. الـ script ده محتاج jq كمان. ماجربتهوش على Windows.

My reading: أبسط بداية: /statusline show model, context percentage with a progress bar, and the 5-hour limit، وClaude Code هيكتب الـ script. بعد كده لو عايز حساب الـ effective window، خد الفكرة من claude-status-line.

Limitations and common misconceptions ​

  • "Compact at 80% and you're safe." مفيش رقم سحري. الأهم إنت فين في المهمة؛ والـ docs نفسها بتربط الـ compact بالانتقال لمهمة جديدة [cc-contextwindow].
  • "The status line percentage tells me when compaction will run." لأ، النسبة من الـ window كلها، ومع CLAUDE_CODE_AUTO_COMPACT_WINDOW مابقتش بتقول ده خالص [cc-modelconfig].
  • "A summary keeps everything important." الملخص بيحل محل الأصل؛ اللي مادخلش فيه ضاع (Compaction). استخدم /compact بتعليمات، أو PreCompact hook، أو اكتب القرارات في ملف.
  • "A monitoring tool is free." أي أداة بتحقن نص في الـ context بتاكل منه، وأي أداة بتنادي موديل تاني محتاجة API.
  • الأرقام زي 967K والـ 33K buffer بتتغير مع الإصدارات؛ الـ docs بتذكر أرقام versions كتير جنب كل feature.

Exercises ​

Exercise: Two percentages

موديل بـ 1M window، والـ context فيها 750,000 input token، والـ auto-compact على الـ default. الـ used_percentage هتقول كام؟ وstatus line بتقيس من 967K هتقول كام؟

Solution

used_percentage = 750,000 / 1,000,000 = 75%. من الـ effective window: 750,000 / 967,000 ≈ 78%. نفس المثال موجود في الـ README بتاع claude-status-line. الفرق صغير هنا، بس بيكبر لو ضبطت auto-compact window أصغر، زي /autocompact 500k: ساعتها 400,000 token هتبقى 40% في الـ JSON، بس فاضل 100K بس على الـ compaction.

Exercise: Compact, clear, or wait

لكل موقف قرر: /compact بتعليمات، /clear، ولا تكمّل؟ (1) 85% وإنت في نص bug صعب لسه بتجمع stack traces. (2) 50%، الـ phase خلصت والـ tests نجحت، والـ phase الجاية بتكمّل على نفس الكود. (3) 40%، وعايز تنقل لمهمة documentation مالهاش علاقة.

Solution

(1) كمّل لو تقدر، وقبل الـ limit اكتب الملاحظات المهمة في ملف أو اعمل /compact بتعليمات تركّز على الـ bug. (2) اكتب القرارات والخطوة الجاية في ملف، وبعدين /compact بتعليمات. (3) /clear، لأن الـ context القديمة مش هتفيد وهتزاحم.

Key takeaways

  • Observability هنا = النسبة، وإيه اللي مالّيها، والمسافة للـ auto-compact.
  • الـ used_percentage من الـ window كلها ومن الـ input tokens بس؛ الـ auto-compact بيحصل قبل الحد.
  • /context بيقولك إيه اللي بياكل الـ context؛ الـ status line بتخليك تشوف الرقم طول الوقت.
  • اعمل compact أو clear على حدود المهام، واحفظ القرارات في ملفات بتتقري تاني بعد الـ compaction.
  • من الأداتين اللي اترشحوا، واحدة مش بتدعم Windows والتانية Bash script لسه صغيرة.

Review questions ​

  1. ليه 75% في الـ status line ممكن تكون أقرب للـ compaction مما تبان؟
  2. إيه اللي بيفضل بعد الـ compaction من غير ما تعمل حاجة، وإيه اللي بيضيع؟
  3. إزاي PreCompact hook يساعدك تحافظ على قرارات المشروع؟
  4. إمتى /clear أحسن من /compact؟
  5. ليه أداة بتحقن سطر في الـ context مع كل رسالة ليها تكلفة حتى لو مجانية؟
