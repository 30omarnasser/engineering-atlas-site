Durable Execution ​

ReviewedPublishedAI-assisted

Running a multi-step job so that its progress is recorded step by step and survives crashes: after a restart it resumes from the last recorded step instead of starting over, provided every step with a side effect is safe to run twice.

Also known as
durable workflow, durable workflows, workflow engine, durable execution engine

2026-11-08

Definition ​

Definition: Durable Execution

طريقة لتشغيل شغلانة فيها كذا خطوة بحيث كل خطوة بتخلص بتتسجل في مكان دايم (database أو event history). لو الـ process أو الـ server وقع في النص، الشغل بيكمّل من آخر خطوة متسجلة بدل ما يبدأ من الأول. والشرط إن أي خطوة ليها side effect تبقى idempotent: تشغيلها مرتين مايعملش ضرر [cs146s-1008, slide 21].

Learning objectives ​

  • تفرّق بين الـ job queue العادي والـ durable workflow لما الـ server يقع في نص الشغل.
  • تشرح إزاي workflow engine زي Temporal بيرجع لنفس النقطة عن طريق الـ event history والـ replay.
  • تفهم ليه "durable" مش معناها "exactly once"، وتحمي الـ side effects بـ idempotency key.
  • تفرّق بين snapshot للـ VM وcheckpoint للمهمة.

Intuition ​

تخيل agent بيعمل 4 خطوات: يعمل clone للـ repo، يشغّل الـ tests، يعدّل الكود، يكتب تقرير. وهو في الخطوة التالتة الـ server عمل restart عشان deploy.

  • لو الشغل ده job في queue عادي، الـ job بيرجع للطابور ويبدأ من الأول: clone تاني، tests تاني. ده مضيعة وقت بس، لكن لو خطوة من اللي اتعادت بتبعت إيميل أو بتدفع فلوس، يبقى عندك مشكلة حقيقية.
  • لو الشغل durable workflow، كل خطوة خلصت متسجلة. بعد الـ restart الـ engine بيقرا السجل، ويعرف إن الخطوتين الأولانيين خلصوا، ويكمّل من الخطوة التالتة [cs146s-1008, slide 21].

الفكرة شبه لعبة فيديو بتحفظ عند كل checkpoint: لو الكهربا قطعت، بترجع لآخر checkpoint مش لأول المرحلة. بس التشبيه بيقف هنا: اللعبة مابتبعتش إيميلات، والـ agent بيبعت. الخطوة اللي كانت شغالة ساعة الوقوع ممكن تكون عملت الـ side effect فعلًا ومالحقتش تسجّل إنها خلصت، وده موضوع الجزء الجاي.

Formal explanation ​

Job queue vs durable workflow ​

الـ slide بتحطهم قصاد بعض [cs146s-1008, slide 21]:

Job queueDurable workflow
لما الـ server يقع في نص turnالـ job بيبدأ من الأول وبيعيد شغل خلصبيكمّل من آخر خطوة متسجلة
اللي لازم تبنيه بنفسكالـ retries والـ timers والـ cancellationجاهزين في الـ engine (زي Temporal)
الشرطكل خطوة idempotent

وفي الـ always-on agent ده مهم لأن الـ turn الواحد ممكن ياخد ساعات، والـ deploys بتحصل كل يوم. والقاعدة اللي جنبها: "Save everything on the server. The virtual machine can then always be rebuilt" [cs146s-1008, slide 19].

How the engine resumes: event history and replay ​

في Temporal فيه نوعين من الكود:

  • الـ Workflow: الكود اللي بيرتّب الخطوات. لازم يبقى deterministic، لأن الـ engine بيرجّعه لنفس الـ state عن طريق إنه يشغّله تاني (replay) ويقارن الأوامر اللي بيطلّعها بالـ event history المتسجل. "If a failure occurs, the Workflow Execution picks up where the last recorded event occurred in the Event History" [temporal-execution, Replays].
  • الـ Activity: الخطوة اللي بتعمل I/O فعلًا. الـ docs بتقول إن العمليات اللي ممكن تفشل أو مش deterministic، "(API calls, LLM invocations, etc.) should be placed in Activities"، لأن الـ Activities ليها retry policy جاهزة [temporal-retry, Workflow Execution].

يعني في agent: الـ loop اللي بيقرر "الخطوة الجاية إيه" هو الـ workflow، وكل model call وكل tool call هو activity. والـ Activity اللي خلصت ونتيجتها اتسجلت مش بتتعاد في الـ replay [temporal-activity, Idempotency].

Durable is not exactly-once ​

هنا الغلطة الشائعة. الـ docs بتقول: "Activities won't record to the Event History until they return or produce an error. If an Activity fails to report to the server at all, it will be retried" [temporal-activity, Idempotency].

خد السيناريو ده: activity بتبعت إيميل. الإيميل اتبعت فعلًا، وبعدها على طول الـ worker وقع قبل ما يبلّغ الـ server. الـ server مايعرفش إن الإرسال نجح، فبيعمل retry، والإيميل بيتبعت مرتين. الـ engine ضمن إن الشغل مايضيعش، لكنه ماضمنش إن الـ side effect مايتكررش. عشان كده Temporal "recommends that Activities be idempotent"، وبتقول إن غياب الـ idempotency "might affect the correctness of your application but does not affect the Temporal Platform" [temporal-activity, Idempotency]: يعني المسؤولية عليك إنت.

الحل المعتاد idempotency key: رقم ثابت للعملية المنطقية (مش للمحاولة)، والخدمة اللي بتنفذ بترفض أي طلب شافت رقمه قبل كده. ونفس الفكرة على مستوى الرسايل: الـ app بيحفظ كل رسالة بـ unique ID، والـ server بيرمي أي ID شافه قبل كده، "so retries are safe" [cs146s-1008, slide 20].

Snapshot vs checkpoint ​

في الـ always-on agent فيه حاجتين بيتحفظوا، وواحدة ماتغنيش عن التانية:

  • VM snapshot: حالة الـ computer نفسه (الملفات، والـ logins، والأدوات المتثبتة). الـ VM بتتعمل snapshot لما تنام وبترجع مع أول tool call [cs146s-1008, slide 16].
  • Workflow checkpoint: حالة المهمة المنطقية: أنهي خطوة خلصت ونتيجتها إيه. دي على الـ server [cs146s-1008, slides 14, 19].

لو عندك snapshot بس، هتلاقي الملفات زي ما هي بس مش هتعرف المهمة كانت فين. ولو عندك checkpoint بس، تعرف المهمة فين بس ممكن تحتاج تبني البيئة من جديد، وده بالظبط اللي الـ slide بتقبله: الـ VM "can then always be rebuilt" [cs146s-1008, slide 19].

Technical example ​

مثال صغير بالـ standard library بس، مش Temporal: runner بيسجل كل خطوة خلصت في ملف JSON، وبعد أي crash بيكمّل من بعدها. وخطوة الإيميل محمية بـ idempotency key.

python
import json
from pathlib import Path

LOG = Path("run-log.json")       # durable record of finished steps
SENT = Path("sent-keys.json")    # stands in for the email service's dedup table


def load(path: Path) -> dict:
    return json.loads(path.read_text()) if path.exists() else {}


def save(path: Path, data: dict) -> None:
    tmp = path.with_suffix(".tmp")
    tmp.write_text(json.dumps(data))
    tmp.replace(path)            # atomic rename: never a half-written log


def send_email(key: str, to: str) -> str:
    """The *service* refuses a key it has already seen: that is what makes it idempotent."""
    sent = load(SENT)
    if key in sent:
        return sent[key]         # same result, no second email
    sent[key] = f"message-to-{to}"
    save(SENT, sent)
    return sent[key]


STEPS = {
    "clone": lambda: "repo cloned",
    "test": lambda: "18 passed, 1 failed",
    "email": lambda: send_email(key="run-42/email", to="owner"),
    "report": lambda: "report written",
}


def run() -> None:
    done = load(LOG)
    for name, step in STEPS.items():
        if name in done:
            continue             # recorded: skip it, like a replay
        done[name] = step()      # a crash here leaves `name` unrecorded,
        save(LOG, done)          # so it runs again on restart


run()

لو الـ process وقع بعد send_email وقبل save(LOG, done)، الخطوة email هتتشغّل تاني بعد الـ restart. الـ runner مش هيمنع ده؛ اللي بيمنع الإيميل التاني هو إن الخدمة بتشوف نفس الـ key (run-42/email). والـ key ثابت للعملية مش للمحاولة: لو كان بيتولد عشوائي في كل محاولة، كان مافيش أي حماية.

Diagram ​

الرسمة بتبين الفرق كله في نقطة واحدة: بعد الـ crash، الـ job queue بيرجع لأول خطوة، والـ durable workflow بيرجع لأول خطوة ماتسجلتش. والخطوة دي بالذات (الـ 3 هنا) ممكن تكون اتنفذت نصها أو كلها، فهي اللي لازم تبقى idempotent.

Limitations and common misconceptions ​

  • "Temporal بيضمن إن الخطوة مش هتتكرر." لأ. الخطوات اللي اتسجلت مش بتتعاد، لكن الخطوة اللي كانت شغالة ساعة الوقوع ممكن تتعاد [temporal-activity, Idempotency].
  • "أحط الـ LLM call جوه الـ workflow code." الـ workflow لازم يبقى deterministic عشان الـ replay؛ الـ LLM calls والـ API calls مكانها activities [temporal-retry, Workflow Execution].
  • فيه أفعال مالهاش idempotency key. زي رسالة اتبعتت لإنسان. هنا محتاج تصميم تاني: تسأل الخدمة "هل اتبعت؟" قبل الـ retry، أو تطلب موافقة قبل الفعل، أو compensation step بعده (شرح من عندي، مش من المصادر).
  • مش كل agent محتاج workflow engine. مهمة قصيرة من غير side effects، إعادتها من الأول أرخص من تعقيد engine كامل. الـ lecture بتربط الاختيار ده بـ agents بتشتغل ساعات وشهور [cs146s-1008, slides 4, 21].
  • الـ snapshot مش checkpoint، والعكس (الجزء اللي فوق).

Exercises ​

Exercise: Find the step that must be idempotent

agent بيعمل: (1) يقرا issues جديدة، (2) يلخصها بالـ LLM، (3) يفتح ticket في Jira لكل issue، (4) يبعتلك تقرير. أنهي خطوات لازم تبقى idempotent، وإيه الـ key المناسب لكل واحدة؟

Solution

(3) و(4) ليهم side effects برا النظام. key مناسب لـ (3): issue-id (ticket واحد لكل issue مهما اتعادت الخطوة). لـ (4): run-id/report أو تاريخ التقرير. الخطوة (1) قراية بس، و(2) model call تقدر تعيدها من غير ضرر (غير التكلفة)، لكن نتيجتها لازم تتسجل عشان الخطوات اللي بعدها تشتغل على نفس الملخص.

Exercise: Random keys

زميلك كتب send_email(key=str(uuid4()), to=...) جوه الـ activity. إيه المشكلة؟

Solution

كل retry بيولّد key جديد، فالخدمة عمرها ما هتشوف نفس الـ key مرتين، والـ dedup مابيشتغلش. الـ key لازم يتعمل مرة واحدة برا الـ activity (مثلًا في الـ workflow، أو من بيانات ثابتة زي run-id) ويتباصى ليها.

Exercise: Retry budget

بالـ default retry policy، لو الخدمة واقعة 10 دقايق، تقريبًا كام محاولة هتحصل؟

Solution

أول 8 retries بياخدوا 227 ثانية (من الجدول فوق). الـ 373 ثانية الباقية على 100 ثانية لكل retry = 3 كمان تقريبًا. يعني المحاولة الأولى + حوالي 11 retry (من غير وقت تنفيذ المحاولات نفسها) [temporal-retry, Default values for Retry Policy].

Key takeaways

  • الـ durable workflow بيكمّل من آخر خطوة متسجلة؛ الـ job queue بيبدأ من الأول.
  • Durable مش exactly-once: الخطوة اللي كانت شغالة ساعة الوقوع ممكن تتعاد.
  • الـ idempotency key ثابت للعملية مش للمحاولة، والخدمة اللي بتنفذ هي اللي بتعمل dedup.
  • الـ workflow code deterministic؛ الـ LLM calls والـ tools تبقى activities.
  • الـ VM snapshot بيحفظ الـ computer، والـ checkpoint بيحفظ المهمة. محتاج الاتنين.

Review questions ​

  1. ليه الـ replay بيتطلب إن الـ workflow code يبقى deterministic؟
  2. ليه activity ممكن تتعاد حتى لو اتنفذت بنجاح؟
  3. إيه الفرق بين unique ID للرسالة في slide 20 والـ idempotency key في activity؟
  4. إمتى تختار job queue بسيط بدل durable workflow؟
