Overview ​

حلقة من The Pragmatic Engineer، اتنشرت يوم 4 مارس 2026، ومدتها حوالي ساعة و37 دقيقة. المضيف Gergely Orosz بيتكلم مع Boris Cherny، اللي عمل Claude Code وبيقوده في Anthropic، وألّف كتاب Programming TypeScript [orosz2026].

الحلقة ماشية على خط واحد: Boris بقى ماكتبش كود بإيده خالص، فإزاي بيشتغل، وإزاي الفريق بيتأكد إن الكود ده سليم، وده معناه إيه لمهنة الـ software engineer. الصفحة دي مش تلخيص بالترتيب؛ هي الأفكار متجمعة حسب الموضوع، مع فصل واضح بين اللي Boris بيقوله واللي عليه دليل.

How to read this page

  • تقريبًا كل الأرقام في الحلقة تقديرات Boris في حوار، مش قياسات منشورة بمنهجية. الجدول في Claims and evidence بيوضح ده رقم رقم.
  • الـ timestamps والاقتباسات من الـ captions اللي YouTube عملها أوتوماتيك، فممكن كلمة هنا ولا هناك تختلف عن الصوت.
  • Boris بيتكلم عن منتج شركته. ده مش عيب، بس خليه في بالك وإنت بتقرا الآراء.

Learning objectives ​

  • تحكي إزاي Claude Code اتولد، وتربط ده بالـ agent loop والـ tool calling.
  • توصف workflow Boris (plan mode، وparallel sessions، وworktrees) وتفرق بين اللي هو بيعمله واللي بينصح بيه.
  • ترسم طبقات التحقق من الكود اللي الـ AI بيكتبه، وتفرق بين الـ deterministic والـ non-deterministic.
  • تشرح ليه فريق Claude Code ساب الـ vector database واستخدم glob وgrep.
  • تفرق بين الـ correlated والـ uncorrelated context windows، وعلاقتها بالـ skills والـ subagents.

Key takeaways ​

1. Coding as a means to an end ​

Boris اتعلم البرمجة من مشاكل عملية: وهو عنده حوالي 13 سنة كان بيبيع كروت Pokémon على eBay، واكتشف إن الـ HTML (ومنه الـ <blink> tag) بيخلي الإعلان يبيع بسعر أعلى [orosz2026-yt, 02:02]. وبعدها برمج آلة حاسبة TI-83 تحل مسائل الامتحان، ولما الامتحانات صعبت كتب solvers عامة، ونزل من BASIC لـ assembly عشان السرعة [orosz2026-yt, 02:43].

درس البيزنس وساب الكلية عشان يعمل startups، وعمره ماتخيل إن البرمجة هتبقى شغلانة. بالنسبة له "coding is a means to build things" [orosz2026-yt, 03:44]. ونفس الفكرة رجعت في آخر الحلقة وهو بيتكلم عن حبه للـ type systems: في الآخر البرمجة وسيلة، مش هدف [orosz2026-yt, 1:25:25].

قصة Agile Diagnosis: startup بدري من YC (حوالي 2011-2012) عملت decision-tree software للدكاترة [orosz2026-yt, 05:07]. الـ DAU كان ثابت، فـ Boris ركب الموتوسيكل وراح UCSF وقعد يراقب الدكاترة يومين [orosz2026-yt, 06:11]. لقى مشكلتين ماليهمش علاقة بالكود: الدكتور عنده حوالي 5 دقايق بين كل مريض والتاني، والكمبيوتر القديم بياخد حوالي 3 دقايق يفتح، وInternet Explorer 6 نص دقيقة كمان [orosz2026-yt, 06:31]. ولما نقلوا المنتج لـ Android، لقوا إن الدكتور ماشي وراه residents ومش عايز يبان إنه بيدوّر على الإجابة في موبايله [orosz2026-yt, 06:51]. الدرس عنده: الفكرة دايمًا hypothesis، وغالبًا هتعمل pivot مرة واتنين وتلاتة [orosz2026-yt, 05:07; orosz2026-yt, 07:32].

2. Clean codebases help people and models ​

في Meta، Boris بدأ في Facebook Groups، وبقى tech lead، وبعدين راح Instagram وهو شغال remote من Nara في اليابان [orosz2026-yt, 11:38; orosz2026-yt, 13:20; orosz2026-yt, 14:00]. هناك اتصدم: Facebook عنده stack ممتاز (Hack، وHHVM، وGraphQL، وRelay، وReact)، وInstagram كان Python والـ type checker والـ click-to-definition مش شغالين [orosz2026-yt, 14:40; orosz2026-yt, 15:21]. فاشتغل في Dev Infra وفي migrations كبيرة، ولما ساب كان بيقود code quality لكل Meta: Instagram، وFacebook، وMessenger، وWhatsApp، وReality Labs [orosz2026-yt, 15:41; orosz2026-yt, 16:42].

برنامج Better Engineering: حسب كلامه، Zuckerberg فرض إن كل مهندس يصرف 20% من وقته على الـ tech debt [orosz2026-yt, 17:02]. وBoris بيقول إن تحليل causal inference داخلي لقى إن الـ code quality بتساهم بنسبة "double-digit percent" في الإنتاجية [orosz2026-yt, 18:03]. ماقالش الرقم بالظبط، وقال إن "بعض" النتايج اتنشرت من غير ما يحدد فين.

النقطة الأهم للـ agents: لو الـ codebase في نص migration، وكل feature محتاجة تختار بين framework X وY وZ، المهندس الجديد هيتعب، والـ model كمان ممكن "يختار الغلط" [orosz2026-yt, 19:04]. نصيحته: أي migration تبدأها، كمّلها.

3. How Claude Code was born ​

أول PR: Boris دخل Anthropic حوالي أغسطس أو سبتمبر 2024 [orosz2026-yt, 21:07]. كتب أول PR بإيده، والـ ramp-up buddy بتاعه Adam Wolff رفضه وقاله يستخدم أداة داخلية اسمها Clyde [orosz2026-yt, 19:44]. Clyde كانت research code مكتوبة بـ Python، بتاخد حوالي 40 ثانية تفتح، ومش agentic [orosz2026-yt, 20:45]. أخد نص يوم يفهم الـ flags بتاعتها، وبعدها عملت الـ PR صح من أول مرة [orosz2026-yt, 21:07].

من chatbot لـ agent: عشان يفهم الـ Anthropic API، عمل chatbot بسيط في الـ terminal [orosz2026-yt, 24:16]. بعدها ادّاله tool واحدة بس: bash. وسأله "what music am I listening to?"، والموديل (Claude 3.5 Sonnet وقتها) كتب AppleScript سأل بيه الـ music player وجاب الإجابة من أول مرة [orosz2026-yt, 25:18; orosz2026-yt, 25:40]. الأداة التانية بعد bash كانت file edit، وأول 3 شهور كان شغال لوحده [orosz2026-yt, 27:02].

ده نفس الـ loop اللي اتشرح في Agent Loop: الموديل يطلب tool، والبرنامج ينفذ، والنتيجة ترجع للموديل. والمحاضرة الأولى في CS146S بنت نفس الفكرة من الصفر في حوالي 200 سطر: Building a Minimal Coding Agent.

The Bitter Lesson: الطريقة الشائعة وقتها كانت إنك تحط الموديل "in a box": function صغيرة جوه برنامج عادي. Boris بيقول العكس: الموديل حاجة قائمة بذاتها، اديله tools وسيبه يكتب ويشغّل برامج، ويعتبر ده corollary من الـ Bitter Lesson [orosz2026-yt, 26:41]. الـ essay الأصلي بيقول إن الطرق العامة اللي بتستفيد من الـ computation بتكسب على المدى الطويل الطرق المبنية على معرفة البشر بالمجال [sutton2019]. My reading: التطبيق على الـ agents هو تفسير Boris، مش حاجة الـ essay قالها.

Freedom inside limits

"سيب الموديل يختار الخطوات" مش معناها "من غير حدود". نفس الحلقة فيها permission prompts، وclassifiers، وsandbox (شوف section 7). الحرية في إزاي يحل، مش في إيه اللي مسموح.

4. Why Anthropic released it ​

بعد ما Claude Code انتشر جوه الشركة، كان فيه نقاش: نخليه ميزة داخلية ولا ننشره؟ القرار كان النشر عشان "study safety in the wild" [orosz2026-yt, 27:42]. Boris بيقسم دراسة الأمان لتلات مستويات [orosz2026-yt, 28:02]:

LayerWhat it means (as described)
Alignment and mechanistic interpretabilityعلى مستوى الموديل نفسه
Evalsالموديل في "petri dish": سيناريوهات مصطنعة
In the wildتشوف الناس بتستخدمه إزاي فعلًا، وإيه المخاطر اللي بتظهر

والانتشار الداخلي ماكانش بالإجبار: لما Dario سأله "إنتو بتجبروا الناس؟" قال لأ، الناس "vote with their feet" [orosz2026-yt, 30:30]. ودلوقتي، حسب كلامه، تقريبًا كل technical employee بيستخدمه كل يوم، ونص فريق الـ sales كمان [orosz2026-yt, 30:08]، وبيكتب "something like 80%" من الكود في Anthropic في المتوسط [orosz2026-yt, 30:51].

وملاحظة مهمة عن النمو: Claude Code ماكانش نجاح بين يوم وليلة. البداية كانت بطيئة، وأول inflection كبير كان في مايو مع Opus 4 وSonnet 4 [orosz2026-yt, 1:14:08].

5. Boris's daily workflow ​

أول جملة قالها لما اتسأل: مفيش طريقة واحدة صح، وأغلط استنتاج إنك تنسخ طريقته زي ما هي [orosz2026-yt, 32:55]. Claude Code معمول hackable لأن كل مهندس له workflow مختلف.

إمتى بطّل يكتب كود: التحول كان فوري مع Opus 4.5 (من قبل ما يتنشر، وقت الـ dogfooding). وشال الـ IDE من جهازه بعدها بحوالي شهر، لما اكتشف إنه مابقاش بيفتحه [orosz2026-yt, 31:11; orosz2026-yt, 31:32]. في ديسمبر كان بيعمل 10 لـ 20 PR في اليوم، كلهم مكتوبين بالكامل بـ Claude Code، وبيقدّر إن Opus دخّل حوالي 2 bugs في الشهر ده، مقابل حوالي 20 لو كان كتب بإيده [orosz2026-yt, 32:34]. ودلوقتي بيقول 20 لـ 30 PR في اليوم، وحجمهم من سطر واحد لآلاف السطور [orosz2026-yt, 39:45].

الـ setup:

  1. Parallel sessions: 5 terminal tabs، كل واحدة فيها checkout منفصل من الـ repo، وبيلف عليهم round-robin [orosz2026-yt, 33:36].
  2. Plan mode دايمًا تقريبًا: Shift+Tab مرتين. بيرجع لكل session لما يجيله notification، ويتناقش في الخطة. لما الخطة تبقى كويسة، الموديل "will one-shot the implementation almost every time" [orosz2026-yt, 33:56; orosz2026-yt, 37:42]. (عن plan mode كجزء من الـ harness: Plan mode.)
  3. Desktop app وworktrees: لما الـ tabs تخلص، كان بيروح للـ web، ودلوقتي الـ desktop app لأن فيه built-in worktree support، فمش محتاج checkouts منفصلة [orosz2026-yt, 34:16].
  4. الموبايل: كل يوم الصبح بيبدأ كام agent من الـ iOS app، وده بيشتغل في الـ cloud. البيئة بتتجهز بـ SessionStart hook [orosz2026-yt, 35:37]. وبيخمّن إن تلت لنص الكود بتاعه بيتكتب من الموبايل [orosz2026-yt, 35:58]. (عن الـ hooks: Hooks.)

الـ git worktree، زي ما Boris شرحه، كأن Git عمل كذا نسخة رخيصة من نفس الفولدر، فكل session تشتغل من غير ما تدوس على التانية [orosz2026-yt, 34:56]. My reading: الـ worktree بيعزل الملفات والـ branches بس؛ الـ ports، وقواعد البيانات المحلية، والـ environment variables لسه مشتركة، فلو الـ tasks بتشغّل services، محتاج عزل أكتر (containers مثلًا).

لو إنت جديد على codebase: نصيحته مختلفة. من /config اختار output style "explanatory" (أو "learning")؛ الفريق بيرشح explanatory للناس اللي لسه داخلين [orosz2026-yt, 37:00; orosz2026-yt, 37:22].

6. Code review when AI writes the code ​

زمان: Boris كان من أكتر الناس اللي بتعمل code review في Meta (بسبب فرق التوقيت ومفيش meetings). أي تعليق يتكرر كان بيكتبه في spreadsheet، ولما صف يعدّي 3 أو 4 مرات، يكتب lint rule ويريّح نفسه [orosz2026-yt, 40:48; orosz2026-yt, 41:29].

دلوقتي: نفس الفكرة بس على طبقات:

  • Claude غالبًا بيشغّل tests محليًا أو بيكتب tests جديدة. وفي repo بتاع Claude Code نفسه، بيشغّل نفسه في subprocess ويختبر نفسه end-to-end؛ وBoris بيقول إن ده بدأ يحصل لوحده مع Opus 4.5 من غير ما حد يبرمجه [orosz2026-yt, 42:11; orosz2026-yt, 42:32].
  • كل PR في Anthropic بيعدّي على review من Claude في الـ CI (claude -p، يعني الـ Agent SDK)، وده "catches maybe like 80% of bugs, something like this" [orosz2026-yt, 42:53].
  • وفيه دايمًا مهندس بيعمل الـ second pass ويوافق قبل الـ merge [orosz2026-yt, 42:53].
  • الـ type checkers والـ linters والـ build شغالين كمان. ولما يشوف حاجة "lintable" في PR زميل، بيكتب @claude يطلب lint rule على نفس الـ PR [orosz2026-yt, 44:55; orosz2026-yt, 45:16].

الـ non-determinism: Gergely سأل: الـ LLM ممكن يلقط bug مرة ويفوّته مرة. Boris قال إن الحل جزء منه deterministic (lint، types، build)، وجزء best-of-N: تشغّل كذا agent بالتوازي، وبعدين agents تانية تشيل التكرار والـ false positives [orosz2026-yt, 45:37]. وقال إن الـ code review skill اللي بيستخدموه open source. النسخة المنشورة دلوقتي plugin بيشغّل أكتر من review agent بالتوازي، وبعدين subagents تتأكد من كل issue قبل ما تتعرض [claude-plugins-code-review].

Best-of-N is not a guarantee

لو كل الـ agents شايفين نفس الـ context ونفس الافتراض الغلط، تكرار المحاولة مش هيلقط الغلط. وده سبب إن الـ deterministic checks والمراجعة البشرية لسه موجودين في الصورة.

7. A simple core with heavy safety layers ​

الـ architecture: Boris بيقول إنها بسيطة: core query loop، وشوية tools بيضيفوا ويشيلوا منهم طول الوقت، والـ TUI. والتعقيد الحقيقي في الأمان: إن كل حاجة Claude Code بيعملها تبقى آمنة وفيه human in the loop [orosz2026-yt, 47:18; orosz2026-yt, 47:39]. ده نفس مبدأ البساطة في Agent Harness.

Swiss cheese model: كل طبقة حماية فيها خروم، ومع طبقات كتير احتمال إن الهجوم يعدّي بيقل؛ Boris بيقول "count the number of nines" وتختار الحد اللي يناسبك [orosz2026-yt, 47:59]. My reading: حساب الـ nines بيفترض إن الطبقات مستقلة عن بعض؛ لو طبقتين بيفشلوا لنفس السبب، العدد بيدّي ثقة مش حقيقية.

Prompt injection في web fetch، على تلات طبقات [orosz2026-yt, 48:19]:

LayerMechanism (as described)Source
Alignmentالموديل متدرب يقاوم الـ prompt injection؛ وBoris بيقول إن Opus 4.6 هو "the most aligned model we've ever released"[orosz2026-yt, 48:41]
Runtime classifiersلو الـ request شكله prompt-injected، بيتعمله block والموديل يحاول تاني[orosz2026-yt, 49:01]
Subagent summaryنتيجة الـ web fetch بتتلخص بـ subagent، والملخص بس اللي بيرجع للـ main agent[orosz2026-yt, 49:22]

Permissions: فيه classifiers، وstatic analysis، وallow list يقدر المستخدم يعدّلها. شوية Unix utilities read-only مسموحة من غير سؤال، بس عددها قليل، لأن حتى find ليها flags بتنفذ أي أمر، وبرنامج تاني اسمه في الـ captions "set" (غالبًا sed) [orosz2026-yt, 52:50; orosz2026-yt, 53:30]. فالـ default محافظ.

وأصل الـ permission prompts: في أول internal release (سبتمبر 2024)، فرق الأمان كانوا معترضين إن الموديل يشغّل bash أصلًا. Boris وBen Mann (من مؤسسي Anthropic، واللي عيّن Boris) وصلوا لحل بسيط: لو مش متأكد، اسأل الإنسان [orosz2026-yt, 54:12; orosz2026-yt, 54:52].

8. Agentic search instead of RAG ​

في الأول Boris عمل RAG: local vector database مكتوبة بـ TypeScript على جهاز المستخدم، والـ embeddings بتتحسب بموديل في الـ cloud. اشتغلت "pretty good"، بس كان فيه مشكلتين [orosz2026-yt, 50:23; orosz2026-yt, 51:05]:

  1. Drift: الكود بيتغير، وأي function لسه متعدلة مش في الـ index.
  2. Permissions: مين يقدر يوصل للـ index؟ وإزاي تمنع حد في الـ IT من إنه يشوف بيانات حد تاني؟

جربوا كمان إن الموديل يعمل index لكل حاجة recursively، وجربوا glob وgrep، و"agentic search just outperformed everything" [orosz2026-yt, 51:27]. والتعريف بتاعه: "It's just a fancy word for glob and grep" [orosz2026-yt, 51:49]. والفكرة جت من Instagram: لما click-to-definition ماكانش شغال، المهندسين كانوا بيدوروا على foo( في الـ global index [orosz2026-yt, 52:10].

This is about code, not every corpus

الكلام ده عن البحث في codebase: أسماء دقيقة، وملفات بتتغير كل دقيقة، وموديل يقدر يكرر البحث. في آلاف المستندات اللي الكلام فيها مش بنفس الألفاظ، الـ semantic أو الـ hybrid retrieval ممكن يفضل أحسن. الدرس العام: جرّب الأبسط الأول، وقيس قبل ما تضيف complexity.

وده جزء من ثقافة تجريب أوسع: الـ spinner لوحده، حسب كلامه، عدّى على حوالي 100 iteration، ونزل منهم للـ production حوالي 10 لـ 20 [orosz2026-yt, 50:03].

9. Team culture: one title, everyone codes, prototypes over PRDs ​

  • عنوان واحد: كل الناس في Anthropic "Member of Technical Staff". الفكرة إنك تفترض إن أي حد بيعمل أي حاجة، بدل ما تشوف "software engineer" على Slack وماتسألوش سؤال product [orosz2026-yt, 55:14; orosz2026-yt, 56:16].
  • الكل بيكتب كود: data scientist في الفريق بدأ يستخدم Claude Code يشغّل SQL queries، والأسبوع اللي بعده الصف كله من الـ data scientists عمل كده. ودلوقتي في فريق Claude Code المهندسين، والـ engineering manager، والديزاينرز، والـ data scientists، وحتى "our finance guy" بيكتبوا كود [orosz2026-yt, 57:38; orosz2026-yt, 58:18].
  • Prototypes بدل PRDs: "we don't really write stuff. We just we show" [orosz2026-yt, 1:00:23]. وBoris بيقول جزء من السبب إن Anthropic لسه startup ومفيش ناس كتير محتاج تتفق معاهم [orosz2026-yt, 59:21]. أمثلة:
    • Gergely افتكر من thread لـ Boris إنه عمل 15 لـ 20 prototype شغالين للـ to-do list في حوالي يوم ونص [orosz2026-yt, 59:42; orosz2026-yt, 1:00:02].
    • الـ condensed view لنتايج الـ file reads والـ search: حوالي 30 prototype، وبعدين dogfooding جوه الشركة حوالي شهر، وحوالي dozen تعديل، وبعد الإطلاق اتعدلت تاني من feedback على GitHub [orosz2026-yt, 1:03:08; orosz2026-yt, 1:03:29].
    • وقال: "I'm wrong like half the time" [orosz2026-yt, 1:02:05]. لما تكلفة البناء تقل، بتجرب بدل ما تصوّب كويس قبل الطلقة الوحيدة.

My reading: ده وصف فريق صغير بيبني developer tool وبيدوق منتجه بنفسه. في مشروع فيه عملاء كتير، أو متطلبات قانونية، أو فرق كتير محتاجة تتفق، كتابة المتطلبات لسه ليها دور؛ الـ prototype بيغيّر إمتى بتكتب، مش بيلغي الحاجة للاتفاق.

10. Agent teams and uncorrelated context windows ​

Agent teams هي implementation بتاعتهم للـ swarms: lead agent بيوزع شغل على teammates، وبينهم تواصل [orosz2026-yt, 1:00:44; orosz2026-yt, 1:14:28]. Daisy وSuzanne وKaren جربوا "hundreds of versions" لشهور قبل ما الـ UX يبقى كويس [orosz2026-yt, 1:01:05].

الفكرة الأساسية اسمها uncorrelated context windows [orosz2026-yt, 1:15:31]:

  • لو الموديل عمل task وبعدين task تانية في نفس الـ window، التانية "عارفة" الأولى: correlated.
  • الـ subagent بيبدأ بـ window فاضية؛ مايعرفش غير الـ prompt اللي الـ parent بعتهوله: uncorrelated.
  • الـ skill أو الـ slash command بيشوفوا الـ parent context window، فهما correlated [orosz2026-yt, 1:15:52]. (عن الـ subagents في الـ harness: Subagents.)

Boris بيقول إن رمي tokens أكتر على المشكلة في windows uncorrelated بيدّي نتايج أحسن، ويعتبره "a form of test time compute" [orosz2026-yt, 1:16:12]. جربوا الـ teams من حوالي سبتمبر أو أكتوبر، و"it clicked" مع Opus 4.6 في evaluations داخلية لمهام أعقد من اللي Claude واحد يعمله [orosz2026-yt, 1:16:32; orosz2026-yt, 1:16:53]. ونزلت research preview ومحتاجة opt-in لأنها بتاكل tokens كتير، ومناسبة للمهام المعقدة بس [orosz2026-yt, 1:17:13].

قصة الـ plugins: Daisy شغّلت نسخة بدرية من الـ swarms طول weekend: طلبت منها تكتب spec، وتعمل Asana board، وتقسّم الشغل tasks، والـ agents تنفذ. اشتغلت في container، وClaude في "dangerous mode". عملت "a couple hundred agents" وحوالي 100 task، وBoris بيقول إن ده "pretty much the version of plugins that we shipped" [orosz2026-yt, 1:04:31; orosz2026-yt, 1:04:51].

Do not copy the plugins setup as-is

الـ "dangerous mode" معناه إن الـ agents بتنفذ من غير ما تسأل. ده كان جوه container معزول. على جهازك أو على repo فيه secrets، نفس الإعداد ده خطر.

11. Claude Cowork ​

ليه اتعمل: latent demand. ناس مش مهندسين كانوا بيستخدموا Claude Code: واحد بيراقب زرع الطماطم بكاميرا، وواحد بيرجّع صور فرحه من hard drive بايظ، وفريق الـ finance والـ sales في Anthropic [orosz2026-yt, 1:05:53; orosz2026-yt, 1:06:13; orosz2026-yt, 1:06:34].

اتبنى في حوالي 10 أيام بفريق صغير، وبالكامل بـ Claude Code [orosz2026-yt, 1:07:37]. بس ده مش من الصفر: هو tab في نفس الـ Claude desktop app، وتحته نفس Claude Code ونفس الـ Agent SDK [orosz2026-yt, 1:08:40; orosz2026-yt, 1:09:00]. التعقيد الجديد أغلبه أمان: classifiers في الـ backend، وvirtual machine بتتشحن مع الـ app، وintegrations على مستوى الـ OS عشان محدش يمسح صور العيلة بالغلط، وإعادة تفكير في الـ permission system مع الـ Chrome extension [orosz2026-yt, 1:09:21; orosz2026-yt, 1:09:41]. الـ stack: Electron وTypeScript [orosz2026-yt, 1:11:23].

مثال Boris: كل أسبوع بيطلب من Cowork يبص على spreadsheet الفريق، ويلاقي الصفوف اللي الـ status فيها فاضي، ويبعت للمهندس على Slack. بيفتح tab للـ spreadsheet وtab لـ Slack، وبيعملها من أول مرة تقريبًا [orosz2026-yt, 1:10:02; orosz2026-yt, 1:10:43].

Observability مع privacy: بيستخدموا خليط من vendors جاهزين وكود داخلي. بس لأنهم enterprise company، Boris مايقدرش يفتح logs المستخدم لما حد يبلّغ عن bug، فشغل كتير بيروح في logging بيحافظ على الـ privacy [orosz2026-yt, 1:13:07; orosz2026-yt, 1:13:27].

Exercises ​

Exercise: Turn review comments into checks

عندك التعليقات المتكررة دي في الـ PRs: (1) الـ function مالهاش type hints، (2) except Exception: pass، (3) أسماء variables مش واضحة، (4) الـ PR غيّر behavior من غير test. لكل واحدة قول: ينفع تبقى lint rule deterministic، ولا محتاجة reviewer (AI أو إنسان)؟

Solution

(1) deterministic: type checker أو rule زي ANN في ruff. (2) deterministic: rule بتمنع الـ bare except والـ pass الفاضي. (3) مش deterministic بالكامل: rules للطول والـ style ممكن، بس "واضح" حكم محتاج reviewer. (4) جزئيًا: الـ CI يقدر يطلب إن الـ coverage ماتقلش، بس "الـ test ده بيختبر الـ behavior الصح" محتاج reviewer.

Exercise: Correlated or uncorrelated?

لكل حالة، قول هل الـ context correlated ولا uncorrelated، وده كويس ولا وحش هنا: (أ) skill بتعمل format لملف لسه معدّل، (ب) reviewer بيراجع PR كتبه نفس الـ agent في نفس الـ session، (ج) 3 subagents بيدوروا على سبب bug من تلات اتجاهات.

Solution

(أ) correlated، وده كويس: الـ skill محتاجة تعرف إيه اللي اتعدل. (ب) correlated، وده وحش: الـ reviewer شايف نفس الافتراضات اللي عملت الكود، فممكن يفوّت نفس الغلط؛ الأحسن reviewer بـ fresh context. (ج) uncorrelated، وده كويس: كل واحد يبدأ من غير افتراضات التاني، بس على حساب tokens أكتر.
