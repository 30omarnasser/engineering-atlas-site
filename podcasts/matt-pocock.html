Overview ​

حلقة من بودكاست The Pragmatic Engineer، المضيف فيها Gergely Orosz والضيف Matt Pocock، صاحب Total TypeScript وAI Hero واللي عامل الـ skills repo المشهور mattpocock/skills [pe2026]. أول نص ساعة تقريبًا عن قصته: من voice coach لـ developer لـ educator. الباقي (من حوالي 30:32) هو اللي يهمنا: إزاي بيشتغل مع الـ coding agents، وليه رجع لكتب software engineering قديمة عشان يخلي الـ agents تشتغل أحسن [pe2026].

الفكرة اللي بتربط كل الحلقة: الـ agent بيقدر يعمل الشغل الـ tactical (كتابة الكود نفسه)، والقيمة اتنقلت للشغل الـ strategic: تصميم النظام، وتقسيم الشغل، وتحسين البيئة اللي الـ agent بيشتغل فيها [pe2026-video, 27:01].

How this episode was identified

الـ study notes الأصلية مافيهاش اسم البرنامج ولا لينك. الحلقة دي هي اللي محتواها بيطابق الـ notes: grill-me، وwayfinder، والـ smart zone، والـ tracer bullets والـ leading words، والـ DDD، ورأيه في الـ TDD، والـ gardeners، والـ observability، وترشيح نفس التلات كتب، والجملة "your code is the environment the agent operates in". التفاصيل في الـ verification ledger.

Learning objectives ​

  • تشرح الفرق بين الـ tactical والـ strategic programming، وليه Matt شايف إن الـ AI غيّر وزن كل واحد.
  • ترسم الـ workflow بتاعه: grill-me ثم spec ثم tickets ثم ticket واحدة في كل session.
  • تختار بين "align afterwards" وgrill-me وwayfinder حسب حجم الشغل.
  • تفرّق بين اللي Matt بيعتقده من تجربته واللي فيه دليل فعلي.
  • تقارن طريقته بـ RePPIT من غير ما تفترض إن واحدة أصل التانية.

Key ideas ​

1. Tactical vs strategic programming ​

Matt واخد التقسيمة دي من John Ousterhout (A Philosophy of Software Design): الـ tactical programming هو إنك تخلّص الحاجة اللي قدامك، والـ strategic هو التفكير طويل المدى في شكل النظام. ورأيه إن الـ AI "أكل" الجزء الـ tactical تقريبًا، وإن الـ strategic بقى شغلنا إحنا [pe2026-video, 27:01].

ده مش معناه إنك مش محتاج تفهم الكود. Matt قال صراحة إن تحسين البيئة دي محتاج tactical knowledge: تفهم الكود متركّب إزاي وإيه قيوده [pe2026-video, 1:02:35]. والسبب إن الـ strategic مهارة صعبة تتعلمها: الـ feedback loop بتاعها طويل جدًا. شبّهها بـ mixing desk فيه sliders كتير (microservices ولا monolith مثلًا)، وإنت مش هتسمع الغلط غير بعد 9 شهور. ورأيه إن الـ AI بيسرّع الشغل، فالأخطاء الـ strategic بترجعلك أسرع [pe2026-video, 1:01:27].

2. grill-me: align before you delegate ​

الـ skill دي بسيطة جدًا: بتقول للـ agent يعمل معاك interview "relentlessly" لحد ما توصلوا لفهم مشترك [pe2026-video, 34:39]. الفكرة جاتله من Thariq Shihipar من Anthropic، اللي قال إنك لما تخلي الـ agent يعمل معاك interview النتايج بتبقى أحسن [pe2026].

Matt بيقول إن المشكلة اللي بتحلها هي فجوة التواصل: الـ agent، مهما كان الموديل ذكي، مش بيقرا أفكارك. لازم يبقى فيه process تنقل بيه قيمك وأولوياتك للـ agent: إيه جوه الـ scope، وإيه براه، وإيه المهم بالنسبالك [pe2026-video, 37:29]. والمثال اللي اتحكى في الحلقة كان بتاع Gergely نفسه: endpoint بسيط يرد على "الإيميل ده subscriber ولا لأ"، والـ skill سألته 35 سؤال، منها نوع الـ authentication (bearer token ولا غيره) وإزاي يطبّق الـ rate limits [pe2026-video, 01:07].

ملف الـ skill النهارده بيوضح الطريقة أكتر من الحلقة: الأسئلة بتتعامل كـ design tree، وكل round بيسأل كل الأسئلة اللي شروطها اتحسمت (الـ frontier)، ومع كل سؤال إجابة مقترحة. والأهم: الحقائق (facts) شغلة الـ agent يدوّر عليها بنفسه، والقرارات (decisions) بتاعة المستخدم [pocock-skills, skills/productivity/grilling/SKILL.md].

3. The smart zone and the dumb zone ​

الفكرة دي Matt بينسبها لـ Dex Horthy: كل ما تحط context أكتر، كل token بيتنافس على الـ attention، والموديل بيبدأ يفقد الربط بين الحاجات ويغلط [pe2026-video, 41:14]. وتقديره الشخصي إن الـ smart zone حاليًا حوالي أول 150,000 token في الموديلات الكبيرة، مهما كان حجم الـ context window، وبعدها الجودة بتنزل تدريجيًا [pe2026-video, 41:57].

ومن هنا السؤال اللي بنى عليه كل الـ skills: إزاي تاخد شغل أكبر من 150K token وتوزعه على كذا session [pe2026-video, 41:57]. أول محاولة كانت الـ Ralph loops: تدي الـ agent هدف، يعمل أصغر تغيير يقرّبه منه، وبعدين تمسح الـ context. الحالة مش بتضيع، لأنها محفوظة في الـ codebase والـ file system، مش في الموديل [pe2026-video, 42:18]. (نفس المصطلح "dumb zone" ظهر في المحاضرة، شوف Agent Harness.)

4. Spec, tickets, and one ticket per session ​

عشان يخلي فكرة الـ Ralph loop أثبت، Matt وصل لنوعين من المستندات [pe2026-video, 43:08]:

  • مستند للوجهة (destination): كان بيسميه PRD، ودلوقتي بيسميه spec. ده اللي بيحدد إمتى الشغل خلص.
  • tickets: الـ spec بتتقسم لـ tickets، ticket واحدة لكل session [pe2026-video, 43:21].

والـ flow: grill، وبعدين حوّل الـ grilling لـ spec، وبعدين شغّل implement loop على الـ tickets. والـ spec الواحدة ممكن تغطي 30 أو 40 ticket [pe2026-video, 43:23].

الرسمة تجميع من الحلقة ومن ملفات الـ skills (to-spec، to-tickets، implement)، مش رسمة عرضها Matt. ملف to-tickets بيقول إن كل ticket هي tracer-bullet vertical slice، مقاسها يكفي context window واحدة، ومعاها acceptance criteria وblocking edges [pocock-skills, skills/engineering/to-tickets/SKILL.md]. وملف implement بيطلب TDD لو ينفع، وtypecheck وtests، وبعدين code review، وبعدين commit [pocock-skills, skills/engineering/implement/SKILL.md].

ليه الـ loop ده؟ Matt كان عايز يشتغل بـ day shift وnight shift: تخطط بالنهار، والـ agents تشتغل بالليل (أو وإنت بتعمل حاجة تانية)، وتصحى تراجع كود نضيف، بدل ما تفضل تنط بين terminals طول اليوم [pe2026-video, 44:05]. وقال إن اللي اكتشفه في ديسمبر إن الموديلات بقت كويسة كفاية إنك تفوّض لها وتشغّلها AFK [pe2026-video, 44:30].

5. wayfinder: planning bigger than one session ​

زي ما التنفيذ اتقسم على sessions، الـ grilling نفسه ممكن يكون أكبر من session. مثال Matt: "ابنيلي Stripe clone"؛ مستحيل تخطط ده في 150K token [pe2026-video, 45:03]. فعمل map هي المركز اللي فيه كل القرارات، ومعاها استعارة الـ fog of war: إنت عارف وجهتك تقريبًا، وكل grilling session بتكشف نقط جديدة على الخريطة [pe2026-video, 46:22]. وكل session هي ticket على الخريطة، والـ tickets أنواع: grilling، وprototype، وresearch، ومهمة عملية زي provisioning [pe2026-video, 47:00]. وقال إنه عمل maps فيها 50 لـ 100 ticket [pe2026-video, 46:43]، واستخدمها كمان في تخطيط كورس وفي بناء garden office [pe2026-video, 47:14].

ملف الـ skill بيكمّل الصورة [pocock-skills, skills/engineering/wayfinder/SKILL.md]:

  • الـ map عبارة عن issue واحدة على الـ issue tracker، والـ tickets child issues تحتها.
  • الـ wayfinder بيخطط، مابينفذش: كل ticket نتيجتها قرار، والـ map بتخلص لما الطريق يبقى واضح.
  • أنواع الـ tickets الأربعة بالظبط: research (AFK)، وprototype (HITL)، وgrilling (HITL)، وtask.
  • كل ticket متقاسة على agent session حوالي 100K token، وsession واحدة تحسم ticket واحدة بس (ما عدا الـ research).
  • اللي لسه مش واضح كفاية إنه يبقى ticket بيتكتب في قسم "Not yet specified"، مش بيتقسم بدري.

6. Choosing the workflow by size ​

Gergely سأل: الـ agents سريعة في التنفيذ، فليه نخطط كتير؟ ممكن نصلّح ونحن ماشيين. Matt قال إن grill-me مش لكل حاجة: هي للشغل الكبير اللي صعب ترجع فيه، لأن لو الـ agent عمله غلط، الكود الغلط هيفضل في الـ context ويأثر على كل اللي بعده، والتصليح بعدين مكلف [pe2026-video, 1:13:02]. أما تحريك زرار 3 pixels أو bug fix بسيط، فتقدر تعمل الـ alignment بعد التنفيذ [pe2026-video, 1:13:33].

القاعدة بكلامه: صغيرة كفاية تتظبط بعدين؟ ماتستخدمش grill-me. تكفيها session واحدة؟ grill-me. محتاجة كذا session؟ wayfinder [pe2026-video, 1:14:42]. ومثال على النوع الأول: في الـ video editor بتاعه زرار feedback بيعمل GitHub issue، يلقطها implement agent، وبعده code review agent، وهو بيشوف النتيجة في الآخر [pe2026-video, 1:14:10].

وعن تهمة "ده waterfall": Matt بيعمل prototyping كتير قبل الـ spec، لأن الـ prototypes بقت أرخص من أي وقت؛ تقدر تطلع 3 أو 4 نسخ وتختار [pe2026-video, 1:15:43].

7. Leading words: tracer bullets and vertical slices ​

قبل ده، Matt جرّب spec-driven development: spec دايمة يعدّلها والـ agent يغيّر الكود. والنتيجة كانت أسوأ من الكتابة بإيده، والكود كان بيبوظ مع كل لفة [pe2026-video, 51:43]. فرجع لـ The Pragmatic Programmer، ولقى فكرة software entropy: الأنظمة بتميل للفوضى، والـ agents بتنتج entropy أسرع من أي وقت [pe2026-video, 53:08].

المشكلة اللي كان شايفها: الـ agent بيبني الـ database كلها، وبعدين الـ application layer كلها، وبعدين الـ UI، وماحدش بيتأكد إن الطبقات بتتكلم مع بعض غير في الآخر [pe2026-video, 54:23]. الحل من الكتاب: tracer bullet (مسار صغير شغال عبر كل الطبقات بيديك feedback بسرعة)، وvertical slices بدل horizontal slices [pe2026-video, 53:50] [pe2026-video, 54:49].

ولما بدأ يستخدم الكلمات دي في الـ prompts، لاحظ إن الـ agent بيرددها في الـ reasoning بتاعه ("Okay, I'll turn this into a tracer bullet"). وسمّى ده leading word: كلمة بتكررها مرتين تلاتة في الـ skill أو الـ prompt فتغيّر سلوك الـ agent [pe2026-video, 55:21]. ومن ساعتها بيدوّر في الكتب على كلمات زيها؛ من كتاب Ousterhout أخد مثلًا deep modules [pe2026-video, 55:45].

My reading: ده تفسير معقول لأن الكتب دي غالبًا جوه الـ training data، بس اللي Matt قدمه ملاحظة من تجربته، مش قياس مقارن (شوف Claims and evidence).

8. Domain-driven design and grill-with-docs ​

بعد الكلمات اللي في الـ prior بتاع الموديل، السؤال بقى: إزاي نتكلم لغة مشتركة عن التطبيق بتاعي أنا؟ ومن هنا رجع لـ DDD بتاع Eric Evans وفكرة الـ ubiquitous language [pe2026-video, 57:14]. فعمل grill-with-docs: grilling بيبني domain language وإنت ماشي، ولما الـ agent يستخدمها تقدر توصف التغيير بكلام أقل بكتير [pe2026-video, 57:40].

مثاله: في تطبيق فيه ghost lessons وreal lessons، لو حوّلت ghost lesson جوه ghost section جوه ghost course لـ real، لازم الـ section والـ course يبقوا real كمان. الاسم اللي طلع بيه هو والـ agent: "materialization cascade" [pe2026-video, 58:18]. ولو المصطلحات دي موجودة في الكود نفسه، الـ agent بيلاقي الـ functions بـ grep بسيط [pe2026-video, 58:43].

في الـ repo، grill-with-docs بتنادي grilling وdomain-modeling مع بعض [pocock-skills, skills/engineering/grill-with-docs/SKILL.md]، وdomain-modeling بتكتب GLOSSARY.md وADRs تحت docs/adr/ أول ما المصطلح أو القرار يتحسم [pocock-skills, skills/engineering/domain-modeling/SKILL.md]. My reading: دي ملفات context دايمة شبه فكرة Agent Instruction Files، بس محتواها لغة المشروع وقراراته، مش تعليمات للـ agent.

9. Memento-driven development ​

Matt شبّه الـ agent بالراجل في فيلم Memento: بيصحى كل يوم مش فاكر هو مين. الإنسان بيتعلم يتعايش مع codebase وحشة لأنه بيبني ذاكرة عنها، لكن الـ agent بيبدأ من الصفر كل session، فلازم تظبط الـ codebase عشانه [pe2026-video, 1:00:17; pe2026]. وده اللي الـ software fundamentals بتحاول تعمله من زمان: كود مفهوم لحد شايفه لأول مرة. ومن هنا جملته: "your code is the environment the agent operates in"، ولازم تفضل تحسّن البيئة دي [pe2026-video, 1:02:35].

ده مرتبط مباشرة بالـ Agent Loop: الـ loop مابيشيلش حاجة بين الـ sessions غير اللي مكتوب في الملفات والكود.

10. TDD and proof of work ​

رأي Matt في الـ TDD متلخبط شوية، وهو قال كده [pe2026-video, 1:20:42]:

  • الـ TDD معمول لناس عندهم working memory صغيرة: الـ test الفاشل بيفكّرك إنت فين لما ترجع من البريك [pe2026-video, 1:18:42].
  • الـ agents عندها working memory أكبر بكتير (بس مش لا نهائية)، فالـ TDD "aiming at the wrong problem" بالنسبالها. اللي محتاجاه فعلًا هو feedback loops [pe2026-video, 1:19:06].
  • عشان كده بيطلب: "provide proof that your change does the thing it's purported to do"، و"Give me TDD evidence"، يعني دليل إن الـ test كان هيفشل من غير التغيير ده [pe2026-video, 1:20:02].
  • ومشكلة تانية: الـ agents بتكتب tautological tests، test بيأكد الـ implementation نفسه، زي constant بتتأكد إنه بيساوي نفسه [pe2026-video, 1:20:22].

ومع ده، لسه بينصح بالـ tdd skill بتاعته لأنها بتدي ثقة أكتر من وجهة نظر الإنسان [pe2026-video, 1:20:42]. والـ skill نفسها بتعرّف الـ tautological test كـ anti-pattern: الـ expected value لازم ييجي من مصدر مستقل (literal معروف، أو مثال محسوب، أو الـ spec) [pocock-skills, skills/engineering/tdd/SKILL.md].

11. Review agents and gardeners ​

Matt شايف إن الـ agents بتنتج tech debt بسهولة، حتى في codebase صغيرة، لأنها بتركز على اللي قدامها ومش بتفكر strategically [pe2026-video, 1:21:17]. الحل اللي لقاه شغال: implement agent يعمل الشغل، وautomated review agent يطبّق الـ coding standards ويدوّر على الـ tautological tests [pe2026-video, 1:22:09]. بس هو نفسه سأل: وإزاي تعرف إن الـ review agent شغال كويس؟ وقال إن ده حرب مستمرة [pe2026-video, 1:22:23].

وعنده loop بتشتغل كل صبح: تشغّل improve-codebase-architecture وتطلع اقتراح لحاجة يحسّنها، وهو بيدوس زرار يحوّلها لـ tickets ويشحنها [pe2026-video, 1:08:22]. الـ skill دي بتدوّر على "deepening opportunities": modules سطحية ممكن تبقى deep [pocock-skills, skills/engineering/improve-codebase-architecture/SKILL.md].

وعن تويتة "every team needs a gardener"، رد Matt إن الـ gardeners هم كل اللي فريقك محتاجه (وهو بيهزر جزئيًا) [pe2026-video, 1:31:28]. وفكرته: إحنا بقينا الـ platform team بتاع الـ agents، شغلتنا نبني البيئة اللي يقدروا ينجحوا فيها، ونشخّص الـ entropy قبل ما تبقى مشكلة [pe2026-video, 1:31:50].

12. Observability for agents ​

سؤال من مستمع: إزاي تقنع ناس مش engineers إن الاستثمار في الـ fundamentals يستاهل؟ Matt قال إنك محتاج metric، وأول خطوة observability على كل agent في المؤسسة: بيعمل إيه، ونسبة نجاحه وفشله إيه [pe2026-video, 1:06:24]. وده كان invasive مع البشر، بس مع الـ agents مقبول لأنك بتدفع تمن الخدمة [pe2026-video, 1:06:28]. وبعدها: تقارن repos نجاحها أعلى وتنقل دروسها، وتتفق المؤسسة على مجموعة skills مشتركة، وتعمل A/B tests بين فرق [pe2026-video, 1:07:08].

Matt ماذكرش metrics محددة غير الـ success والـ failure rate. جدول الـ metrics اللي في الـ study notes (first-pass success، tokens per task...) إضافة من الـ notes، مش من الحلقة.

13. Other topics ​

  • Cloud agents: Matt بينقل شغله لـ remote box عشان الـ agents تفضل شغالة والـ laptop مقفول، وعشان الـ grilling يبقى collaborative في Slack أو Discord [pe2026-video, 1:09:23; pe2026-video, 1:10:46].
  • Skills as distribution: الـ skills عنده "folder of markdown files"، منها اللي الموديل بيناديها ومنها اللي إنت بس بتناديها [pe2026-video, 30:42]. وقال إن الـ repo كان وقت التسجيل 230,000 star [pe2026-video, 31:58].

Exercises ​

Exercise: Classify the work

لكل مهمة اختار: align afterwards، ولا grill-me، ولا wayfinder، حسب قاعدة Matt. (1) تغيير لون زرار. (2) endpoint جديد بـ authentication وrate limiting. (3) نظام billing كامل من الصفر. (4) fix لـ bug واضح فيه stack trace.

Solution

(1) align afterwards. (2) grill-me: session واحدة تكفي، بس فيها قرارات (auth، rate limits) صعب ترجع فيها. (3) wayfinder: أكبر من session، وفيه قرارات مجهولة لسه. (4) align afterwards، ويستحسن تطلب "TDD evidence" إن الـ test كان بيفشل قبل الـ fix.

Exercise: Horizontal vs vertical tickets

عندك feature: "المستخدم يرفع صورة profile ويشوفها في الـ header". اكتب 3 tickets horizontal (طبقة طبقة)، وبعدين 3 tickets vertical (tracer bullets). إيه أول ticket تقدر تعمله demo؟

Solution

Horizontal: (a) جدول وstorage للصور، (b) upload API، (c) UI للرفع والعرض. مفيش حاجة تتجرب غير بعد التلاتة. Vertical: (a) رفع صورة ثابتة وعرضها في الـ header end to end (أبسط storage، من غير validation)، (b) validation للنوع والحجم في كل الطبقات، (c) crop وresize. أول ticket في الـ vertical نفسها demo.

Exercise: Spot the tautological test

الـ agent كتب DISCOUNT = 0.1 وtest بيعمل assert DISCOUNT == 0.1. ليه ده tautological؟ واكتب test أحسن لـ apply_discount(price).

Solution

الـ test بيكرر الـ implementation، فعمره ما هيختلف معاه. test أحسن بياخد الـ expected value من مصدر مستقل، زي مثال من الـ spec: assert apply_discount(200) == 180، ومعاه حالة حدّية زي apply_discount(0) == 0.

Key takeaways

  • الـ AI بياخد الشغل الـ tactical؛ قيمتك في الـ strategic: تقسيم الشغل وتحسين البيئة.
  • grill-me بتقفل فجوة التواصل: الـ agent يدوّر على الحقائق، وإنت تاخد القرارات.
  • spec للوجهة، وtickets كـ vertical slices، وticket واحدة في كل session عشان تفضل في الـ smart zone.
  • الـ codebase هي ذاكرة الـ agent الوحيدة بين الـ sessions، فنضافتها شغل أساسي مش رفاهية.
  • معظم كلام Matt خبرة ممارس، مش قياسات؛ جرّبه وقيسه بنفسك.
